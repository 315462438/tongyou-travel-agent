# 海外地名被高德国内同名 POI 污染

## 现象

协同行程的目的地是吉隆坡、仙本那、亚庇，但地图点位散落在中国多个省份。检查中心据此
计算出数百至数千公里的“步行/驾车”路段，并把整天误判为长途驾驶。

## 原因

1. 高德底图能显示海外，不代表当前 Web Service Key 拥有海外地理编码和路径权限。
   高德海外 Web Service 需要单独开通；普通国内 Key 的 POI 搜索会返回国内同名或近似结果。
2. 旧实现直接采用 `pois[0].location`，没有检查候选的国家、省、市是否与查询城市一致。
3. Phase 55 缓存键只有 `城市|地名`，没有 provider/country/version。错误结果一旦写入，
   后续重新打开、串路线和导入都会稳定复用错误坐标。
4. 多城行程的新增地点和补漏曾使用整段 `destination`，没有按逐日过夜城市约束。
5. 海外坐标仍被送入高德国内 direction，失败后没有向前端明确区分“真实路线”和“估算”。
6. 只按 `overnight_city` 也不够：转移日可能同时包含出发城和到达城，过夜城市不能代表
   当天每个地点（例如吉隆坡吃饭、去机场、当天抵达仙本那）。

## 解决办法

- 国内使用高德，候选必须通过行政区文本匹配。
- 海外先用 Open-Meteo/GeoNames 解析城市国家与锚点，再用 Photon/OSM 按 country code
  限定国家，并拒绝距城市锚点超过 120km 的候选。
- Photon 不索引中文查询名，攻略抽取需同时给海外地点生成英文/当地官方 `search_name`；
  已有行程的高频中文地点使用确定性别名。
- 新缓存键改为 `v2|provider|country|city|name`；海外不读取旧缓存。
- 导入、新增、补漏、住宿坐标全部按逐日城市查询。
- 当天城市未命中时，只在该行程的其他城市中受限重试；距离阈值收紧到 120km。
- 增加“重新定位”接口：重新解析成功则覆盖；解析失败且旧坐标离城市明显过远则清除。
- 检查中心检测一天内多次 250km+ 跳点，生成 `geocode` 告警并直达修复。
- 海外路段不调用高德 direction，使用 haversine + 交通方式估算，并返回 `estimated=true`。

## 公共全球编码服务使用约束

- 必须发送可识别的 `User-Agent`；
- 代码用进程级串行限速，避免滥用公共实例；
- 命中结果必须持久缓存；
- 前端保留 OpenStreetMap contributors 署名；
- 业务量增大时，通过 `GLOBAL_GEOCODER_URL` 切到自托管或商业兼容实例。

部署服务器实测 `nominatim.openstreetmap.org` 连接 20 秒超时，因此不能把它作为线上默认源；
`photon.komoot.io` 和 `geocoding-api.open-meteo.com` 均可达。外部源选择必须从实际部署网络探测，
不能只依赖本机或单元测试。
