# 携程酒店列表页 keyword 参数不生效，叠加持久 profile 导致错城市

> 记录：2026-07-06（用户报告：查成都酒店，来源却是携程上海酒店页）

## 现象

用户查「成都市中心的酒店」，抓到的携程来源却是**上海**酒店预订页，
生成环节 LLM 发现资料错配，拒绝引用。

## 原因（两个因素叠加）

1. `https://hotels.ctrip.com/hotels/listPage?keyword=成都` 里的 **keyword 参数
   根本不生效**——列表页展示哪个城市由携程自己的站内状态（cookie/localStorage
   记忆的上次城市）决定。
2. Phase 5 为保留登录态把 headless Chrome 改成了**持久 profile**，此前冒烟测试
   查过上海外滩酒店，profile 里记住的城市就是上海 → 之后所有 keyword URL
   全部打开上海页。
3. 相关性校验当时只要求「含旅行关键词」，上海酒店页满打满算全是酒店词 → 放行。

## 解决办法

1. **改用数字城市 ID**：`hotels.ctrip.com/hotels/listPage?city={id}` 实测可靠切城市。
   14 个主要城市 ID 已逐一线上验证（`site_router.CTRIP_CITY_IDS`：北京1 上海2
   重庆4 青岛7 西安10 南京12 杭州17 厦门25 成都28 深圳30 广州32 昆明34 三亚43
   香港58）。目的地不在表内 → 不路由，回退公开搜索，绝不开错城市页。
2. **站点直抓来源改用严格校验**（`_dest_in_page`）：标题/正文必须出现目的地城市名
   （含「市」后缀归一化），泛旅行关键词不再放行——即使 URL 层再出问题也有兜底。

## 经验

- 站点 URL 参数**必须实测**，不能想当然；参数无效时页面会"看起来正常"地展示
  错误内容，比报错更危险。
- 引入持久 profile（登录态）的同时引入了"站内状态记忆"这类副作用，
  凡是依赖 URL 定位内容的地方都要重新审视。
- 站点直抓的相关性校验要比搜索结果更严格：搜索引擎有 query 兜底，直抓没有。
