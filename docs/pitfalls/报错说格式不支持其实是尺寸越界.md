# 报错说「格式不支持」，其实是尺寸越界

## 现象

用户上传行程长截图后，助手无视图片、反问「目的地是哪里？」。日志里每一次都有：

```
openai.BadRequestError: Error code: 400 -
  '.messages[1].image[0]: You have uploaded an unsupported image.
   Please make sure your image is valid and has one of the following formats:
   webp, png, jpeg, and gif.'
```

而那张图是 `image/png`——**格式白名单里第二个就是它**。

## 原因

真正越界的是**尺寸**：DeepSeek 视觉端单边上限 8192px，那张图是 1800×25242。
报文里关于格式的那句话与实际原因**毫无关系**。

逐档实测（同一张图裁切）：

| 尺寸 | 字节 | 结果 |
| --- | --- | --- |
| 1800×8192 | 941KB | OK |
| 1800×8500 | 988KB | FAIL |
| 1024×14360 | 1207KB | FAIL |
| 1800×6000 | 689KB | OK |

## 教训

**别拿报文当诊断，拿它当线索。** 照着 "unsupported format" 去查会一路走错：
去核对 magic byte、去查 mime 探测、去怀疑上传链路——全都没问题，因为格式本来就是对的。

真正管用的是**做对照实验**，让被测系统自己划出边界。这里只花了两轮探测（先粗定
6000 过 / 9000 挂，再二分到 8192 过 / 8500 挂），三个假设一次排掉：

- 字节数？941KB 过、988KB 挂，而 1046KB 与 1207KB 同样挂——**三档交错，字节不是判据**。
- 宽高比？1024×14360 比例更极端，照样只挂在高度上——**压宽度没用**。
- 格式？白名单里就有 png——**从一开始就不成立**。

一般化：**当报文给出的原因与你手上的事实矛盾时，相信事实。** 报文是服务端写死的一句
兜底文案，它未必知道自己为什么拒绝。

## 附带的第二个坑：静默失败被读成「智能体很笨」

这个 400 被 `logger.warning` 吞掉、返回空串，链路照常往下走。用户看到的是：
先播一句「正在看你发的 1 张图…」，然后被问「你要去哪」。

**用户给出的诊断是「这个智能体逻辑太死板」——一次硬失败，被完整地误读成了设计问题。**

凡是「读取外部内容失败后继续跑」的地方，都要检查：前面有没有播过一条声称做了这件事的
进度？有的话，失败就必须同样可见，否则用户只能用「它很蠢」来解释。
