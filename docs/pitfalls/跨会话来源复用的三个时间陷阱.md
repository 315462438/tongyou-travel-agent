# 跨会话来源复用的三个时间陷阱（2026-07-31）

做「同目的地近期会话的小红书正文直接复用」时，三个都跟**时间**有关的坑，前两个是
实现期实测抓到的，第三个是设计期靠实证避开的。

## 1. 库里的 naive 时间戳是**本地时间**，不是 UTC

`_now()` 返回 `datetime.now(timezone.utc)`（aware），但列是 `timestamp without time zone`
——psycopg 写入时先转成**会话时区（服务器本地 CST）**再抹掉 tzinfo。所以读出来的 naive
值是本地时间。

实测（服务器上）：

```
DB updated_at : 2026-07-31 14:00:29 (tzinfo=None)
UTC now       : 2026-07-31 07:42:51
本地 now      : 2026-07-31 15:42:51
```

原来的 `_age_label`/`_age_days` 把 naive 值当 UTC 解读 → **所有时间都显得新 8 小时**。
在「记忆年龄」这种天级展示上无感，但 20 小时的图片有效期窗口会因此放行已经 403 的 URL。

修法：`age_delta()` 统一按「aware 用 UTC now、naive 用本地 now」相减。
**凡是拿 DB 时间做窗口判断的地方都要走它**，别自己写 `datetime.now(timezone.utc) - ts`。

## 2. 会话的 `updated_at` 不等于攻略的抓取时间

`travel_conversation.updated_at` 带 `onupdate=_now`：改标题、折叠历史摘要、继续聊天……
任何后续活动都会把它刷成「刚刚」。用它算来源年龄 → 3 天前抓的图会被当成新鲜的，
复用后满屏 403。

修法：候选筛选用会话的 `updated_at`（便宜、够用），**年龄一律看攻略消息自己的
`created_at`**。这是「用于排序的时间」和「用于判定有效性的时间」必须分开的典型例子。

## 3. 不同来源的时效性差三个数量级，不能整包复用

实测（同一批 URL，服务器直连）：

| 来源 | 年龄 | 结果 |
| --- | --- | --- |
| 小红书图片 | 20 小时 | 200 |
| 小红书图片 | 39 小时 | **403** |
| 小红书图片 | 4 天 | **403** |
| 高德 POI 图 | **24 天** | 200 |

小红书图片 URL 路径里带 `202607311401` 这样的时间戳段，有效期就是 **24 小时**；
高德图不过期。据此分类：

- **小红书正文**（玩法/店名/避坑）：半衰期以周计 → 复用，窗口 7 天。**这是最贵的一步**
  （详情逐篇串行 19-20s × 5 ≈ 首轮耗时 85%）；
- **小红书图片**：超 20 小时清空 `images`（留 4 小时余量），宁可没图也不要破图；
- **高德天气**：逐日预报，几天就废 → **必须重取**（秒级零成本，照常跑）；
- **携程酒店**：价格/房态实时 → **绝不复用**。

## 附：两个非时间但同样重要的约束

- **沿途中转轮不复用**：`waypoint_trip` 的语料是「A到B沿途」，与终点城市攻略不是一回事
  （同一个坑在 `is_revision` 那里已经踩过一次）。
- **复用后必应不许 skip，最多降到 light**：复用的资料是**上次那个问法**抓的，本轮角度
  可能不同（上次问美食这次问亲子）。多花 ~30s 做一次轻量搜索覆盖新角度，相对省下的
  3.5 分钟仍是大赚。
