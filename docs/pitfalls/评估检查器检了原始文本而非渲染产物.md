# 踩坑：评估检查器检的是原始文本，不是用户真正看到的渲染产物

**发现时间**：2026-08-04（三层验证接入后首次真实跑基线）
**涉及文件**：`backend/evals/checks.py`、`frontend/src/interaction.ts`

## 现象

评估集刚接上三层验证，第一次跑基线就 **0/3 全红**，三条攻略全部只栽在同一个码：

```
single_city_basic     ✗ 质量层未通过：qual_排版完整性   raw_bold_marker 5 处
single_city_budget    ✗ 质量层未通过：qual_排版完整性   raw_bold_marker 3 处
multi_city_domestic   ✗ 质量层未通过：qual_排版完整性   raw_bold_marker 7 处
```

把真实正文拉下来看，命中的是这种：

```
；**巴公房子**：复古红砖公寓…
均为**参考价（非实时）**，动车时刻…
```

**全是配对完好的加粗**，用户界面上显示完全正常。

## 原因

`check_raw_bold` 守的是 2026-07-30 那个真 bug：GFM 的 left/right-flanking 规则下，
`**` 紧邻中文标点时强调不成立，星号会原样显示。它的实现是直接对**数据库里的原始
markdown** 匹配 `[，。、；：！？）】」]\*\*[^\s*]`。

但那个 bug 当时就已经在**前端**修掉了——`interaction.ts` 的 `prepareMarkdown()`
往 `**…**` 里塞零宽空格，让 `**` 重新满足 flanking 规则：

```ts
markdown.replace(/\*\*([^*\n]+?)\*\*/g, '**​$1​**')
```

而且三个渲染入口（`Home.tsx:2600`、`Trips.tsx:648`、`Trips.tsx:1342`）**全部**走了它。

于是：**用户看到的是正常加粗，checker 却在骂它。** 检查器检的是原始存储，
真正的产物是"经 prepareMarkdown 渲染后的结果"——**检错了 artifact**。

最能说明问题的是：`frontend/tests/interaction-utils.test.mjs` 断言
`，**烤匠麻辣烤鱼（春熙路店）**` **会被修好**，而 `tests/test_evals_checks.py` 拿
**同一个字符串**断言它**是硬伤**。两个测试套件对同一个串给出相反结论，各自都绿。

## 解决

让检查器面向渲染后的产物判定。注意有个陷阱：

> **不能"套一遍 prepareMarkdown 再用老正则"**——U+200B 不属于 Python 的 `\s`，
> `；**​` 照样命中 `[，。、；：！？）】」]\*\*[^\s*]`，等于没修。

改成"把前端能修好的形态剔除，剩下的才算硬伤"：

```python
_PAIRED_BOLD = re.compile(r"\*\*[^*\n]+?\*\*")   # 单行内配对 = prepareMarkdown 能修

residue = _PAIRED_BOLD.sub("", guide)
hits = re.findall(r"\*\*", residue)
```

剩下的正是前端**修不掉**的两种，也就是 07-30 那个真 bug 的原始形态：

- **未闭合**的 `**`（`**人均（含` ——截断留下的半个加粗）
- **跨行**的 `**`（`prepareMarkdown` 的 `[^*\n]` 匹配不到）

修完对同样三条真实攻略重跑 `check_raw_bold`：全部 clean。

## 教训

1. **检查器必须检"用户看到的东西"。** 产物在存储与展示之间还有一层变换时，
   对存储层做规则检查就是在检一个中间态。落到本项目：后端 evals 判排版类问题前，
   必须先想清楚前端 `prepareMarkdown` / `_embed_images` 会把它变成什么样。
2. **前后端各自绿灯不代表一致。** 同一个字符串在两个测试套件里被断言成相反结论，
   而且两边都通过——这种矛盾只有把两个套件放在一起看才发现。新增跨层规则时，
   拿对方套件里的样本当自己的样本，是最便宜的一致性检查。
3. **全红的闸门等于没有闸门。** 0/3 且红得没道理，只会训练人无视它。评估集第一次
   跑出大面积失败时，先怀疑检查器，再怀疑产品。
