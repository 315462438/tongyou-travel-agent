# 测试红了，但原因不是你以为的那个

2026-08-25 收拾一批爆红时，三条红各有各的成因，**没有一条是「代码写错了」**。
逐条改绿很容易，但每一条改错方向都会留下更糟的东西。

## 一、断言从写下那天起就没绿过

`visual-regressions.test.mjs` 断言 `.trip-cost-inputs { … grid-template-columns }`，
而 CSS 里真实类名是 `.trip-cost-money`。查 `git log -S'trip-cost-inputs' -- frontend/src/index.css`
——**这个字符串在本仓库 45 个 commit 的历史里从未出现过**。

也就是说这条断言**引入时就是红的**，作者大概是先按设想的类名写了测试、实现时改了名字、
没跑测试就提交了。它在仓库里红了整整一天没人发现。

**教训**：`git log -S` 查一次比盯着断言猜快得多。一条「看起来应该绿」的断言红了，
先问它**曾经绿过吗**——如果从来没有，那就不是回归，是测试本身写错了，改测试才是对的。

## 二、改绿的方式会把护栏改废

另外两条是真·改名带来的：`COST_CURRENCIES` → `DEFAULT_COST_CURRENCIES`，
`convertedTicketPrice(a, b)` → `convertedTicketPrice(a, b, currencies)`。

顺手把断言照抄成新签名就能绿，但那样**下次再加一个参数又会假红一次**。这类断言该钉的是
**意图**不是**字面**：

```js
// 不好：写死实参列表，加参数就假红
assert.match(trips, /convertedTicketPrice\(ticket, ticketCurrency\)/)
// 好：钉「换算函数确实被用在存盘的 ticket_price 上」
assert.match(trips, /ticket_price: hasTicketCost \? convertedTicketPrice\(/)
assert.match(trips, /Math\.round\(amount \* rate\)/)
```

判据：**这条断言红的时候，是功能坏了，还是只是名字变了？** 只有前者才值得红。

## 三、本机环境把安全防线触发了

`test_context_security` / `test_research_context` 6 条红，报的是
「该地址不可访问（该域名解析到内网/保留地址）」。查解析：

```
本机   example.com → 198.18.0.180     ← RFC 2544 保留段
服务器 example.com → 104.20.23.154
```

`198.18.0.0/15` 是 VPN/代理的 **fake-IP 模式**分配的假地址。Phase 69 的
`ensure_safe_url` 会解析 DNS 后复验网段（防域名解析到内网），于是**正确地**拒绝了它。

**代码没问题，防线也没问题——是本机 DNS 不正常。** 服务器上同样两个文件 24/24 全过。

**教训**：凡是测试里出现真实域名（`example.com` 也算），它就隐含依赖 DNS。
在这类失败上动代码之前，先在另一台机器上跑一遍——**换个环境复现不了的，就不是代码的问题**。
（也别顺手把 `ensure_safe_url` 放宽来让测试变绿：那是拿生产的安全防线去迁就本地的网络配置。）

## 汇总

| 红 | 真实原因 | 正确做法 |
| --- | --- | --- |
| `.trip-cost-inputs` | 断言引入时就错，从未绿过 | 改断言，对上真实类名 |
| `COST_CURRENCIES` 等 2 条 | 真改名 | 改断言，且改成钉意图不钉签名 |
| 安全防线 6 条 | 本机 VPN 的 fake-IP DNS | **什么都不改**，换机器验证 |
