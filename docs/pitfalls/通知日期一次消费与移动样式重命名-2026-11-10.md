# 通知日期一次消费与移动样式重命名

## 现象与原因

- 通知原本已有 `meta.day`、`poll_id`，但客户端只取行程 ID，所以进入后默认第一天。Web overlay 的 `initialBoardId` 只初始化一次，已经打开行程时再收另一条通知不会换板。
- 只把 day 作为初始状态仍不够：异步加载前天数为 1，可能提前清掉第 2 天；若在每次轮询后重新设置日期，又会覆盖用户刚选的日期。旧通知也可能引用已修改或删除的投票。
- 旧 `AndroidTripWorkspace` 实际也供手机网页使用。重命名其 CSS 为 `mobile-trip-days` 时，撞上现有列表卡片的天数徽章：绝对定位和固定尺寸把日期条压到拖动手柄下面。浏览器真实点击发现了遮挡，TypeScript 编译不会发现。
- 旧浏览器脚本只改 Android UA，并依赖原生桥强制移动布局；去掉桥后，横屏测试还需要模拟触摸指针，才与真实手机一致。非地图测试若加载线上地图 SDK，还可能被瓦片网络异常打断。

## 解决

- 三端传完整目标并在详情加载后校验。当前投票的日期优先（null 表示整趟行程），无效日期回退当前有效日期或第 1 天；删除目标时仍打开行程。
- Web 使用请求序号，iOS 使用独立请求 UUID；Android 每次通知创建带参数的详情导航条目。详情只消费一次，滚动也只消费一次。Web 换行程重建详情，投票通知关闭已有群聊，普通群聊通知仍照常展开。
- 共用组件命名为 `MobileTripWorkspace`，其样式统一用独立的 `compact-trip-*` 前缀，保留原列表 `mobile-trip-days`。删除 native-android 专属规则，保留浏览器主题和 Android 浏览器模糊半径降级。
- 浏览器用例使用真实触摸媒体条件、假业务 API；非地图专项拦截地图 SDK。地图专项继续验证标记、定位、空坐标、失败回退及横屏。
- 清理分享逻辑时顺带将既有 MessageBubble 的分享状态 Hook 移到 early return 之前，消除条件调用 Hook 的 lint 错误。

## 回归

`frontend/tests/trip-notification-browser.mjs` 覆盖手机/桌面、跨行程、重复已读通知、整趟投票、删除目标、旧通知及群聊切换；`trip-route-browser.mjs` 验证日期按钮真实可点击。Android 与 Swift 的独立逻辑测试验证日期修正和非法值。
