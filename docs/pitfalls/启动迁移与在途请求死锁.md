# 启动迁移把用户那一轮拖进死锁

> 2026-08-14　线上连炸三次（16:19 / 16:22 / 17:30）

## 现象

用户侧：思考工作台**停在第 1 步「理解需求」不动**，计时一直走，进度条不满。
快答（初步判断）已经出来了，完整版永远不来。停止按钮点了也没用。

服务端：那一轮的后台任务其实**早就死了**，前端只是在等 `turn_stale_min`(30 分钟) 的兜底。

## 根因

```
ERROR:  deadlock detected
DETAIL: Process A waits for AccessShareLock on travel_conversation; blocked by B.
        Process B waits for AccessExclusiveLock on travel_user; blocked by A.
        Process A: SELECT ... FROM travel_conversation WHERE id = $1
        Process B: ALTER TABLE travel_user ADD COLUMN IF NOT EXISTS memory_consolidated_at TIMESTAMP
```

关键认知：

> **`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 即使列早就存在，也要拿 AccessExclusiveLock。**

`IF NOT EXISTS` 只是让它不报错，**不是让它不加锁**——它必须先拿到锁才能判断列在不在。

而 `migrate_and_bootstrap` 每次启动都把 **40+ 条这样的 ALTER 放在同一个事务里**跑一遍。
于是每次部署重启，只要有人正在跑一轮攻略，就是一场锁的赛跑：

- 迁移事务：已经锁住 `travel_conversation`（前面几条 ALTER），正等 `travel_user`
- 用户那一轮：已经在读 `travel_user`（记忆/鉴权），正等 `travel_conversation`

PG 检测到环，杀掉其中一个。**被杀的往往是用户那一轮**——它跑了几分钟、烧了 LLM 调用，
纯损失；而迁移只要下次启动重来就行。

## 修法

### 1. schema 已是最新时，一条 DDL 都不发

`pending_schema_changes(engine)` 比对 `Base.metadata` 与 `information_schema`：
表/列判据**从模型推导**（migrate.py 里每条 ADD COLUMN 之所以存在，就是因为模型上有那一列，
不维护平行清单）；手写索引另用 `_EXPECTED_INDEXES` 登记。

返回空就直接跳过整个 DDL 事务。**绝大多数重启走这条路**，也就根本不存在抢锁。

登记表有测试钉住（`test_every_handwritten_index_is_registered` 扫 migrate.py 源码里所有
`CREATE INDEX IF NOT EXISTS` 与登记表双向核对）——漏登记的后果很隐蔽：schema 被判成
「已最新」→ 整块 DDL 跳过 → 那个索引**永远建不上，且无任何报错**。

### 2. 真要跑 DDL 时设 `lock_timeout`

```sql
SET LOCAL lock_timeout = '5s'
```

**迁移必须是让路的一方。** 抢不到锁就放弃这一轮迁移，下次启动重来；
绝不能让它把用户那一轮拖进死锁。

## 一般化

- **`IF NOT EXISTS` 不等于「无副作用」**：它省的是报错，不是锁。判断「要不要执行」
  必须在发语句**之前**做，不能指望语句自己是幂等的。
- **每次启动无条件重放全部历史迁移**这个模式，在没有在线流量时很省事，
  一旦有长事务的后台任务就会变成定时炸弹。
- 相关：`docs/pitfalls/create_all只建表不加列.md`（为什么这些 ALTER 一开始就存在）

## 顺带暴露的第二个问题（未修）

后台任务因异常死掉时，**没有留下任何终稿消息**，前端只能靠 30 分钟的
`turn_stale_min` 兜底。`repair_interrupted_conversations` 只修「流式占位残留」，
这次连占位都没建起来（快答之后就死了），所以它兜不住。

值得补：启动时把「最后一条 user 消息之后既无流式占位、也无终稿 assistant，
且已超过 N 分钟」的轮次收尾成一条说明消息。
