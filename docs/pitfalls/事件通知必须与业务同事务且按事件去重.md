# 事件通知必须与业务同事务且按事件去重

日期：2026-08-11（Phase 84）

## 现象

社交提醒如果简单地在每次点击后 `insert + commit`，很快会出现三类问题：

- 好友关系或反馈写入失败，通知却已发送，形成“幽灵通知”；
- 用户把“有用”切换成“属实”时产生两条提醒，未读数被重复放大；
- 用户取消反馈或作者删除接力后，通知仍然指向不存在的内容。

## 原因

通知不是独立广播，而是原业务状态的一个可读投影。若它自行提交事务，或者只按通知 UUID 去重，
就无法与好友关系、接力反馈的最终状态保持一致。

## 解决办法

1. 通知 helper 只 `flush`，由好友/反馈的原 API 在同一个数据库事务中统一 `commit`；
2. 用稳定事件键去重，而不是随机通知 ID：好友申请按规范化用户对，接力反馈按
   `post_id + actor_id`；
3. 反馈类型切换时更新原通知并把 `read_at` 清空，表示出现了新的状态；
4. 再点同一反馈、删除接力、撤回好友申请时同步删除对应通知；
5. 读取和已读接口始终附加当前 `user_id` 校验，越权统一返回 404；
6. 自动化覆盖“新增 → 切换 → 取消”完整状态机，不能只测首次插入。

## 结论

事件通知应被设计成“带稳定业务键的持久化投影”。同事务、可撤销、可去重比先做实时推送更重要；
轮询频率可以后续优化，但错误通知一旦展示给用户会直接损害信任。
