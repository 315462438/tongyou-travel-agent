# 别靠文案认出自己发过的消息

## 现象

用户上传行程长截图连问两轮，两轮拿到**同一个反问**「请问您这次行程的目的地是哪里？」。
Phase 68 明明有追问熔断（`clarify_max_rounds=2`，两轮后强制代选），它一次都没触发。

## 原因

熔断靠 `_recent_clarify_rounds` 数「最近连续几轮是追问」，而判据是：

```python
def _is_clarify_text(text):
    t = (text or "").strip()
    return 0 < len(t) <= 60 and t.endswith(("？", "?"))
```

线上那句实际是：

> 请问您这次行程的目的地是哪里？方便告诉我具体城市或景点吗？**我好帮您推荐周边美食和检查路线。**

模型在问句后面顺手接了一句说明——**句尾变成「。」，长度也过了 60**。判据返回 False，
计数恒为 0。用户问 10 次也永远是「第 0 轮」。

同一个判据还管着 `_is_clarify_continuation`（「10天」这类短回答要延续 guide 流水线），
所以一起失灵。

## 关键点

**这条消息是我们自己发的。** 发的时候我们百分之百知道它是一次澄清——却在下一轮
回过头去**猜自己的文案**。中间隔着一个自由发挥的语言模型，措辞随时会漂。

判据换成事实：发的时候写 `meta={"clarify": True}`，读的时候读它。
文案启发式降级为**只认改造之前的老消息**。

## 一般化

凡是「系统读回自己写过的东西」，判据都必须是**当时记下的结构化标记**，不能是产物的形状：

- 反问 → `meta.clarify`，不是「问号结尾」
- 占位 → `meta.streaming`，不是「内容为空」
- 面板 → `meta.poster` / `meta.budget`，不是「以某个标题开头」

本仓库同类：Phase 14 用「看最后一条消息」判本轮是否结束、Phase 108 用
`updated_at` 兼表「最后更改」和「最后注入」——**都是拿一个会因为别的原因而改变的
东西当判据**。

## 失效方式最坏的一点

它**不报错**。熔断代码一直在，测试也一直绿（因为单测直接喂「想去哪里呢？」这种
教科书式的短问句，正好落在启发式命中的那一侧）。只有真实模型的真实措辞会让它失效，
而线上没有任何日志会说「我本来该熔断但没数出来」。

补的回归测试**直接用线上那句原文**做输入，而不是再造一句「像追问的话」。
另有一条 AST 护栏扫 `parse_request` 里每一处「发完消息就 return clarify」的分支，
要求 `_add_message` 都带上标记——**判据写对了没用，得有人写**。
变异检验：把任一处的 `meta` 去掉，该护栏立刻红。
