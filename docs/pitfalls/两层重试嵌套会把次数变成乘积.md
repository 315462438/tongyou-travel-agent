# 两层重试嵌套会把次数变成乘积

**日期**：2026-08-21（Phase 103 落地当天，被单测抓到，没上线）

## 现象

给 `LLMClient.stream_generate_with_reasoning` 加重试时，单测
`test_stream_gives_up_after_max_retries` 报：

```
IndexError: pop from empty list
```

脚本里准备了 10 个连续失败的效果，断言「总请求数 == MAX_RETRIES + 1 == 6」，
结果它把 10 个全消费完了还不够。日志一看就明白：

```
llm.stream.open failed (1/5) … (5/5)      ← 内层重试 5 次
llm.stream failed before first token (1/5) ← 外层这才算「第 1 次失败」
llm.stream.open failed (1/5) … (4/5)      ← 内层又来一遍
```

## 原因

流式生成有个额外约束——**只在还没吐出任何内容时才能重试**（已 yield 过 delta 的话，
调用方 `_stream_into` 已经把它累进 `content_parts` 并周期落库了，重开一条流会让用户看到
重复正文）。所以它不能直接套通用的 `call_with_retry`，得自己写一个带 `produced` 标志的
重试循环。

写的时候顺手把里面开流那一步**也**包了 `call_with_retry`——想的是「开流失败也该重试」。
但外层循环本来就会接住开流失败（那时 `produced` 还是 False）。于是变成：

```
内层 5 次 × 外层 5 次 = 最坏 36 次请求
```

503 风暴下这不是「多试几次」，是**把 provider 打爆**，而且退避总时长也从分钟级涨到十几分钟。

## 解决办法

内层去掉，开流直接裸调，让外层唯一的循环兜住：

```python
# ⚠️ 这里**不能**再套 `call_with_retry`：本函数自己就是重试循环，套上去就是双层嵌套
# （内层 5 次 × 外层 5 次 = 36 次请求），503 风暴下会把 provider 打爆。
stream = self._client.chat.completions.create(..., stream=True)
```

## 一般化

**重试是会相乘的，而每一层单独看都是「合理的 5 次」。** 危险在于两层往往由不同的关注点
引入——一层是「通用传输重试」，一层是「这个场景的特殊约束」——写第二层时很容易忘了
第一层还在。

排查线索：日志里出现两种不同 `what` 标签的重试交替刷屏，就是嵌套的指纹。

防线：**断言总请求数，而不是断言「最后抛了异常」。** 这个 bug 之所以当场就被抓到，是因为
用例写的是 `assert fake.calls == MAX_RETRIES + 1`；如果只写 `pytest.raises(...)`，
36 次和 6 次的表现完全一样，会一路带上线。

同理适用于：LangGraph 的 `arun_with_retry` 套在内部自带重试的节点上（Phase 59 那次
「collect 节点被重试 3 次，每次再等 2-5 分钟」就是这个形状的另一个实例），
以及 httpx transport retries 套在业务重试外面。
