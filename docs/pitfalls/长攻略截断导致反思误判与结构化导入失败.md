# 长攻略截断导致反思误判与结构化导入失败

日期：2026-07-23

## 现象

18 天跨省攻略线上实测出现：

- 初稿已经有预算和 Day 18，自检仍提示「缺少分项预算」「只写到 Day 13」，连续触发重写。
- 点击「导入协同行程」后长时间停在「AI 起草中」，固定显示 Day 1、Day 2 且均为 0 个地点。
- 服务器日志最终记录：

```text
ValueError: LLM 结构化输出解析失败（重试后仍不合法）
Invalid JSON: EOF while parsing a string at line 435 column 45
```

## 原因

### 反思误判

质检节点只读取 `guide[:6000]`。长攻略的后半程和预算通常位于截断点后，模型看到的是不完整攻略，
却被要求判断完整性，因此把「输入没给我」误判成「攻略没有写」。

### 导入失败

导入把最多 24000 字符的攻略一次性抽取为一个 `TripDraft`。该对象同时包含全部地点、住宿、
逐日性质、酒店候选和预算，18 天时 JSON 输出超过 8000 tokens，在字符串中途被模型截断。
旧重试逻辑又把巨大的半截 JSON 放回上下文要求整份重写，第二次仍容易超限。

### 隐性天数限制

协同行程多处使用 `min(15, days)`，且抽取提示词硬编码 Day 1–15。即使 JSON 成功，Day 16–18
仍会被落库层截掉。

## 解决办法

- 质检输入改为短文全文，或长文的「开头 + 全部 Day 标题索引 + 结尾」，并附代码提取的 Day/预算事实。
- 导入拆成两个层次：
  - 全局小对象：标题、目的地、天数、酒店候选、预算。
  - 每个 Day 一个小对象：地点、住宿、逐日性质；使用快模型有限并发后合并。
- 切 Day 时必须识别最后一天之后的全局章节。真实攻略的 Day 18 后还包含美食、住宿、预算、
  避坑和来源；若把它们留在最后一个逐日块，模型会把大量餐厅/酒店误抽为 stops，再次触发长度上限。
- 实测三天一块仍可能在 Day 4–6 达到 4000 tokens。不要继续提高单次 token 上限；改为一天一块并限制
  每天最多 8 个地点、note 最多 80 字，才能从数据规模上消除截断条件。
- 统一使用 `MAX_TRIP_DAYS = 30`。
- 检测 `finish_reason=length`；截断内容不再放回重试上下文。
- 创建导入行程时先从 Day 标题预判实际天数，失败状态写入可见提示。
- 大批量地点首轮坐标补全结束后冷却 2 秒，只对仍缺坐标的名称再查一次，消化共享高德 key 的瞬时 QPS 限流。
- 多城市攻略不能用 `destination="西安至丽江"` 作为所有 POI 的城市过滤条件。按 day_plan 的
  `overnight_city` 分组查询；返程/火车过夜日没有城市时，沿用最近一个有效城市。

## 环境注意

后端 `Settings` 从 `backend/.env` 读取必填 `database_url`。从仓库根目录直接运行
`backend/.venv/bin/python -m pytest backend/tests/...` 时，当前目录没有 `.env`，测试会在收集阶段失败。
应进入 `backend/` 后运行：

```bash
cd backend
.venv/bin/python -m pytest tests/ -q
```
