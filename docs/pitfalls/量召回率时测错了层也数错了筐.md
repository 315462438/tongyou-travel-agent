# 量召回率时，测错了层、也数错了筐

Phase 108 判定「关掉思考链会不会让抽取漏信息」时，第一版探针得出**完全相反**的结论，
并且差点据此否掉一个 10× 的提速。两个缺陷各自独立，凑在一起让假结论看起来很有说服力。

## 缺陷一：测的不是会被改动影响的那一层

改动落在抽取上，于是探针直接调了 `poster._extract_poster_data`。但本体架构（Phase 86）下：

- 海报/预算/导入常规都走 `ensure_trip_object` → 命中缓存就**零 LLM 调用**，纯投影；
- `_extract_poster_data` 的注释白纸黑字写着「回退：直接从正文抽（Phase 13 旧路径）。
  **只在本体层不可用时生效**」。

也就是说探针量的是一条平时几乎不跑的路，它的 prompt、schema、`max_tokens` 都和真正
受影响的 `build_trip_object` 不同。**「哪段代码会因为这次改动而行为不同」和「哪段代码
看起来在做同一件事」不是一回事**，缓存/投影架构里尤其如此。

## 缺陷二：只数了一个筐

`PosterData` 有 `stops` / `foods` / `lodgings` / `specialties` 四个列表，探针只比了 `stops`。
于是得到「off 漏了 佩姐老火锅、鹤鸣茶社、陈锦茶铺、宫廷糕点铺……」——

全是**餐馆茶馆**。它们没丢，只是被归进了 `foods`。

**分类行为的差异被读成了数据丢失，而这两个结论的方向正好相反。** 更糟的是这个假象很
"自洽"：漏的条目看起来确实像「模型没仔细看」，符合「关掉思考就会变糙」的预期，
所以不容易起疑。

## 修正后

同时改掉两点（测 `build_trip_object`、把四类实体并成一个集合再比）后：

| 档位 | 中位耗时 | 实体数(均) | 召回率 | 稳定核心 |
| --- | --- | --- | --- | --- |
| none | 130.3s | 46.0 | 51.1% | 37 |
| low | 82.8s | 44.0 | 48.9% | 32 |
| off | **12.0s** | **58.0** | **64.4%** | **41** |

**off 抽得更多，不是更少**——思考链关掉后整个 token 预算都留给正文，而基线会被自己的
思考链挤爆输出（同一探针里 none 三轮有两轮 `8000 上限 JSON 截断`）。

## 后续约束

1. **先确认「改动的作用面」再设计探针**：有缓存/投影/回退的系统里，
   「调用同名功能」不等于「跑到了被改的代码」。写探针前先回答：这次改动让哪一次
   LLM 调用的请求体变了？就测那一次。
2. **比较结构化输出时，先比全集再比分项**。分项差异可能只是归类口径变了；
   只有全集缩小才是真的丢信息。
3. 与之配套的是 `docs/pitfalls/用与基线相同来判定字段未生效会误报默认档.md`：
   同一个 Phase 里，**两次错误结论都出在判据设计上，而不是出在被测系统上**。
   实验设计的错误不会报错，只会给你一个像模像样的数字。
