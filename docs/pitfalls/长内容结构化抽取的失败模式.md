# 长内容结构化抽取的失败模式（2026-07-31，导入协同行程线上事故）

用户实测：同一篇 6 天攻略（大理、丽江）连续两次导入失败，各等约 2 分钟，
账号里留下两条「6 天 0 个地点、未定目的地」的空行程，页面上没有任何可点的恢复入口。

## 根因链（一次失败，五处放大）

服务端日志一句话定位：

```
Day 2–2 分段抽取失败：LLM 结构化输出解析失败（重试后仍不合法）:
结构化输出达到 3000 tokens 上限，已在 JSON 中途截断
```

### A. 分段生效了，但**输出上限**没跟着调

`IMPORT_DAYS_PER_CHUNK = 1` 已经把攻略切到**单天**，可 `max_tokens=3000` 对一天的
「景点 + 备注 + 住宿 + 逐日计划」仍然不够。于是产品对用户说「长行程会自动分段处理」，
分段确实做了，还是失败——**用户看到的是"自动处理无效"，真相是上限设低了**。

教训：分段（输入侧）和 max_tokens（输出侧）是两个独立的量。**切得再细，也只减少输入，
不减少单块的输出需求**；结构化抽取的输出量取决于内容密度，必须单独给足。

### B. `asyncio.gather` 默认快速失败 → 已成功的天陪葬

```python
parsed_chunks = await asyncio.gather(*(extract_chunk(*c) for c in chunks))  # 一个抛出，全盘皆输
```

6 天里 5 天解析成功，只因 Day 2 超限，全部丢弃。
修法：`return_exceptions=True` + 逐块判定，失败的天记进 `draft.failed_days`。

**凡是「N 个独立子任务，部分成功也有价值」的 gather，都必须 `return_exceptions=True`。**

### C. 先建行再解析 → 失败必然留下空壳

端点里 `db.add(trip); db.commit()` 之后才 `background.add_task(_run_import)`。
只要解析失败，库里就躺着一条 0 地点的行程，且没有任何状态区分它和"用户手建的空行程"。

修法：行照建（它要承载进度显示和幂等锚点），但**状态必须显式**：
`seeding` / `partial` / `failed` 三态 + 文案写明失败的是哪几天 + 页面给「继续重试」「删除草稿」。
**不允许存在"看起来正常但其实是失败残骸"的数据。**

### D. 没有幂等键 → 重试变新建

每次 POST 都 `TravelTrip(...)`。用户按提示"重试"，得到的是第二条空行程。
修法：按 `(source_message_id, owner_id)` 查已有行程，存在即复用；
`failed/partial` 状态则原地重跑。**同一份源内容对同一用户永远只有一条导入任务。**

### E. 独立成功的信息被整包丢弃

`destination`/`title` 来自 summary 那一步，它跟逐天抽取**完全独立且已经成功**
（库里验证：确实拿到了「大理、丽江」），却因为整体 except 而没有落盘 →
板上显示"未定目的地"。修法：能落的先落，失败只影响它自己那部分。

## 修复后实测（同一篇攻略，同一条失败行程）

| | 修复前 | 修复后 |
| --- | --- | --- |
| 状态 | `failed` | `None`（正常行程） |
| 目的地 | 空 → 显示"未定目的地" | `大理、丽江` |
| 地点数 | 0 | **31** |
| 重复点击导入 | 每次新建一条空行程 | 返回同一条 `{reused: true}` |

## 附带修掉的同类问题

**停止检查点第三次缺失**：`parse_request` 的 `llm.parse` 是同步阻塞调用且没有取消点，
用户在解析阶段点停止要干等 27 秒。这与本周修过的 budget/poster 是同一模式
（见 `停止链路asyncio线程池join与记忆污染.md`）。
**结论：凡是「阻塞的 LLM 调用」都要在调用前后 `cancel.check`，长调用还要 `wait_cancellable`。**
