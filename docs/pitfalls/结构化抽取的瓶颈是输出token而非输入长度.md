# 结构化抽取的瓶颈是**输出 token**，不是输入长度；拆路要按消费者拆

2026-08-13，Phase 86 本体化上线当天连踩两个，都靠线上实测才暴露。

## 现象

用户点「🎨 生成手账海报」，卡在「手账生成中…」约两分钟。`travel_guide_object` 表长时间为空，
日志里没有任何 error。

## 坑一：把三个消费者合并成一个大 schema 一次抽

本体化的初衷是「一份攻略只解析一次」，于是把 `PosterData` + `BudgetData` +
`TripImportDays` 合并成一个 `TripFullExtraction` 一次抽完。判断要不要分块用的是
**输入字符数**（`ontology_extract_max_chars = 24000`），6638 字的 3 天攻略算「短」，
走单次抽取。

结果：

```
ValueError: LLM 结构化输出解析失败（重试后仍不合法）:
            结构化输出达到 8000 tokens 上限，已在 JSON 中途截断
```

**真正的硬约束是输出 token 数**，不是输入长度。合并 schema 的输出是
`stops[] × 10 字段 + expenses[] + lodgings[] + foods[] + specialties[] + tips[] +
reservations[] + day_meta[]`，一份 3 天攻略就顶破 `llm.parse` 的默认 `max_tokens=8000`。
截断后 `llm.parse` 会带提示重试一次——**再截断一次**，于是一次失败要花 ~140s。

雪上加霜：DeepSeek 的 **reasoning tokens 与正文共用同一个 `max_tokens` 预算**。
模型多想几步就截断，所以同一路抽取实测在 **5.6s ~ 229.9s** 之间剧烈波动，
且是否成功完全随机。

> 这不是本体层引入的：同条攻略上，**改造前的 `budget.py` 老路径同样失败**
> （141.7s 后报「预算信息提取失败了，请重试」）。本体化只是把它暴露得更频繁。

### 修法

1. `llm.parse` 的 `max_tokens` 对抽取类调用给足余量（`ontology_lane_max_tokens = 16000`）。
   合法输出通常 <2000 token，余量是留给 reasoning 的。
2. 分块判据从**输入字符数**改为**天数**（`ontology_single_call_max_days`）——天数是
   输出规模的代理，而输入长度不是。

## 坑二：按「概念」拆路，比不拆还慢

修完坑一，把抽取拆成三路并发：画像（profile）/ 花费（cost）/ 逐日地点（days），
以为墙钟 ≈ 最慢的一路。实测：

| | 耗时 |
| --- | --- |
| 旧 `PosterData`（单次） | **37.9s** |
| 新 profile 路 | 11.8s |
| 新 cost 路 | 5.6s（另一次 229.9s） |
| 新 days 路 | 54.5s |
| 新海报路径（profile + days 并发） | **53.8s** ← 比旧的还慢 |

原因：**抽取调用的固定开销很高**（排队 + reasoning + 结构化校验重试），并发并不能把
两次调用压缩成一次的时间。而旧的 `PosterData` 恰好**就是** profile + days 的并集，
一次调用 37.9s 就拿全了。

### 真正的划分原则

> **一路对应一个消费者要的完整数据，不按概念细分。**
> 能一次拿到的绝不拆；要拆就按消费者拆——那样每个人只付自己那份，且付过一次就进缓存。

最终落成两路：

| 路 | 覆盖面 | 谁用 |
| --- | --- | --- |
| `itinerary` | ≈ 旧 `PosterData`（画像 + 逐日地点） | 手账海报、行程导入 |
| `cost` | ≈ 旧 `BudgetData`（开销/预约/人数/口径） | 预算明细、行程导入 |

配合 `ensure_trip_object(..., need=POSTER_LANES)` 按需抽取 + 分路缓存：
点海报只跑 `itinerary`（与改造前同一量级），点预算只补 `cost`，
两个面板都点过之后任何一方再打开都是 **0.0s**。

## 教训

1. **结构化输出的成本按输出算。** 评估一个抽取 schema 贵不贵，数它要吐多少字段 ×
   多少条记录，不要看喂进去多少字。
2. **reasoning 模型的 `max_tokens` 要留余量**，它和正文抢同一个预算；卡线的表现是
   「随机失败 + 耗时剧烈波动」，很容易被误判成网络或并发问题。
3. **「减少重复调用」和「减少墙钟时间」是两个目标，可能互相冲突。** 合并成一次调用
   减少了总调用数，却让唯一那次变得又慢又易失败；按概念拆开增加了并发度，
   却让单个消费者要等两次调用。**按消费者边界拆 + 缓存**才同时满足两者。
4. **单测证明不了性能。** 本次全部 48 个单测用 fake LLM，全绿，但线上第一次点击慢了 3 倍。
   涉及 LLM 延迟的改动，必须在真实环境上计时对比新旧路径。
