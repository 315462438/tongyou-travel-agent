# 函数体内的惰性导入，在真跑到之前是隐形的

## 现象

Phase 109 的独立扫码连接，24 条单测全绿、变异检验做了 9 种、部署核对也过了。
真机第一次点「扫码连接」，直接弹「连接过程出错，请重试」。

日志：

```
connect session failed user=293cbea7…: No module named 'app.tools.chrome_mcp'
  File "app/agent/connect_session.py", line 142, in _drive
    from app.tools.chrome_mcp import ChromeMCP
ModuleNotFoundError: No module named 'app.tools.chrome_mcp'
```

真实路径是 `app.tools.mcp_client`。写的时候没查，照印象拼了一个看起来很合理的名字。

## 为什么测试全绿

两层原因叠在一起：

**① 模块顶层的 import 写错会在 import 期就炸，函数体内的要等真跑到才炸。**
本仓库大量使用函数体内惰性导入（避免循环依赖、加快启动），`_drive` 里的五个
`from app.x import y` 全在函数体内。只要没执行到那一行，写什么都不会报错。

**② 测试恰好绕开了那条路径。** fixture 为了不真拉 Chrome，把 `_run` 整个换成了
假实现：

```python
monkeypatch.setattr(cs, "_run", fake_thread_start)
```

于是 `_drive` 一次都没被执行。测试覆盖的是会话状态机（互斥、取消语义、token 语义），
那些确实都对——**但它们全在 `_drive` 之外**。

讽刺的是这个 mock 本身是对的：单测里不该真拉浏览器。问题不在 mock，
在于**没有任何一条测试触碰那个被 mock 掉的函数体**。

## 解决办法

不执行函数，也能验证它引用的名字存在——**静态解析 + importlib 逐个核实**：

```python
for node in ast.walk(ast.parse(inspect.getsource(cs))):
    if isinstance(node, ast.ImportFrom) and node.module.startswith("app."):
        mod = importlib.import_module(node.module)      # 模块存在吗
        for a in node.names:
            assert hasattr(mod, a.name)                  # 名字存在吗
```

变异检验：把模块路径改错 → 红；把符号名改错 → 也红。

## 后续约束

1. **凡是「为了不碰外部资源而 mock 掉整个函数」的地方，都要问一句：那个函数体里
   还有什么是只有运行时才会暴露的？** 惰性导入是最常见的一种，此外还有
   属性名拼写、`getattr` 的字符串键、SQL 里的列名。
2. 写 `from app.x import y` 之前**查一下真实路径**，别照印象拼。
   `grep -rn "class Foo" app/` 花两秒。
3. 一般化：**测试绿不代表代码跑过。** 要分清「断言通过」和「这条路径被执行过」——
   这次的 24 条断言全部通过，而出事的那 20 行一次都没跑。
