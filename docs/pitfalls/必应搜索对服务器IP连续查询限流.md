# 踩坑：必应搜索对服务器 IP 连续查询限流

> 日期：2026-07-03　|　阶段：Phase 2 搜索引擎抓取

## 现象

Phase 2 里 Agent 拆解出 6 个搜索任务，逐个用必应查询。结果：

- **第一个查询结果正确**（如"重庆美食攻略"→重庆美食 TOP10、本地人红黑榜）
- **第二、三…个查询结果完全跑偏**——返回黄金价格、Windows 安装教程、支付宝、微信、豆包 AI 等和查询毫不相关的内容

## 排查过程（排除了几个错误假设）

| 假设 | 验证 | 结论 |
|---|---|---|
| take_snapshot 抓不全结果 | 改 evaluate_script 直接读 DOM | 排除，DOM 能读到但内容是错的 |
| 必应结果页 SPA 缓存（连续 navigate 抓旧 DOM） | 加 about:blank 中转 | 第一个对，后面仍错 → 排除 |
| 浏览器 bfcache | 改 new_page 每次新标签 | 第一个对，后面仍错 → 排除 |
| 浏览器指纹/会话被识别 | 每个查询用独立 ChromeMCP（全新 chrome 进程） | **第一个对，后面仍错** → 排除 |

关键规律：**无论怎么隔离浏览器，每个测试批次的第一个查询总是正确，后续都是垃圾。**
→ 与浏览器状态无关，是**必应对服务器公网 IP 的连续查询频率限流**：
短时间内多次查询，第一次正常，后续被降级返回推荐流/随机内容。
（本地开发时不明显，可能因本地 IP 信誉不同或查询间隔较长。）

## 解决办法

既然「第一个查询总是可靠」，就**把查询数降到最少**：

- `_build_queries()` 只生成 1-2 个**综合查询**（覆盖攻略+景点+美食），
  而非 6 个细分查询
- 每个查询用**独立浏览器会话**（全新进程）
- 查询之间**拉开 12s 间隔**，降低触发限流概率
- 单查询 `top_n=6~8`，一次拿够结果
- 抓取阶段用**单会话**（打开普通攻略网页没有这种 IP 限流）

配合两层过滤兜底（`_is_relevant` 相关性 + 垃圾域名 skip 列表），
即使偶有噪声混入也会被挡掉。

## 兜底：攻略质量不依赖来源数量

实测即使来源少或含噪声，DeepSeek 的攻略生成质量依然很高（prompt 要求
「只用资料里真实地点」，模型结合自身知识补全，成都/重庆这类大城市攻略准确地道）。
所以来源主要用于**时效信息和来源引用**，攻略主体质量有保障。

## 后续可选优化（Phase 3+）

- 换官方搜索 API（必应/Google Custom Search，需 key，无 IP 限流）
- 多搜索引擎轮换（DuckDuckGo html 版等）
- 结果缓存（同目的地复用）
