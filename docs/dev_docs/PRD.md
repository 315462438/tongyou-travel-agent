# PRD：个人旅行规划浏览器智能体

## 1. 产品名称

**Travel Browser Agent**

中文名：**个人旅行规划浏览器智能体**

## 2. 产品定位

这是一个面向个人自用的旅行规划平台。

用户只需要在页面中输入旅行需求，例如：

“我 8 月想去东京玩 5 天，预算 8000，喜欢美食和购物，不想太累。”

系统通过 Agent 直接接入 Chrome DevTools MCP，控制真实 Chrome 浏览器去浏览携程、Expedia、小红书、Google Maps 等页面，读取用户可见内容，自动整理酒店、攻略、景点、美食、交通和预算信息，最后生成完整旅行计划。

产品不做自动下单、不做自动支付、不绕过登录、不绕过验证码。遇到登录、验证码、隐私页面、个人信息填写等场景时，系统暂停并提示用户手动处理。

---

## 3. 产品目标

### 3.1 核心目标

让用户不需要自己做复杂攻略，只需要输入想法，系统自动完成信息收集、整理、对比和路线规划。

### 3.2 具体目标

1. 自动搜索目的地攻略。
2. 自动读取酒店页面信息。
3. 自动总结小红书帖子和旅行攻略。
4. 自动对比多个酒店。
5. 自动生成每日行程。
6. 自动估算预算。
7. 自动识别路线是否绕路、是否太累、是否超预算。
8. 支持用户多轮修改，例如“太累了”“酒店便宜一点”“多安排美食”。
9. 遇到登录、验证码、隐私页面时让用户手动接管。

## 4. 用户使用流程

### 4.1 主流程

```text
1. 用户打开本地旅行规划平台页面
2. 用户输入旅行需求
3. Agent 抽取目的地、天数、预算、偏好
4. Agent 拆解搜索任务
5. Agent 通过 Chrome DevTools MCP 控制 Chrome 打开网页
6. Agent 自动搜索酒店、攻略、景点、美食
7. Agent 读取页面可见内容
8. Agent 抽取结构化信息
9. Agent 对比酒店和攻略
10. Agent 生成每日行程
11. 用户查看结果并提出修改意见
12. Agent 重新规划
13. 用户保存最终行程
```

### 4.2 登录/验证码接管流程

```text
1. Agent 打开某个平台页面
2. 页面要求登录或出现验证码
3. Action Guard 判断该动作需要用户接管
4. 系统暂停浏览器自动操作
5. 页面提示：“当前页面需要你手动登录/处理验证码”
6. 用户在 Chrome 中手动完成操作
7. 用户点击“已完成，继续”
8. Agent 继续读取用户可见页面内容
```

## 6. 核心功能

## 6.1 旅行需求输入

用户可以输入自然语言需求。

示例：

```text
我 8 月去东京玩 5 天，预算 8000，喜欢美食、购物和拍照，不想太累，酒店希望靠近地铁。
```

系统需要抽取：

```json
{
  "destination": "东京",
  "days": 5,
  "budget": 8000,
  "pace": "轻松",
  "interests": ["美食", "购物", "拍照"],
  "hotel_preference": ["靠近地铁"]
}
```

---

## 6.2 自动任务拆解

系统根据用户需求自动生成搜索任务。

示例：

```json
[
  {
    "type": "hotel_search",
    "query": "东京 新宿 酒店 8月 价格 评分"
  },
  {
    "type": "guide_search",
    "query": "小红书 东京 5天4晚 攻略"
  },
  {
    "type": "food_search",
    "query": "东京 新宿 涩谷 美食 推荐"
  },
  {
    "type": "transport_search",
    "query": "东京 地铁 交通 攻略"
  }
]
```

---

## 6.3 浏览器自动浏览

系统通过 Chrome DevTools MCP 控制真实 Chrome 浏览器。

浏览器动作包括：

```text
打开 URL
搜索关键词
点击搜索结果
读取页面文本
读取页面标题
读取当前 URL
滚动页面
截图
等待页面加载
检测登录页
检测验证码页
检测支付/订单页
```

---

## 6.4 酒店信息抽取

从携程、Expedia、Booking 等页面中抽取酒店信息。

字段包括：

```json
{
  "source": "expedia",
  "hotel_name": "Tokyo Example Hotel",
  "address": "Shinjuku, Tokyo",
  "price_per_night": 1200,
  "currency": "CNY",
  "rating": 4.6,
  "review_count": 2300,
  "pros": ["靠近地铁", "周边餐饮多", "交通方便"],
  "cons": ["房间偏小", "价格偏高"],
  "nearby": ["新宿站", "歌舞伎町"],
  "suitable_for": ["首次东京旅行", "购物", "交通优先"]
}
```

## 6.5 攻略信息抽取

从小红书、博客、游记中抽取攻略信息。

字段包括：

```json
{
  "source": "xiaohongshu",
  "title": "东京5天4晚攻略",
  "spots": ["新宿", "涩谷", "浅草寺", "银座"],
  "restaurants": ["一兰拉面", "牛かつもと村"],
  "photo_spots": ["涩谷 Sky", "东京塔", "浅草寺雷门"],
  "tips": ["涩谷 Sky 建议提前预约", "新宿站出口复杂"],
  "avoid_pitfalls": ["不要把浅草和涩谷安排在同一个半天"],
  "recommended_route": ["新宿", "涩谷", "原宿", "银座"]
}
```

---

## 6.6 酒店对比

系统支持多个酒店横向对比。

对比维度：

```text
价格
位置
交通便利度
评分
评论数量
差评关键词
是否靠近地铁
是否靠近核心景点
是否适合用户偏好
退改政策
综合推荐分
```

输出示例：

```text
推荐排序：

1. A 酒店
推荐理由：离新宿站近，交通方便，适合首次东京旅行。
风险点：房间偏小。

2. B 酒店
推荐理由：价格较低，适合预算优先。
风险点：距离地铁稍远。

3. C 酒店
推荐理由：环境较好，适合情侣。
风险点：价格偏高。
```

---

## 6.7 行程生成

系统根据酒店位置、景点分布、用户偏好、预算和攻略信息生成每日行程。

生成原则：

```text
同一天安排相近区域
避免来回横跨城市
轻松模式下减少景点数量
热门景点安排在合适时间段
晚上优先安排商圈、美食、夜景
保留休息时间
预算不要明显超标
```

输出示例：

```text
Day 1：抵达 + 新宿周边
上午：抵达东京，前往酒店寄存行李
下午：新宿御苑、新宿站周边
晚上：歌舞伎町、思出横丁晚餐

Day 2：涩谷 + 原宿 + 表参道
上午：涩谷 Sky、忠犬八公
下午：原宿竹下通、表参道
晚上：涩谷周边晚餐和购物

Day 3：浅草 + 上野
上午：浅草寺、雷门
下午：上野公园、阿美横町
晚上：上野或浅草周边用餐
```

---

## 6.8 预算估算

预算维度：

```text
酒店
餐饮
市内交通
景点门票
购物预留
其他预留
```

输出示例：

```text
预算估算：

酒店：约 4800 元
餐饮：约 1500 元
市内交通：约 500 元
景点门票：约 800 元
其他预留：约 500 元

总计：约 8100 元

当前略高于预算 8000 元，建议把酒店预算控制在每晚 1000 元以内。
```

---

## 6.9 多轮修改

用户可以继续输入修改意见。

示例：

```text
太累了，少安排几个景点。
```

系统需要：

```text
减少每日景点数量
增加休息时间
删除跨区域景点
重新生成轻松版路线
```

示例：

```text
酒店预算降一点。
```

系统需要：

```text
重新筛选低价酒店
推荐性价比区域
重新计算总预算
```

## 9. 验收标准

### 9.1 浏览器控制验收

```text
能打开指定网页
能读取页面标题
能读取页面正文
能截图
能滚动页面
能识别登录/验证码场景
能暂停等待用户接管
```

### 9.2 信息抽取验收

```text
能从酒店页面抽取名称、价格、评分、地址
能从攻略页面抽取景点、餐厅、避坑点
能把多个页面保存到同一个旅行计划
能对多个酒店进行对比
```

### 9.3 行程生成验收

```text
能根据目的地和天数生成每日路线
能结合用户偏好调整节奏
能估算预算
能根据用户反馈重新规划
```

### 9.4 安全验收

```text
遇到登录页必须暂停
遇到验证码必须暂停
遇到支付页必须禁止自动操作
遇到订单页必须要求用户确认
不得自动提交任何交易或身份信息
```
