# 记忆系统：行程类信息该放哪（2026-07-31 决策记录）

## 结论

**具体某一次行程不进记忆表。** 记忆只留「下次出行仍然成立」的东西。

| 信息 | 归属 | 理由 |
| --- | --- | --- |
| 口味/节奏/兴趣/预算档位/住宿偏好/出行方式 | `travel_memory`(preference) | 跨行程复用，越积越准 |
| 常驻城市/忌口/同行情况 | `travel_memory`(fact) | 稳定事实 |
| 去过/规划过哪些城市 | `travel_memory`(fact, key=旅行足迹) | 行程信息里**唯一**值得长期留的部分；只留城市名，不带日期/天数/预算 |
| 「最近一次规划的目的地」 | **确定性查询**（`memory.recent_plan_hint`） | 从会话数据直接推导，永远新鲜、不进记忆表 |
| 某次行程的完整结构（逐日/坐标/预算明细） | `travel_trip` 协同行程 | 有结构、有日期、用户可见可编辑可删 |

## 为什么退役 `trip_state`（「当前行程」单槽）

上线数据：8 条 trip_state 里 **5 条 hit_count=0**（从未被注入过），两条活跃的正是当日两个
线上 bug 的污染源——用户问「合肥→武汉沿途有什么古镇」（全程没提时间和预算），
攻略里却写「国庆期间大概率不堵」「都在 5000 元预算内」，全部来自上一次成都行程的记忆。

它的四个结构性问题：

1. **单槽即遗忘**：只保留最新一次，10 月成都被 11 月武汉覆盖——连「行程档案」都算不上。
2. **时点事实伪装成长期偏好**：注入块说「请在规划时考虑」，生成端就把里面的日期/预算/人数
   当成本次约束。为它先后堆了四道防线（过期警告、完整规划请求时过滤、目的地过滤、prompt 纪律）。
3. **防线还有洞**：5 个注入点里 4 个传 `destination=""`（解析/直答/深度研究×2），
   基于目的地的过滤在那 4 处根本不生效。
4. **信息本来就可确定性推导**：「最近规划的目的地」在 `meta.preference.destination` 里躺着，
   却绕道让 LLM 复述成一句自然语言再存——又丢结构又会过期。

它唯一不可替代的用途是**跨会话指代消解**（新对话说「帮我加一天」而不报地名）。
这个用途已由 `recent_plan_hint` 接管，且做得更好。

## `recent_plan_hint` 的设计要点

- 查该用户**其它会话**里最近一条带 `sources` 的 assistant 消息，取 `meta.preference.destination`；
- 超过 `RECENT_PLAN_HINT_DAYS`(14) 不给（陈旧指代比没有更糟）；
- 措辞是**待确认指代**不是事实断言：「仅当用户本轮没有指明目的地、且像是在延续那次行程时，
  才把它当作本轮目的地……它只是指代线索，不代表本次的日期、预算或人数」；
- 只注入 `parse_request`（destination 的产出点）与 `run_direct_answer`（「那边冷不冷」类）；
  **guide 生成端与 deep research 不注入**——那时目的地已定，旧行程零增量、纯污染面。

线上验证：全新对话只说「帮我在原来的行程上再加一天」（无任何地名）→ 直接按武汉开始规划，
不反问；同一账号问沿途推荐 → 不再出现国庆/5000。

## 通用教训

判断一条信息该不该进记忆，问两个问题：

1. **下次出行它还成立吗？** 不成立的（日期、这次的预算、这次住哪）就是时点信息，不该进。
2. **它能从现有数据确定性推导吗？** 能推导的不要让 LLM 复述成自然语言存一份——
   那是拿"会过期的模糊副本"换"永远新鲜的结构化原件"。
