## 二、P0（等了很久，产物却缩水/损坏）

### P0-1 深度推理：流式展示了完整报告，落库只剩 200 字摘要
等待期间流式播出了一份完整报告（核心维度对比表 + 重庆预算明细表 + 西安预算表…），
终稿刷新后只剩：

> 报告已生成。核心结论：西安更划算——…住宿是最容易踩坑的超支项，建议提前两个月订。

刷新页面复核，落库确实只有这段摘要，那份表格报告**被丢弃了**。

根因：`app/agent/deep_research.py` 的 `_extract_answer()` 取"最后一条有文本的 AI 消息"
（注释也写着"最终报告是最后一条 AI 文本消息"）。本轮模型先写完长报告，又追加了一条
"报告已生成。核心结论…"的收尾寒暄，于是终稿取到寒暄、报告被覆盖。

修法（任一）：取**最长**的 AI 文本消息；或按结构化特征（含 `##`/表格）择优；
或 system_prompt 明确禁止在报告后追加总结性收尾消息。

### P0-2 兜底插图把表格从中间劈开（确定性复现）
Day 1 的四行表格只渲染了前两行，后两行变成裸文本：

```
| 傍晚 | 锦城公园：… | 步行约10分钟；停留1-1.5小时 | 免费；共享单车约3元 | | 晚上 | …
```

DOM 顺序证实：`TABLE(3 rows)` → `P(空)` → `IMG` → `P("| 傍晚 | …")`，
即 `_embed_images` 的兜底插图插到了表格行之间，打断了表格块。
多轮改写重新生成后**同样复现**，不是偶发。

修法：兜底插入位置需跳过表格块内部（只在表格整体之前/之后插）。

### P0-3 价格区间被 GFM 单波浪线吃成删除线
深度推理报告里：`¥400~600/晚，中档 ¥600~900/晚` 渲染成
**`¥400600/晚，中档 ¥600900/晚`**。remark-gfm 支持单个 `~` 作删除线，
两个价格区间的 `~` 互相配对，中间文字被吞。价格是决策核心信息，这个 bug 直接误导
（"¥400600" 会被读成 40 万）。

修法：渲染前对"数字 ~ 数字"形态的单 `~` 做转义，或关掉 single-tilde strikethrough。

## 三、P1（等待期的信息质量）

### P1-1 时间黑洞：小红书详情串行抓，且为凑 5 篇抓了 11 篇
xhs-mcp 容器日志（首轮，UTC）：

```
10:31:39 搜索Feeds「成都 旅游攻略 美食 小众景点」
10:31:55 / 10:32:14 / 10:32:36 / 10:32:56 / 10:33:15 / 10:33:37 /
10:34:00 / 10:34:14 / 10:34:33 / 10:34:54 …  ← 每篇 get_feed_detail 19–20s，串行
```

`collect_xhs_sources()` 里 `desc < 100` 的笔记跳过后**继续取下一篇**，
没有尝试次数上限：为拿到 5 篇合格笔记实际抓了 11 篇 ≈ **3.5 分钟**，
其中 6 篇被丢弃 ≈ **2 分钟纯浪费**。这是首轮 4 分钟等待的 ~85%。

修法：搜索结果层面先预筛（标题/摘要/图片数）；给"最多尝试 N 篇"上限；
`xhs_notes_per_turn` 降到 3–4；或先用搜索摘要开写、详情到了再增量补。

### P1-2 「当前动作」卡 3 分 20 秒一动不动，且与足迹自相矛盾
00:23 → 03:43 期间"当前动作"始终是`📕 正在小红书搜索：成都 旅游攻略 美食 小众景点`，
而下方足迹最后一条已经是"正在深入思考中（这一步没有中间进度，属正常）"。
两个控件说法冲突，用户唯一能确认"还活着"的东西是秒表。

小红书这一步其实有天然的进度素材（第 3/5 篇、笔记标题），白白没播。

### P1-3 文案过度承诺
1:32 就显示"快好了，正在把资料整理成完整答案…"，此时距离首字还有 2.5 分钟。
`interaction.ts::waitReassurance` 按 `elapsed < expected` 判"快好了"，
而 `THINKING_EXPECTED_SEC` 本身估低了（智能规划实测 ~5:40 vs 承诺 2 分钟）。
建议先把预期值改成实测 P50，再谈文案。

### P1-4 360 兜底搜索没有相关性校验，广告位当成结果
进度足迹里出现：

> 🔎 搜到 6 条：唧唧Down下载-唧唧Down中文版、分享一个下载bilibili（B站）…
> 🔎 搜到 6 条：哔哩哔哩下载中心、bilibili官网入口（b站网页版…

`browser_tool._search_360()` 直接抓 `h3 a`，只过滤 360 自家服务，
**没有 bing 路径那样的 `_query_matches` 校验**，于是 so.com 的通用下载站推广位
被当成搜索结果返回，agent 还可能真去读（每篇 20–30s）。
Bing 路径的踩坑修复（注释里写着"搜『商丘古城』返回 Doomworld 论坛"）没同步到 360 路径。

### P1-5 agent 试着搜 Google，被 url_guard 拒
`travel-backend` 日志：`拒绝不安全 URL 'https://www.google.com/search?q=…'：该域名解析到内网/保留地址`。
拦截行为正确（该机器上 google 解析到保留地址），但白跑一轮。
建议在 research 的 system_prompt 里明确国内可达的检索入口，别让模型试 Google。

## 四、P2（内容一致性 / 可信度）

- **配图与正文打架**：Day 1「城南绿洲：铁像寺水街→锦城公园→双子塔」下方配了一张
  全宽小红书图，图里画的是**宽窄巷子 / 杜甫草堂 / 人民公园 / 武侯祠**——
  而同篇「避坑提示」明确写"宽窄巷子慎入""杜甫草堂酌情放弃"。图是最抢眼的元素，直接自我打脸。
- **两个预算数并列**：正文预算表「合计约 3210 元（2人）」，
  下方预算明细面板「¥1,075.5 人均 · 合计 ¥2,151」，差 1,059 元。
  明细只抽了正文逐项花费，正文里的汇总项（餐饮 1400、杂项 200 等）没落项。
- **表格里 `**加粗**` 原样显示**：`，**烤匠麻辣烤鱼（春熙路店）**解决午餐`。
  CJK 标点紧邻 `**` 时 CommonMark 强调不成立，中文场景高频。
- **未替换的图片占位符漏进正文**：`[img:小红书灵感·📍成都可以分成3个板块游玩，不绕路✔️·2]`
  （名字里 emoji/`✔️` 变体选择符导致匹配失败）。
- **把内部实现讲给用户**：住宿章节写"因本轮参考资料中不含携程实时酒店列表，无法提供
  具体酒店名称与价格"。用户要的是住哪，不是知道你这轮没抓携程。
- 快答里出现"**春节**人流下体验更累"（问的是国庆）。
- 直答建议"如需实时天气预报，可以让我联网查询"——平台自带高德天气，白搭一轮往返。
