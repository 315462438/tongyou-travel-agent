## 1. Phase 55 — geocode 持久缓存（纯增益）

### 痛点
`geocode_names(names, city)` 在**导入攻略 / 加地点 / AI 起草 / 生成海报**处被反复调用，
同样的地名（宽窄巷子、布达拉宫…）每次都重新打高德 geocode。有并发限流（Semaphore）
但**无跨请求缓存**——重复地名反复请求，慢且吃高德 QPS（之前踩过 QPS 限流的坑）。

### 改动
- 新表 `travel_geocode`：`key="城市|地名" → location="lng,lat"`（`create_all` 启动自动建）。
- `geocode_names` 三步：① 一次 `IN` 查缓存 → ② 只对**未命中**的打高德（保留 Semaphore 限流）
  → ③ 新坐标 `merge` 写回。
- 只缓存命中（有坐标）的；未命中不缓存（名称可能后续修正）；key 带城市前缀防不同城同名误命中；
  缓存写失败不影响本次结果。

### 时效性
**故意无 TTL**——地名→坐标是静态的（坐标不随时间变），永久缓存是对的。若某名当初 geocode 错，
改名即换 key 自愈，不需要过期重查。

### 涉及文件
`app/db/models.py`（TravelGeocode）、`app/agent/trip_planner.py`（geocode_names 重写 + `_geocode_key`）、
`tests/test_geocode_cache.py`（命中跳过 / 部分命中只查未命中 / 未命中不缓存 / city 隔离）。

### 效果
重复地名直接命中，省掉整段网络往返 + 降高德 QPS。导入/按天加酒店/生成海报受益最明显。

## 2. Phase 56 — 深度研究提速（流式 + 模型分层 + 并行子任务）

### 背景
深度研究（deepagents ReAct）整轮 ~6 分钟。定位到三个大头：
1. **不流式**：`run_deep_research` 走 `ainvoke`，用户干等 6 分钟才见终稿（体感耗时）。
2. **整个循环跑 v4-pro（推理模型）**：每步长思考链 ×几十步（真实耗时）。
3. **子任务串行**：对比类问题一个个城市查（可并行）。

### ① 终稿流式（体感提速）
- `_invoke_streaming`：`agent.astream(stream_mode=["messages","values"])`，按 message id 跟踪
  「当前正在写的 AI 消息」，token 增量落进 streaming 占位消息（1.2s 节流）；`values` 事件留最终
  state，收尾用 `_extract_answer(最终 state)` 的**干净终稿**定稿 + 挂 sources/记忆（与原逻辑共用）。
- **关键修复（见 §3 踩坑）**：初版只流 `content`，但采集阶段模型输出是工具调用+思考、正文为空，
  于是前 2 分钟仍是空气泡。补上流式 **reasoning**（`_chunk_reasoning` 从
  `additional_kwargs['reasoning_content']` 取）后，采集期就能看到思考链在滚。
- 心跳改后台协程；取消每次迭代查 `is_cancelled`；工具消息不入流。
- **安全阀**：`deep_research_stream`（.env `DEEP_RESEARCH_STREAM=false`）即刻回退 `ainvoke` 老路——
  真 astream 无法离线测，留开关兜底。

### ② 模型分层（真实提速）
- `api-researcher` 子任务（纯数据采集：高德/fetch_url，不需深推理）改用**快模型 v4-flash**
  （`SubAgent` 支持 `model` 字段），主 agent 保持 v4-pro（规划/汇总要质量）。
- 配置 `model_research_sub`（空=回退 `model_classifier`）。

### ③ 并行子任务（对比类提速）
- `RESEARCH_SYSTEM` 子任务纪律加一条：独立采集子问题（多城对比）**同一步并发派多个
  api-researcher**（LangGraph 会并行跑），不再串行等；保留「禁止为每个页面单独派」的反滥用。

### 涉及文件
`app/config.py`（deep_research_stream / model_research_sub）、`app/agent/deep_research.py`
（_invoke_streaming / _chunk_text / _chunk_reasoning / _heartbeat_loop / _build_agent 子模型 /
RESEARCH_SYSTEM 并发纪律 / run_deep_research 流式定稿）、
`tests/test_deep_research_context.py`（流式定稿 + chunk 抽取）、`tests/test_docker_sandbox.py`（签名对齐）。

### 线上实测（admin 账号，真实 DeepSeek 链路）
一次「大理 vs 丽江冬季对比」的完整轨迹：

| 时间 | 现象 |
|---|---|
| 0–120s 采集/思考 | reasoning 实时增长 8→330→…→1656，气泡在滚，不再空转 |
| 126–150s 写报告 | content 逐 token 增长 332→806→1257→1648→2246，报告边写边出 |
| 156s | 干净定稿（去 streaming 标记，2246 字结构化报告，结论先行+对比表，引用了技能） |

- **总耗时 ~2–2.5 分钟**（原 ~6 分钟）——②③ 见效。
- 体感：从「干等 6 分钟」→「全程看到思考 + 报告边写边出」。

## 3. 踩坑与经验

1. **流式推理模型 agent，采集期正文为空**：ReAct 前期全是工具调用+思考，`.content` 是空的，
   只流 content 会看到「空气泡」。必须**同时流 reasoning**。langchain-deepseek 的思考链在
   `AIMessageChunk.additional_kwargs['reasoning_content']`（源码 `chat_models.py` 里确认），
   不是 `.content`。
2. **无法离线测真 astream**：streaming 逻辑靠离线 mock（`_FakeAgent.astream` yield 假 chunk）测
   装配，真链路靠线上验证 + `deep_research_stream` 开关兜底。
3. **改公共调用签名要同步 fake mock**：给 `_invoke_*` 加 `stream_state` 参数后，测试里的
   `fake_invoke` 也得加同名 kwarg，否则 `TypeError: unexpected keyword argument`。
4. **本地测试依赖 DB 隧道**：少数直接调 `run_deep_research` 的测试会走真 DB（load_skill_files /
   _build_turn_messages），隧道（15432）断了会报 `connection refused`——先 `scripts/db_tunnel.sh`。

## 4. 明确不做的（取舍）

**「高德 ∥ 浏览器」并行采集**（`collect_sources`）—— 不做：
- 收益封顶：高德是秒级 HTTP，浏览器抓取才是长尾，而酒店站/路线站/必应**共用单条 CDP 会话 +
  MCP 串行锁 + 每用户浏览器池串行**，物理上无法在一个浏览器里真并行；并行只能省高德那几秒。
- 风险集中在最敏感链路：`asyncio.gather` 两分支后，停止按钮的 `TurnCancelled` 取消语义、异常隔离
  都要重做。性价比低，故保留串行。

## 5. 后续可做（未实现，留档）

- **携程实价：页面内直调 JSON 接口替代 DOM 抓取**。登录态（扫码）跑不掉且已持久复用；真正能提速的
  是登录后在页面上下文里直调携程酒店列表 soa2 接口（拿结构化带价 JSON，跳过 SPA 渲染 + DOM 解析），
  和 Phase 8 城市 ID 直调一脉相承。先用 CDP `list_network_requests` 抓 endpoint/入参再落地。
  预估：数据获取子步骤从 ~8–20s → ~1–3s，且更稳（不受携程改版影响）；对整轮是「快一档」不是「快一倍」
  （后面 LLM 生成推荐的时间不受影响）。
- **研究主循环也上模型分层**：目前只把子任务换了快模型，主 agent 仍全程 v4-pro。若想再砍，可探索
  「快模型跑循环编排 + 只在最终汇总用 v4-pro」，但需 A/B 验证规划质量，风险较高。
- **KV / 前缀缓存友好**：把每轮会变的 prompt 片段（credibility_directive 等）后置，稳住 DeepSeek
  自动前缀缓存的命中前缀。纯收益、不碰结构。
