# 记忆系统设计对比与复盘

> 2026-07-20 整理。目的：厘清本项目记忆机制的三个思想来源（避免以后混淆），
> 记录自研的三元组槽格式、召回频次（hit_count）设计、以及记忆变多时的升级路线。
> 配套代码：`backend/app/agent/memory.py`；相关 task plan：phase4/17/30/45。

---

## 0. 一句话先厘清三个来源（最容易混淆的地方）

本项目的记忆设计**同时借鉴了三个不同来源**，它们不是一回事：

| 来源 | 贡献了什么 | 我们对应的实现 |
| --- | --- | --- |
| **Claude Code**（`src/memdir/`） | 检索侧：小模型选择器 + 新鲜度标注 | Phase 30 `select_relevant_memories` / `_age_label` |
| **ai-agent-book chapter3**（那篇文档） | 认知三分类、JSON Cards、重要性四因素评分 | Phase 45 procedural 类型、hit_count 评分 |
| **自研（Phase 17）** | **三元组归槽（谓词 key + 单槽覆盖）** | `CANONICAL_KEYS` + `_upsert_by_key` |

**关键结论：三元组槽是自研的，不是 Claude Code 的设计。** Claude Code 用的是
「文件 + 索引文档」，完全没有谓词槽概念。搬 Claude Code 的只有检索侧那两块。

## 1. Claude Code 的记忆设计（MEMORY.md + 索引文档）

**存储形态：文件式，不是数据库**
- 一条记忆 = 一个 markdown 文件，带 frontmatter：`name` / `description` /
  `metadata.type`；
- 类型 4 类：`user`（用户是谁）/ `feedback`（工作指导）/ `project`（在做什么）/
  `reference`（外部资源指针）——注意与「情景/语义/程序」无关，也和我们的 type 无关；
- **`MEMORY.md` 索引文档**：每条记忆一行（`- [标题](文件.md) — 一句话钩子`），
  **常驻上下文**每次加载；完整正文只在命中时按需读该文件。

**渐进披露（progressive disclosure）**
- 索引层（name+description，占极小 token）负责「路由/发现」；
- 完整文件正文负责「细节」，命中才加载 → 省上下文。

**检索：独立小模型调用挑 ≤5 条**
- `findRelevantMemories.ts`：扫所有记忆文件头 → 生成 manifest → 单独调一次 Sonnet
  （`sideQuery`），JSON schema 约束输出，选最多 5 条相关的；
- 「宁缺毋滥、可返回空列表」是明确纪律。

**新鲜度：`memoryAge.ts`**
- 人类可读年龄「今天 / 昨天 / N 天前」（模型不擅长日期算术）；
- >1 天的记忆附过期告诫（时点观察 ≠ 实时状态，别当事实断言）。

**特点**：记忆文件可**无限累积**（靠模型写入时自己去重），因为一个代码库的事实是
无界的。它没有「单槽覆盖」来限制增长。

## 2. ai-agent-book chapter3 的关键知识点（第三来源）

**认知三分类**（设计框架，不是存储字段）
- 情景记忆：具体事件（「订了下周五东京航班」）；
- 语义记忆：提炼的稳定特征（「用户是素食者」）；
- 程序记忆：行为流程（「订票先搜直飞→确认座位→用常旅客号」）。

**存储格式递进**：Simple Notes（原子事实，O(1) 但丢语义关联）→ Enhanced Notes
（完整段落）→ JSON Cards（类别→子类→键值）→ Advanced JSON Cards（+backstory/
person/relationship/timestamp，解决消歧但成本高）。

**Mem0 两阶段**：提取候选事实 → 更新决策 ADD / UPDATE / DELETE / **NOOP**。

**重要性四因素评分**：访问频率 + 时间衰减 + 情感强度 + 信息独特性。

**双层记忆架构**：Advanced JSON Cards 常驻提供「概览」+ 上下文感知检索按需提供「细节」。

**明确的「别过度设计」原则**：从 Simple Notes 开始；结构化索引（RAPTOR/GraphRAG）
只在需要跨文档综合时才值得；预处理投资回报高于后处理。

**踩坑**：GraphRAG 把知识拆严格三元组会「语义降级」（条件/时间逻辑丢失）——这正是
我们 content 保留自然语言的原因。

## 3. 本项目实现（自研三元组槽）

### 3.1 存储位置
生产服务器 `<服务器IP>` 本机 **PostgreSQL**，表 `travel_memory`，普通关系行。
原始对话另存 `travel_message`（轨迹层），记忆是从轨迹蒸馏出的画像层。
**不是向量库、不是文件、不是缓存。**

### 3.2 三元组格式（精确定义）

叫「三元组归槽」，但**不是严格 RDF (S,P,O)**，而是「隐含主语 + 谓词槽 + 自然语言值」：

```
存储行:  type=preference   key=口味偏好   content="用户爱吃海鲜和辣"
三元组:  (用户,            口味偏好,      爱吃海鲜和辣)
          └主语            └谓词          └宾语
          隐含=user_id     canonical key  自然语言句子(非原子值)
```

- **主语**：永远是「用户」，不单独存，由 `user_id` 隐含（单主语，无多实体关系）；
- **谓词 = `key`**：结构化索引，从固定集合选，**核心约束「每个 (user_id, key) 只留一行」**
  → 同类覆盖合并、不堆积 → 记忆数天然有界；
- **宾语 = `content`**：一句完整自然语言（字面含主语词），故意不拆原子值，保住语义
  （避开 GraphRAG 语义降级坑）。

### 3.3 表结构

```
travel_memory:
  id / user_id / type / key / content / weight / explicit / hit_count /
  source_conversation_id / created_at / updated_at
```

### 3.4 类型体系（4 个 type，非认知三分法的直接落地）

`MEMORY_TYPES = (preference, fact, trip_state, procedural)`

认知三分法是**设计意图**，4 个 type 是**落地实现**，两者非 1:1：

| 认知分类 | 我们的 type / key | 例子 |
| --- | --- | --- |
| 语义 | `preference` + `fact` | 爱吃辣、常驻成都、忌口花生 |
| 情景 | `trip_state`（当前行程）+ `旅行足迹`（key，存为 fact） | 正在规划哈尔滨、去过厦门+成都 |
| 程序 | `procedural`（规划习惯） | 先定酒店再排景点、自由行不跟团 |

真正区分「记忆是什么」的是 **`key`（谓词槽）**，不是 type；type 更多给内部逻辑用
（trip_state 单槽覆盖、explicit 加权）。`旅行足迹` 概念上是情景派生，为归槽方便存成
`type=fact`，靠 key 标识语义身份——这是个已知的「拧巴」但不影响使用。

### 3.5 CANONICAL_KEYS（谓词槽全集）

```
口味偏好/兴趣偏好/节奏偏好/预算偏好/住宿偏好/出行方式 → preference
常驻城市/忌口过敏/同行情况/旅行足迹                  → fact
规划习惯                                            → procedural
当前行程                                            → trip_state
```

### 3.6 抽取流程（写入）
- **时机**：每轮回复**之后**旁路触发（`extract_and_save`），不占用户等待，失败只 warn；
- **过程**：读现有全部记忆 + 本轮输入 + 回复开头 → 调 **v4-flash** 输出
  add/update/delete → 按 key 归槽 upsert；
- **提炼纪律**（`EXTRACT_SYSTEM`）：只记跨对话有用的、抽象化、相对日期转绝对、
  正面确认也记、附原因、规划习惯归 procedural、旧目的地并入旅行足迹。

### 3.7 注入流程（读取，双层）
- **≤12 条**：全量注入；**>12 条**：v4-flash 选择器挑 ≤5 条（trip_state + explicit
  保底常驻）；
- 包 `<background_memory>` 标签（指令/数据分离）+「N 天前」新鲜度标注；
- 注入的记忆 `hit_count` +1（反哺排序，见下节）。

## 4. 记忆召回频次（hit_count，Phase 45 重点）

**动机**：文档重要性四因素里，此前只用了 explicit(weight) + updated_at，**缺访问频率**
——高频命中但久未更新的核心偏好（「爱吃辣」每轮都用到但没人再更新它）会在排序沉底、
40 条剪枝时被误删。

**实现**
- `travel_memory.hit_count INTEGER default 0`；
- `gather_context` 里对**实际注入**的记忆 `_bump_hit_count` +1（写失败 rollback+warn，
  绝不拖垮上下文收集）；
- `load_memories` 排序 = **`weight↓ → hit_count↓ → updated_at↓`**。

**排序语义（三级优先）**
1. `weight`（explicit=2.0 / 推断=1.0）：用户亲口说的**永远**压过推断的；
2. `hit_count`：同档内高频命中靠前；
3. `updated_at`：再同档看新鲜度。

**连带效果**：`_prune`（超 40 条剪枝）复用此排序，所以**高频记忆自动被优先保留**，
不会因久未更新被误删。

**注意**：hit_count 只影响「基础排序 + 剪枝保护」，**不影响选择器**（选择器纯按内容
相关性挑，不看 hit_count）——所以不会形成「越注入越容易被注入」的正反馈失控。
double-count（guide 轮 gather_context 调 ~2 次）无害，因为是相对信号、统一膨胀不失真。

## 6. 记忆变多时的升级路线（复盘决策依据）

**结论：两个都不急；真要选，选 Claude Code 式索引文档，不要向量库；但旅行场景大概率
永远到不了需要升级那步。**

分档：

- **现状 → 每人几百条以内**：不动。选择器拼的清单（`- id=X [key] content`）**本质
  已是 Claude Code 的 MEMORY.md 索引**，只是从 DB 行现拼、非文件。索引文档模式的核心
  收益已在享受。

- **某用户涨到很多百条**（清单本身长到注入嫌贵）：上**两级清单**（Claude Code 式），
  **不是向量库**——常驻层再压：只注入「key 列表 + 一句话」，选择器命中哪个 key 才拉
  完整 content。纯关系库、零新基础设施。

- **向量库（pgvector）只在三条同时成立才值得**：content 变长自由文本 + 需跨几千条模糊
  语义召回 + 关键词/key 查找失效。旅行画像是有界结构化槽，三条一条不占。**硬拦路虎：
  DeepSeek 无 embedding 接口**，上 pgvector 要额外接第三方 embedding（新依赖/成本/
  故障面）——光这条就性价比极低。

**为什么旅行场景天然有界**：一个人的旅行画像维度有限（口味/预算/节奏/住宿/兴趣/忌口/
同行/足迹/习惯…会饱和），不像代码库事实无界或企业对话百万级。三元组单槽覆盖进一步把
记忆数锁在 ≈canonical key 数量级。

---

## 7. 已知取舍与「拧巴」处（复盘时留意）

1. **三元组是自研，非 Claude Code**——别再把「三元组槽」当成 Claude Code 的设计；
2. **认知三分法 ≠ 4 个 type 的 1:1 落地**——`旅行足迹` 情景派生却存为 fact；若想彻底
   对齐（改 episodic type）是另一次改造，收益不大（type 只是内部标签，检索看 key）；
3. **旅行足迹靠 LLM 提炼**（无脆弱文本解析）——可靠性取决于 v4-flash 执行度，漏收可用
   「✨ 整理记忆」（`consolidate_memories`）重新归槽补救；
4. **NOOP 未显式建模**——我们的 upsert 幂等，实质等价 Mem0 的 NOOP，只是没显式输出
   「这轮啥都不改」。
