# 上下文分层压缩架构说明（Phase 29-34 定稿，留档复盘）

> 2026-07-17 讨论定稿。记录三条链路统一后的上下文管理全景：分段压缩的精确语义、
> 每段的成本/可逆性、与 Claude Code 机制的对应、以及已知边界情况。
> 配套：`task_plan-phase29/33/34`、`深度研究prompt缓存结构与技能清单注入备忘.md`。

## 0. 全景图

```
┌─ 跨轮（三链路统一）────────────────────────────────────────┐
│ 历史 = 全部 user/assistant 终稿，逐字、append-only          │
│ · 工具原文/来源从不进历史（轮末蒸馏 = 隐含的「第 0 段」）      │
│ · ≤60k 字符：全文注入；>60k：结构化摘要 + 近 5 轮全文        │
│ · append-only → DeepSeek 前缀缓存跨轮命中                   │
└─────────────────────────────────────────────────────────┘
┌─ 轮内（仅 research 是 agent 循环，有此层）───────────────────┐
│ 第 1 段：返回时精炼（常开）                                  │
│ 第 2 段：microcompact（>30k token 触发）                     │
│ 第 3 段：全量摘要（仍超限兜底，deepagents 内置）              │
└─────────────────────────────────────────────────────────┘
```

## 1. 四段压缩的精确语义

### 第 0 段 · 轮末蒸馏（跨轮，最彻底）

工具结果、抓取原文、中间推理在轮末全部丢弃，只有终稿 assistant 消息进入历史。
这是三条链路能统一「全文历史」的前提——历史里天然没有可清理的工具内容，
所以 direct/guide（单次调用，无轮内循环）不需要 microcompact。

### 第 1 段 · 返回时精炼（research 轮内，常开，机械式）

| 工具 | 进上下文的形态 |
| --- | --- |
| web_search | 标题 + URL 列表 |
| fetch_url / open_page | **前 1500 字原文预览** + 来源编号 sN；全文（≤2 万字）留 source_store |
| read_source | 按 3000 字翻页 |
| amap_city_brief | 代码拼装的紧凑摘要 |

**关键：是「原文预览 + 索引」，不是摘要**。摘要有语义损耗且要花 LLM 调用
（Phase 11 教训：逐来源 LLM 摘要把整轮拖到 3-6 分钟）；预览零成本，缺的靠索引找回。
未覆盖的工具：task（子任务报告）、execute（沙箱输出）、read_file（技能全文）——
它们是第 2 段的主要靶子。

### 第 2 段 · microcompact（research 轮内，>30k token 触发）

- **不是清所有 tool_content**：保留最近 5 个完整（工作集），只清更旧的；
- **不生成摘要**：旧结果换成可行动占位符「[已清理；如需重看请用 read_source]」；
- AI 消息（模型自己的笔记/结论）永不清 → 配套「记笔记纪律」：读完来源先用 1-2 句
  记要点，只有自己写下的内容保证一直在；
- 一次性深清（clear_at_least=0，过线后旧的全清不挤牙膏）→ cache 打断压缩成单次事件。

实现：`ClearToolUsesEdit`（langchain，对齐 Anthropic clear_tool_uses_20250919）。

### 第 3 段 · 全量摘要（research 轮内兜底，deepagents 内置）

仍超限时把旧消息（含对话、占位符、笔记）压成结构化摘要；被驱逐原文落盘
`/conversation_history/{thread_id}.md`，agent 可 read_file 找回。
**勿自行再挂 SummarizationMiddleware**——同名判重线上必炸
（见 pitfalls/deepagents内置Summarization中间件与同名判重.md）。

## 2. 成本/可逆性阶梯（设计原则）

**越早的段越便宜、越可逆；越晚的段越昂贵、越有损。**

| 段 | LLM 成本 | cache 影响 | 可逆性 |
| --- | --- | --- | --- |
| 0 轮末蒸馏 | 零 | 无（历史 append-only） | 不可逆（刻意） |
| 1 预览+索引 | 零 | 无 | 完全可逆（read_source） |
| 2 microcompact | 零 | 单次 bust | 可逆（read_source 重读） |
| 3 全量摘要 | 一次 flash 调用 | 单次 bust | 半可逆（落盘可 read_file） |

## 3. 跨轮 60k 阈值的精确语义（易误解处）

- 60k 字符量的是**压缩前的全量原文**，是「切换形态」的触发线，不是压缩后的目标大小；
- ≤60k 时**不发生任何压缩**（摘要虽每轮末维护，但全文路径用不到）；
- \>60k 后的注入量 ≈ 摘要（硬截 2000 字符）+ 近 5 轮**全文**——通常两三万字符，
  **但无硬保证**（近 5 轮全是超长产出时仍可能超 60k，当前不做二次收缩）。

## 4. 已知边界与观察点（复盘清单）

1. **回退无二次收缩**（上条）：极端时 direct/guide 一次大 prefill 甚至触发上下文上限。
   备选修法：回退路径再查总量，超限逐级缩近 5→3→1 轮（十几行）。
2. **超 60k 后近 5 轮变滑动窗口**：从那轮起每轮 cache miss。个人量级罕见，建议开新会话。
3. **microcompact「触发但清不动」**：全量历史算进 30k 触发线，历史占大头时清工具结果
   收益小 → 自然滑落第 3 段兜底，行为正确，知道衔接即可。
4. **direct 冷启动延迟**：缓存冷时全文历史 prefill 加秒级首字延迟。量化方法：
   LLMClient 层打 DeepSeek `prompt_cache_hit_tokens` 日志；恶化则单独调小
   `HISTORY_FULL_MAX_CHARS`。
5. **快慢通道统一全文的设计依据**：记忆一致性（用户感知同一个助手）+
   append-only 比滑动窗口更省缓存（旧的 5 轮窗口每轮都 bust 前缀）。

## 5. 与 Claude Code 的对应表

| Claude Code | 本项目 |
| --- | --- |
| 工具结果 >50k 落盘换引用 | 第 1 段：1500 字预览 + source_store + read_source |
| microcompact（清旧工具结果，保最近 N） | 第 2 段：ClearToolUsesEdit（保 5，占位符可找回） |
| autocompact（9 段式摘要 + 近期逐字保留） | 第 3 段：deepagents 内置 Summarization（落盘可找回）；跨轮为「摘要+近 5 轮全文」装配 |
| 会话轨迹 append-only 保 KV cache | 全文历史 append-only；易变内容（记忆/沙箱说明/本轮问题）置尾 |
| （无对应） | 第 0 段轮末蒸馏：CC 是持久轨迹没有「轮」边界，我们的跨轮蒸馏比它更激进 |
