| 阶段 | 问题 | 目标 |
| --- | --- | --- |
| 一、流式丝滑 | 攻略正文「一段一段跳出来」，最坏 ~2.7s 才动一次 | 正文连续平滑流动 |

## 1. 阶段一：流式输出丝滑（纯前端 + 一个后端配置）

### 1.1 问题定位

流式链路是「后端定时落库 + 前端轮询整体替换」，四个叠加因素：

1. 后端每 **1.2s** 才把增量写库一次（`orchestrator._stream_into` / `run_direct_answer`）；
2. 前端每 **1.5s** 轮询一次（`Home.poll`），两个时钟叠加 → 最坏 ~2.7s 跳一次；
3. 每次轮询 `setMessages(data.messages)` **全量替换**，未变化消息也整体重渲染，
   `GuideBody` 每次 react-markdown 全量解析正文——长攻略渲染本身卡顿；
4. 模型输出本身是「一段输出→停顿→再一段」的突发模式（DeepSeek 思考模式特性，不可改）。

1-3 可改；第 4 点用前端打字机平滑缓冲抹平。

### 1.2 改动

| # | 改动 | 位置 |
| --- | --- | --- |
| ① | 新增 `settings.streaming_flush_interval_s=0.5`，guide/direct 两处 flush 节拍 1.2s→0.5s | `config.py`、`orchestrator.py` |
| ② | 轮询 1500ms→800ms | `Home.tsx poll` |
| ③ | 纯函数 `mergeMessages`：按 id 比对内容签名，**未变化消息保持原对象引用**；`GuideBody` 包 `React.memo` | `interaction.ts`、`Home.tsx` |
| ④ | 纯函数 `typewriterStep`（积压越大揭示越快：1→2→4→6 字符/tick）+ `useTypewriter` hook（终稿/隐藏瞬间追平，挂载不重放） | `interaction.ts`、`hooks/useTypewriter.ts`、`Home.tsx Message` |

### 1.3 效果

- 可见粒度 ~2.7s → ~1.3s（节拍）+ 打字机连续流动（模型突刺被抹平）；
- 长会话轮询不再全量重渲染（引用保持 + memo）；
- 终稿/停止/切会话回看：瞬间全量显示，不播动画。

## 2. 阶段二：感知提速（让 3 分钟不难等）

### 2.1 快答先行（核心）

深度研究模式早有 `_emit_quick_take`（Phase 71：150 字初步判断 + `meta.preliminary` 橙色徽章 +
`_is_running` 排除逻辑），但 **guide 攻略链路没有**。平移该机制：

- 新增 `settings.guide_quick_take=True`；`orchestrator.emit_guide_quick_take`（v4-flash，
  注入 pref 摘要 + 记忆，150 字初步规划思路）；
- LangGraph 拓扑改为 `parse → quick_take → collect`：`quick_take_node` **先建流式占位
  （Phase 71 顺序不变式：快答是非流式 assistant，没有占位 `_is_running` 会误判本轮完成、
  前端停止轮询、完整版永远收不到）**，再发快答；占位 msg_id 入 state 由 generate 复用；
- 配套修掉两处 **streaming 残留风险**（快答后占位有一段空白期，这是新引入的）：
  - `apologize_node`：collect 无料时**就地终稿占位**而非另加一条消息；
  - `_ensure_stopped_message`：空占位被停止时也**就地终稿**「已停止本轮。」
    （原实现只终稿有内容的占位 → 空占位残留 streaming 标记，前端永远判「运行中」）。

### 2.2 其他三项

| # | 改动 | 说明 |
| --- | --- | --- |
| 预期文案校准 | 核实 `inferThinkingMode` 已按**实际进度文案**推断（Phase 71.1 修过）：guide 显示「通常 3-4 分钟」不混入「4-6 分钟」；补回归测试钉住 | 无需改数值 |
| 页面恢复秒见结果 | `poll` 抽成 `pullOnce`；`visibilitychange` 变可见且正在轮询时**立即补拉一次** | `Home.tsx` |
| 流式字数进度 | 流式正文下新增 `.stream-foot`：光标 + 「已生成 N 字」（前端自算，零后端改动） | `Home.tsx`、`index.css` |

## 3. 阶段三：真实提速（服务器日志诊断驱动）

### 3.1 诊断：Langfuse trace 精确还原 6 分 52 秒

用户反馈"最近一轮 6 分半"（天堂寨 23:45 那轮）。排查中发现两个方法论要点：

1. **`travel_message.created_at` 是占位消息的创建时刻，不是终稿时刻**——流式正文是后续
   UPDATE 上去的（表无 `updated_at` 列）。最初按 `created_at` 算出"9.5 秒出稿"是假象；
2. checkpoint_id 是 uuid4 随机（不是 v1），解不出时间戳；**Langfuse trace 的 span
   startTime/endTime 才是精确证据**（自托管 Langfuse 全程开着，直接 curl API 可查）。

Trace 还原（UTC 时间，本地 +8）：

| 阶段 | 耗时 | 结论 |
| --- | --- | --- |
| 路由分类（v4-flash） | 7s | 用户开着「深度推理」开关（localStorage 持久），但 resolve_route Phase 44 版先分类，kind=guide → 走 guide |
| 需求解析（v4-pro） | 6s | |
| **小红书采集**（搜索 + 5 篇详情串行 ×~20s） | **~163s** | 大头之一；MCP 单浏览器会话**不可并发**（注释写明），但可减量/复用/与必应并行 |
| 必应（1 搜索 + 4 页） | 50s | light 档 |
| **攻略生成（v4-pro）** | **200s** | **思考链 14878 字符吃满 16000 token 预算**（正文仅 5335 字），最大单项 |
| 自检 + 记忆提炼 | 6s | |

另发现：**quick take 的 LLM 调用执行了但没落 preliminary 消息**——DeepSeek 思考模式在
`max_tokens=400` 下 token 全花在思考链、`content` 为空，`(reply or "").strip()` 判空跳过。

### 3.2 改动（三项代码 + 两项配置）

| # | 改动 | 收益 |
| --- | --- | --- |
| ⑨ | **小红书 × 必应并行采集**：`collect_sources` 未复用时 `asyncio.create_task(_collect_xhs)` 与浏览器（必应 light + 携程路由）同时跑——xhs 是 HTTP MCP、必应是 ChromeMCP 两通道独立；xhs 收成 0 篇再补 full 第 2 查询。hotel 意图/复用命中仍走原串行路径 | 采集 213s → ≈max(xhs, 必应) ~165s |
| ⑩ | **生成思考精炼**：ITINERARY/HOTEL system 追加「思考纪律」——思考两三行要点即可，不推演全文，把输出预算留给正文 | 生成 200s → ~120-140s |
| ⑪ | **quick take 空 content 修复**：max_tokens 400→1000 + content 空时用 reasoning 前 200 字兜底（guide 与 deep_research 两处同修） | 30s 快答真正生效 |
| ⑫ | 服务器 `.env`：`XHS_NOTES_PER_TURN=3`（详情 5→3 篇）、`XHS_REUSE_MAX_DAYS=14`（复用窗口 7→14 天） | 省 ~40s；复用命中省 ~120s |

### 3.3 并行采集的等价性论证

- 必应恒 light（预判 xhs 有料）：xhs 收成 1-2 篇时与串行档位一致，省 50s；
- xhs 收成 ≥3（原逻辑 skip 必应）：并行版必应白跑 50s，但总时长 = max(xhs, 必应) 不变；
- xhs 收成 0：原串行 full ~90s，并行版 light 50s + 补查 ~40s ≈ 90s，且必应 light 4 页已兜底。
- **并行总时长 ≤ 串行，任何收成都不亏。**

## 4. 阶段四：故障韧性（线上事故驱动，2026-08-14）

### 4.1 事故：xhs MCP 垮了 → "无限死循环" + 停止按钮无效

线上日志实证（`docs/pitfalls/小红书MCP故障触发LangGraph重试与停止失效.md` 全细节）：

| # | 根因 | 后果 |
| --- | --- | --- |
| 1 | **collect 节点异常冒进 LangGraph 默认重试**：`BrowserAcquireTimeout`（排队 120s）没被 `except MCPConnectionError` 捕获 → 图自动重试 3 次，每次再等 2-5 分钟 | "无限死循环"（10 分钟级） |
| 2 | **quick_take 提前建的 streaming 占位在异常路径无人终稿** → `_is_running` 永远判运行中 | 前端无限转圈、停止形同虚设 |
| 3 | **采集期间无取消检查点**：`await xhs_task`（并行改造引入）、xhs 逐篇、浏览器 acquire 排队 | 停止按钮无效窗口最长 2-5 分钟 |
| 4 | **xhs MCP 故障不快速失败**：每篇详情等 40s 超时 × 7 次尝试 ≈ 5 分钟 | 纯等待 |

### 4.2 修复（⑬ 五处 + ⑭ 总预算 + ⑮ 名实修复）

| # | 改动 | 效果 |
| --- | --- | --- |
| ⑬-① | `collect_sources` 浏览器块全程 try：**除 TurnCancelled 外所有异常就地消化**，绝不冒进 LangGraph 重试；入口加 `_cancel_check` | 故障轮次 ~1 分钟内正常终止（apologize） |
| ⑬-② | `_ensure_stopped_message(cid, text)` 参数化；`run_conversation_turn` 的 `except Exception` 分支也调它（「抱歉，处理过程中出错了」） | 异常失败同样终稿残留占位，前端不再假死 |
| ⑬-③ | `await xhs_task` → 既有 `cancel.wait_cancellable(cid, task)`；`_collect_xhs` 每查询前加 `_cancel_check` | xhs 等待期间停止立即生效 |
| ⑬-④ | `xhs_mcp` 详情**连续** 2 次失败 → break（熔断）；短笔记不计故障 | MCP 全垮时不再逐篇等超时 |
| ⑬-⑤ | `BrowserPool.acquire(user_id, on_wait, cancel_check=None)` 排队循环内周期检查；`ChromeMCP` 透传 | 浏览器排队 120s 期间停止也立即生效 |
| ⑭ | **整轮总预算** `xhs_collect_timeout_s=150`：搜索+全部详情合计超时即整轮放弃（`asyncio.wait_for` 包裹），必应兜底 | 挡"MCP 半死"（失败-成功交替/每篇卡超时边缘），采集段 ≤150s |
| ⑮ | 熔断计数**名实修复**：成功（含短笔记）即重置为 0，恢复「连续」语义（旧实现漏重置 = 累计 2 次失败，健康 MCP 下零星失败会误熔断丢料） | 名实一致 + 回归测试钉住 |

### 4.3 教训

- **LangGraph 默认节点重试对"外部依赖故障"是灾难**：LLM 抖动重试合理，MCP/浏览器/排队
  这类分钟级外部故障必须由节点自身消化；
- **凡是把"占位消息创建"提前的改动，必须排查全部收尾路径**（apologize/停止/异常失败）
  都能终稿占位，否则 `_is_running` 永远 true = 前端假死；
- **MCP 故障要快速失败（熔断 + 总预算）**，不是逐篇等超时；
- **熔断/限流类计数器的语义（连续 vs 累计）必须在代码里写死并配测试，注释不算数**。

## 6. 踩坑索引

1. **`created_at` 陷阱**：流式消息的创建时间 ≠ 终稿时间。复盘耗时必须用 Langfuse trace。
2. **quick take 空 content**：DeepSeek 思考模式在 `max_tokens` 过小时 token 全被思考链吃掉——
   所有"短输出"的 v4 调用都要给足 token + 空内容兜底。
3. **快答引入的占位空白期**：凡"占位可能为空"的收尾路径（apologize/停止/异常失败）都必须
   就地终稿占位。
4. **必应恒 light 的取舍**：xhs 收成好时必应白跑（资源浪费但总时长不变）；换来 xhs 少时省 50s。
5. **数量类参数是"收益-质量"权衡**：3 篇详情 + light 4 页 + 高德，来源总量仍足够；复用窗口
   14 天利用"半衰期以周计"的既有判断（图片 URL 仍按 20h 过期清空）。
6. **LangGraph 重试 × 外部依赖**、**熔断语义名实**：见阶段四与 pitfalls 文档。

## 7. 后续方向（未做）

- **生成两段式**：先概览+前半程（~60s 首段可见）再续写后半程——总时长不变、感知再提升；
- **SSE 真流式**：后端逐 token 推送，前端逐 token 渲染——根治"轮询+落库"架构的延迟上限；
- 若生成仍是瓶颈：DeepSeek 思考开关/更小模型分层（如简单攻略用 flash）需质量评测后再定。
