# 圆周旅迹 UI、交互动效与相册整理体验分析

体验日期：2026-10-20。通过电脑操控本机安装的圆周旅迹，观察实际界面、交互状态和应用内协议。本文是产品研究，不是功能实施计划，不包含应用代码变更。

## 1. 结论与证据边界

最值得 17同游借鉴的是：以照片为主角的统一视觉语言、先展示成品价值再请求授权、把「发现旅行素材」与「生成故事」拆开，以及从行前规划延伸到行后回顾的产品闭环。

实际查看了计划首页、我的、探索地图、旅迹故事引导、城市搜索、授权说明及协议、旅迹故事空态、加号菜单、照片选择器及相簿下拉列表。

- 经用户允许，将体验中的常住城市设为苏州市，并确认页面显示该值。
- 用户随后允许接受协议并继续查看系统权限选择；恢复观察时，页面已显示「照片数量较少，暂未发现旅迹故事」。未观察到中间系统权限选项及其实际选择，不能据此判断授权范围。
- 手动照片选择器显示「未找到图片文件」，相簿下拉列表为「最近项目，0」。只能确认应用当前可访问的素材为空，不能断言用户整台电脑没有照片。
- 未选择、上传或生成照片故事，未发布、分享，未切换自动发现。
- 动效分析来自操作与多次截图中可见的画面变化，没有逐帧录像、帧率、精确时长或缓动曲线测量。
- 无法验证真实旅行切分、重复照片处理、照片质量筛选、生成内容质量、成品编辑/导出、后台处理性能和真实数据传输行为。

## 2. UI：统一的「旅行收藏物」语言

| 页面 | 实际观察 | 设计作用 | 对 17同游的启发 |
| --- | --- | --- | --- |
| 计划首页 | 白底与淡蓝氛围背景；顶部通知和新建；横排倾斜卡片；下部黑色创建行程主按钮与文字式导入入口 | 先让用户看到可逛内容，再提供任务入口；主次动作对比明确 | 保留现有统一输入，强化热门卡和成品预览，避免再堆第二个输入框 |
| 底部导航 | 浮动白色胶囊容纳计划/探索/我的，黑色问 AI 按钮独立 | 把页面导航与助手动作分组 | 可参考视觉分组，但需评估现有四项移动导航与安全区，不机械增加按钮 |
| 我的 | 旅迹故事大卡；国家/城市/故事统计；收藏和订阅用文件夹/叠片图形；采集区使用票券边缘 | 将个人内容表达成可积累的收藏物，形成长期使用感 | 个人回忆入口比把所有照片塞进聊天消息更清晰 |
| 探索 | 淡色地图作为底层；城市图片与短句标记；底部白色圆角内容抽屉 | 空间位置与内容列表共存 | 可用于地点/路线查看；此次未验证抽屉拖拽吸附及地图列表双向联动 |
| 旅迹故事 | 地图横卡与国家/城市计数；信息提示强调生成前不上传；底部右侧黑色加号 | 同时表达足迹、故事集合、素材入口 | 回忆页可用旅行封面和日期作为主结构，地图作为补充 |

它的精致感来自同一套相纸、叠片、文件夹、票券和圆角语言反复使用，界面中的图形与内容含义一致。主操作使用黑色，蓝色主要承担氛围与提示，照片本身承担丰富色彩。

需要谨慎借鉴：本次电脑窗口呈现明显的纵向移动端布局，空态留白很多，部分次级文字对比偏弱。不能把这种截图比例直接作为 17同游桌面布局标准；移动端也应沿用项目已有可读字号基线。

## 3. 动效：用变化解释功能结果

### 实际看到的变化

旅迹故事引导在不继续操作时，主视觉会呈现不同阶段：漂浮的相纸照片、叠放的目的地照片卡（示例含照片数量）、放大的图文故事卡、日期/封面或拼贴画面。照片存在旋转、位移、缩放和叠放的视觉变化；背景维持淡蓝色，底部功能标题、说明和操作区域保持稳定。

这种动效的作用是解释「散乱照片 → 一次旅行 → 可阅读的故事」，用户在授权前便能理解产出。它比单独展示加载转圈更有说明价值。不能仅凭截图推断它使用了哪一种动画框架、真实三维渲染或共享元素转场。

授权说明采用遮罩加底部大圆角面板；协议在上层居中面板中展示；加号打开右下角的两个胶囊选项并压暗背景。这些层级让人能理解当前操作仍属于故事页面。未测得转场时长和曲线。

### 给 17同游的建议值（不是竞品测量值）

- 卡片按压反馈约 120–180ms，轻微缩小即可。
- 面板展开/收起约 220–320ms，以淡入与短距离位移为主。
- 成品演示约 6–10 秒走完「照片 → 分组 → 故事」；允许跳过，不能阻挡主按钮。
- 降低动态偏好开启时显示静态成品预览，仍能理解功能。
- 整理进度用真实阶段和数量，例如「已读取 32 张，发现 2 段旅行」；不要用循环演示冒充真实进度。

优先把动效投入内容状态变化、反馈和上下文延续，少做与任务无关的常驻装饰动画。

## 4. 相册整理：已验证流程与产品声明

### 实际走到的流程

1. 首次入口展示「整理相册，生成游记」，通过示例照片说明产物。
2. 进入「旅迹故事」介绍；填写常住城市。直接点击立即开启也会先进入城市搜索。
3. 搜索苏州，结果区分苏州市与苏州工业园区，并高亮匹配文字；选择后返回引导页。
4. 点击立即开启，出现相册用途、照片隐私、默认私密三块说明，以及协议链接和同意/不同意按钮。
5. 后续观察到照片数量较少提示与旅迹故事空态，国家和城市均为 0。
6. 右下角加号提供「发现新旅迹故事」「选择照片生成」。后者进入照片选择器，支持相簿下拉、预览和确定；无素材时两项操作禁用。

### 应用内声明（未验证底层实现）

- 生成前使用照片时间、位置整理旅行，不上传照片；主动生成后上传选中照片识别，未参与生成的照片不在服务器保留。
- 内容默认仅本人可见，主动发布/分享是另一环节。
- 常住地用于区分、筛选旅行素材；拍摄时间用于排序与划分旅行；拍摄位置用于目的地和路线整理。
- 协议提到位置缺失时可能依据照片中的建筑、景观或文字推测地点，并提示结果可能有偏差。
- 用户主动开启自动发现后，会定期分析授权范围内的照片/视频并形成故事建议。此次只看到了该入口，未开启或测试。

说明来源：[应用内《旅迹故事使用须知及个人信息授权协议》](https://pitravel.cn/story-notice?lang=zh_cn)。这里记录的是产品公开说明，不代表对其实现做过技术审计。

### 做得好的地方

- 将自动发现与手动选图分开，覆盖「我不知道有哪些值得整理」和「我要整理这一组」两种意图。
- 用常住城市帮助解释哪些照片属于旅行，而非要求用户逐张分类。
- 在关键操作前说明照片何时上传，并在故事首页保留简短提示。
- 足迹统计和故事结合，提供回访理由。

### 本次暴露的体验缺口

- 「照片数量较少」没有在该提示中解释最低条件、照片时间/位置要求或权限是否受限。
- 空态主要按钮是再次发现；手动选图藏在加号里。自动发现失败后，直接提供「选择照片」会更明确。
- 未提供可直接体验的示例故事入口，当前无素材时难以评估完整价值。
- 故事为空时已突出「分享旅迹得周边」，与此时最迫切的整理任务存在竞争。

## 5. 17同游应如何吸收

### 产品位置

建议研究一个独立的「旅行回忆」能力，可从已结束行程或个人页进入：行前由攻略形成计划，行中留下照片与记录，行后整理成故事。已有行程可提供日期、目的地和每日地点，但应让用户确认真实发生的内容，不能把计划自动当作事实。

项目代码 `backend/app/api/trip_modules_api.py` 明确记录旧协同行程相册曾按用户要求移除。这里的建议是新的方向，不默认恢复旧模块或改变原先决策。

### 建议分阶段

| 优先级 | 内容 | 价值与范围 |
| --- | --- | --- |
| P0 | 统一旅行封面卡、照片叠片语言与清晰主按钮；提供静态/轻动画成品示例 | 提升可理解性，可先应用在现有入口，无需先做全量照片扫描 |
| P1 | 用户主动选择一组照片；按日期分组并允许改日期/地点/顺序；确认后生成私密故事 | 完成最小可验证闭环。无 GPS、截图、时区不一致均需允许手动修正 |
| P1 | 已有行程作为可选关联，独立确认共享范围 | 可以复用行程信息，但行程成员关系不应自动使所有私人照片公开 |
| P2 | 本机发现候选旅行、常住城市过滤、重复候选合并、增量扫描 | 处理完整相册的复杂度更高，应在手动流程有效后再做 |
| P2 | 足迹地图、故事回看与导出 | 在有真实内容后增强回访和传播价值 |

建议流程：选照片 → 查看按日整理结果 → 修正地点与顺序 → 确认上传范围 → 生成草稿 → 编辑 → 单独决定是否分享。

### 三端能力边界

当前 iOS 已有 `PhotosPicker` 上传聊天图片的路径和相册相关用途描述；这不能自动等同于拥有完整相册扫描、元数据聚类、增量发现能力。Android 目前为独立打包的 WebView 应用，网页和原生能力也需分开设计。

手动选择素材适合作为三端共同起点。系统相册的持续发现应按端设计和验证；不要在 Web 首版承诺后台扫描整机相册。现有上传能力也不能直接当作完整的照片理解和故事生成链路。

如果进入开发，需另写 task plan、对应测试用例文档并落地自动化测试。重点验收：无图片、有限权限、无 GPS、拍摄时间缺失、跨时区、同日多城、用户修正保留、重复扫描幂等、取消与恢复、默认私密及分享隔离。上述均是未来验收方向，不是本次已实现能力。

## 6. 后续仍需实测

用明确获准的旅行测试素材，分别覆盖一段国内旅行、多城旅行、缺少定位的照片和混入日常照片；确认自动切分结果、编辑入口、上传提示、生成质量、失败重试及导出效果。当前没有可访问素材，不能将这些项目标为已验证。
