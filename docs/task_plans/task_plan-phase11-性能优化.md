# Task Plan — Phase 11：查询提速（工程优化，零外部依赖）

> 创建：2026-07-06　状态：已完成并上线
> 范围：提速调研中的方案 A。B（搜索 API）/D（携程列表接口）暂不做，携程维持扫码方案。

## 四项优化

1. **流式输出（体感提升最大）**：攻略生成从「憋 60-90s 一次性出全文」改为
   边生成边显示。实现：LLMClient 增加流式生成；生成开始即落一条
   `meta.streaming=true` 的 assistant 消息，每 ~1.2s 增量更新 content/reasoning，
   完成后写终稿（带 sources/记忆 meta，去掉 streaming 标记）。
   前端轮询天然支持增量渲染；`_is_running` 将 streaming 消息视为运行中；
   启动修复函数处理被打断的 streaming 消息（补中断说明）。
2. **一轮复用一个浏览器会话**：现在一轮起 3-4 次 mcp 进程（携程/每个搜索/抓取
   各一次），每次 2-4s。改为 `_run` 里建一个会话贯穿全程传下去。
   附带：页面预算 max_pages_per_task 20→30（全轮共享）；
   查询间 12s 硬等降为 5s（独立会话防限流的理由已不成立，且有 360 兜底）。
3. **砍掉每页摘要 LLM 调用**（8 次 × 2-5s）：抓取来源的 summary 改为
   「清洗 + 截断的正文摘录」（去掉 a11y 树的 uid 噪声，截 1500 字），
   直接喂给最终生成——生成模型自己消化，效果不降。
4. **页面分类规则快判**：正文 >1500 字且无验证码/登录特征词 → 直接判 content，
   跳过 LLM 分类（8 次 × 1-3s）；模糊情况仍走 LLM。

## 不变式

- Action Guard、登录 handoff、扫码流程、相关性校验全部不动。
- 礼貌限速机制保留，只调低默认值（2-5s → 1-2.5s）。

## 预期

总时长 3-6 分钟 → 约 1.5-2.5 分钟；首字可见时间 60-90s → 5-10s。

## 验收

1. 线上一轮查询计时对比；前端可见回复逐段增长。
2. 中断场景：生成中重启服务 → streaming 消息被修复为中断提示，会话不锁死。
3. 存量测试全过 + 新增：streaming 修复/running 判定、摘录清洗。

## 验收结果（2026-07-06 线上实测，南京 2 天路线）

- 总时长 **130s**（此前同类查询 3-6 分钟）
- 首段回复可见于 **82s**（此前需等全文生成完，3-5 分钟后才见字）
- 收集阶段 ~75s 抓齐 6 来源（高德秒回 + 5 网页），流式生成 ~48s 全程可见增长
- 知乎滑块验证码被正确静默跳过；终稿 meta 完整（sources/记忆）
- 102 tests passed 无回归
