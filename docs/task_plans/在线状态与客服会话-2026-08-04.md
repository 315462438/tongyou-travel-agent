# Task Plan · 管理员在线状态 + 客服会话（2026-08-04）

## 问题

线上已有 28 位注册用户，但 admin 的「用户管理」面板只有**会话数/记忆数**两个静态计数：

- 看不出**谁还在用**。28 个账号里哪些是活跃用户、哪些是注册完再没回来过，完全分不清；
  排查线上问题时也不知道当事人是否还在页面上。
- 用户遇到问题**没有任何反馈通道**。目前只能靠用户自己找到运营者，产品内是死路。

## 决策（已与用户确认）

| 议题 | 选择 | 理由 |
| --- | --- | --- |
| 在线口径 | **最近活跃，无心跳** | 每次带 token 的请求更新 `last_seen_at`（节流 60s），`≤5min` 判在线。不新增轮询，成本接近零；心跳方案要让所有在线用户持续发请求，为这点精度不值得 |
| 客服形态 | **每用户一条常驻会话** | 贴合「汇报问题」，复用 Phase 61 群聊的表结构与轮询模式；工单制的状态流转与多列表在当前规模是过度设计 |

## 方案

### 后端

**① 在线状态**

- `TravelUser` 加 `last_seen_at`（nullable datetime + index），`migrate.py` 幂等
  `ADD COLUMN IF NOT EXISTS`。存量用户为 NULL → 显示「从未活跃」，不伪造。
- `deps.get_current_user` 里 touch：**仅当距上次超过 `online_touch_throttle_s`(60s) 才写**。
  鉴权是全站最热路径，每请求一次 UPDATE 会造成明显写放大。
- `GET /api/admin/users` 返回 `id` / `last_seen_at` / `online`。
  `online` 由**服务端**按 `online_window_s`(300s) 判定 —— 不把阈值下放给前端，
  避免两端口径漂移。

**② 客服会话**

单表 `travel_support_message`：

| 列 | 说明 |
| --- | --- |
| `id` / `user_id` / `content` / `created_at` | 同群聊 |
| `sender` | `user` \| `admin` |
| `read_at` | 已读时间，NULL=未读。**未读数由它算**，不另建 thread 表 |

未读定义对称：admin 未读 = `sender='user' AND read_at IS NULL`；
用户未读 = `sender='admin' AND read_at IS NULL`。读取即标记，语义简单不易错。

`app/api/support_api.py`：

| 路由 | 权限 | 说明 |
| --- | --- | --- |
| `GET /api/support/messages` | 登录 | 自己的客服会话，顺带把 admin 消息标已读 |
| `POST /api/support/messages` | 登录 | 用户发问题 |
| `GET /api/support/unread` | 登录 | 轻量未读数（前端低频轮询红点） |
| `GET /api/admin/support/threads` | admin | 会话列表：用户名/未读数/最后一条摘要/时间，按最新排序 |
| `GET /api/admin/support/{user_id}/messages` | admin | 读某人会话，标记其 user 消息已读 |
| `POST /api/admin/support/{user_id}/messages` | admin | 回复 |

### 前端

- **用户端**：侧边栏 + 移动底栏「💬 联系客服」入口，带未读红点；抽屉式对话
  （左右气泡、Enter 发送、轮询：打开时 3s / 关闭时 30s 查未读）。
- **Admin 端**：用户管理面板每行加在线圆点 + 「在线 / 12 分钟前 / 从未活跃」；
  新增「客服会话」标签页（列表 + 未读徽标 + 逐个回复）。

## 边界

- **不做实时推送**。轮询足够，且与现有对话流一致（本项目全线轮询，不引入 WS）。
- **不做工单状态流转**、不做附件上传、不做客服机器人自动回复。
- 在线判定依赖请求活动：用户开着页面但不操作时，前端仍有轮询（会话列表/未读），
  故一般仍算在线；完全静置且无任何轮询的场景会掉成「N 分钟前」，可接受。
- `last_seen_at` 为 NULL 的存量用户显示「从未活跃」，**不回填**（没有真实数据可依据）。

## 验收

- `tests/test_support_api.py`：未读对称性、读取即已读、非 admin 拿不到他人会话、
  admin 回复后用户侧未读 +1。
- `tests/test_online_status.py`：节流不写库、超窗口才写、`online` 判定边界、
  NULL 不误判在线。
- `tests/test_agent_api_auth.py` 的 AST 全量路由扫描必须继续通过
  （新路由全部带鉴权，不进 `PUBLIC_ROUTES`）。
- `docs/test_cases/` 出验收用例。
