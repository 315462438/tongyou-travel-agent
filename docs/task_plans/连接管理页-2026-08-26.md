# 连接管理页（Phase 109）— 2026-08-26

> 状态：第一期（状态页 + 断开）与第二期（独立扫码连接 + 操作层）**均已落地**。

## 一、动机：先把一个错误论据剔掉

起因是看了豆包的「技能·连接器」目录，想把携程和小红书剥离成用户可连接的模块，
**理由之一是「不连接就不走这两路，因而更快」**。

这条对携程成立，**对小红书是反的**，先说清楚，否则后面所有取舍都会歪：

```python
# orchestrator._web_search_mode
if xhs_count >= settings.xhs_skip_search_min:   # 线上 = 3
    return "skip"      # 必应/浏览器整条道不跑
```

线上 `XHS_NOTES_PER_TURN=3`，**正常轮次恰好命中 skip**。也就是说小红书不是"额外一路"，
它是**主力**——它跑通了浏览器才不用跑。配上 Phase 105 实测（小红书道 96/120/96s，
浏览器道 272/208/457s），"用户不连小红书"= 强制回落必应+浏览器 = **慢 2-4 倍**。

携程那半成立：它只在 hotel 意图时跑，且 `site_ctrip` 的 span **含登录等待**
（Phase 93 记过"那常是整轮最慢的一段"）。没连携程直接走必应，确实更快，
也不会被登录卡在对话中途打断。

**所以本期的目标不是提速，是透明度与可管理性。** 提速留给第二期的「未连接则不尝试」开关。

## 二、两个源结构上不对称（决定了本期只做携程）

| | 携程 | 小红书 |
| --- | --- | --- |
| 登录态 | **已经 per-user**：`travel_site_login` 主键 `(user_id, site)` + Phase 19 每用户独立 Chrome profile | **单个运维账号**：`/home/ubuntu/xhs-mcp-data/cookies.json`，无 user_id 维度 |
| 做成可连接 | 基本是把既有状态**暴露到界面** | 要换掉第三方 MCP 镜像（写死单 cookie 文件），per-user 需每人一个内置 Chrome 的容器 |
| 用户价值 | 看**属于自己**的订单/会员价，必须是本人的号 | 只为过风控读公开笔记，不涉个人数据 |

**小红书本期不做成"用户可连接"**，并且这不是排期问题，是 Phase 68 已做过的决策：

> 小红书不做租户隔离——登录只为过风控读公开笔记，隔离无正确性收益；反而会把写操作
> 风险和封号风险转嫁到用户真实社交账号。

那个 MCP 除搜索/详情外还暴露 `publish_content`/`post_comment_to_feed`/`like_feed`，
现在靠 `xhs_mcp._call_tool` 的只读白名单硬挡。让用户绑自己的号 = 把这个风险从运维账号
转到用户的真实社交账号，方向更坏。**页面上如实标注它是平台内置的公共账号读公开内容。**

## 四、数据与接口

不新增表。`travel_site_login` 已有 `(user_id, site, logged_in_at)`。

连接器清单是**后端常量**（`app/agent/connectors.py`，新增），不入库——它随代码走，
不是用户数据。每项声明：

```python
Connector(
    key="ctrip", name="携程", kind="login",     # login=需用户扫码 / builtin=平台内置
    provides=["酒店价格", "房态", "酒店图片"],
    excludes=["你的订单", "支付与账户", "会员权益"],   # 抄 Trip.com 那个写法
)
```

`excludes` 这一栏是有意加的：现在用户问"我的携程订单"才发现做不到。
Trip.com 的连接器把这条写在描述第一屏（"不提供 Trip.com 预订、账户、支付或订单管理接口"），
值得照抄。

**接口**（`app/api/connectors_api.py`，新增，全部 `get_current_user`）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/connectors` | 清单 + 本用户状态（`connected` / `connected_at`） |
| DELETE | `/api/connectors/{key}` | 断开（见下节） |

`connected` 的判据：`travel_site_login` 有该 `(user_id, site)` 行。
⚠️ `site_login_ttl_min` **在池模式下是死代码**（`_expire_stale_logins` 提前返回，
Phase 68 已订正），所以**不要**用它算过期，否则页面会显示一个系统根本不执行的过期时间。
实际寿命 ≈ 站点 cookie（携程约 13 个月）。页面只显示"上次连接于 X"，不承诺有效期。

## 五、断开必须真的断开，否则界面在说谎

**这是本期唯一有技术难度的地方。** 池模式下 cookie 在磁盘 profile 里
（`browser_pool._default_launch` 的 `--user-data-dir={profile_dir}`），
而**当前代码里没有任何清 cookie 的路径**——`_expire_stale_logins` 在池模式下直接返回。

只删 `travel_site_login` 那行是**纯装饰**：`site_router` 不看这行，它是导航过去看页面
有没有登录墙。profile 里的 cookie 还在 → 下轮照样自动登录 → **界面说"已断开"而系统仍以
该用户身份登录着**。这比不做这个功能更糟。

三个方案：

| 方案 | 结论 |
| --- | --- |
| `evaluate_script` 清 `document.cookie` | ❌ **否掉**。携程会话 cookie 必然是 HttpOnly，JS 碰不到。会"成功执行但没生效"，正是会说谎的那类实现 |
| navigate 到站点登出 URL | 🔸 精确，但依赖站点不改路径，且失败无从察觉。留作后续精细化 |
| `pool.restart(user_id)` + 删 profile 目录 | ✅ **本期采用**。一定有效，代价是清掉该用户**所有**站点登录 |

采用方案三，但**文案必须诚实**：按钮写「断开并清除浏览器登录态」，二次确认里说明
"会同时清除该浏览器上的其他站点登录"。**宁可功能粗一点，不可界面说谎。**

实现要点：先 `pool.restart(user_id)` 杀进程（profile 被占用时删不掉），再 `shutil.rmtree`
profile 目录，最后删 `travel_site_login` 行。**顺序不能反**。

## 七、独立扫码连接：一条被我算错的账

最初的判断是「从设置页扫码会占住浏览器池一个槽，而 `BROWSER_POOL_MAX=2`，所以先不做」。
**这个判断是错的**，因为它只算了新方案的成本，没算现状的成本。

查证：`handoff_wait_s = 180`，而等待循环 `_wait_login(target, browser, ...)` 拿的正是
`collect_sources` 里 `async with ChromeMCP(...)` 建出来的 browser。**整个等待期间槽位
一直被占着**，而且前后还挂着整轮采集：

```
现状：acquire → 导航携程 → 命中登录墙 → 等扫码(≤180s) → 重开页 → 抓取
      → 继续必应搜索 + 最多 8 个页面 → release
      占槽 = 采集全程 + 最多 180s

独立：acquire → 导航登录页 → 等扫码(≤180s) → release
      占槽 = 最多 180s，没有别的
```

| | 现状（登录夹在轮次里） | 独立连接 |
| --- | --- | --- |
| 单次占槽 | 采集全程 **+** ≤180s | **只有** ≤180s |
| 之后的轮次 | 每次都可能再撞登录墙 | 已连接 → 不撞墙，轮次更短 |
| 用户走神 | 照样占 180s，**还连带堵着那一轮的采集** | 只占 180s |
| 超时能不能砍 | 不能，砍了整轮就废 | **能**，失败让用户重试即可 |

**所以把登录挪出轮次是在减轻池压力，不是增加。** 独立流程的超时定
`connect_wait_s = 90`（比 180 短一半，反正可重试）。

还有一层更重要的收益：Phase 71 的结论是「长任务流失的原因不是久，是不知道还要多久 +
静默空隙」，而登录墙恰好在用户等攻略时制造一个 **3 分钟的空隙**。挪走它是直接消除
一个已知的最差体验点。

**剩下的三个是实现细节，不是阻碍**：

1. **同用户互斥**：防同一用户开多个连接会话把自己的槽位耗光。模块级
   `dict[user_id] -> session`，已有会话就返回它而不是新建。
2. **超时后清理**：会话结束（成功/超时/取消）必须删截图文件 + 释放浏览器。
   照 Phase 5 的做法（等待结束删截图）。
3. **失败要有明确反馈**：轮次里失败会静默回退必应；独立流程失败必须告诉用户
   「没连上，可重试」，否则用户不知道发生了什么。
