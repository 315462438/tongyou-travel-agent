# 抽取链路改用协议层思考控制（reasoning_effort）— 2026-08-24

## 背景

DeepSeek 思考模式对**结构化抽取**任务过度推理，我们已经撞过四次：

| Phase | 现场 | 当时的治法 |
| --- | --- | --- |
| 11 | ITINERARY 思考链 1.5 万字吃满 16000 预算 | system 里写「思考两三行要点」 |
| 101 | quick_take 三次里两次 `out=0 / reason=1000`，只能把模型独白当正文给用户 | 思考纪律 + max_tokens 1000→1600 |
| 102 | 导入行程板分块抽取烧 **13124 思考 token / 118.6s**，正文仅 971 | 抽 `EXTRACT_THINKING_DISCIPLINE` 常量挂到五个抽取 system |
| 105 | 视觉输入下 prompt **已经写了**思考纪律照样烧满预算 | 强制 `response_format=json_object`（延迟中位 23.7s→7.4s） |

Phase 105 自己写下的结论是：**「能用协议层约束（response_format/schema）的地方就别写规矩；
加预算不是治法。」** 但当时手上的协议手段只有 `response_format`——它是「约束输出格式」，
顺带刹住了思考，属于**借力**而非对症。

2026-08-24 拉取 `deepseek-ai/deepseek-harness` 上游（854 commits，8-13→8-21）时发现
`226600147e feat(llm-deepseek): support low reasoning effort`：DeepSeek API 有**直接控制
思考档位的协议字段**，而我们全仓 `grep reasoning_effort` 是 **0 处**。

## 上游读到的协议细节（`packages/llm/llm-deepseek/src/serialize.ts`）

两个**顶层**字段（不是 `extra_body` 的嵌套键，是 wire JSON 的顶层）：

```
thinking:          { type: 'enabled' | 'disabled' }
reasoning_effort:  'low' | 'high' | 'max'
```

映射规则（`resolveThinking`）——**`off` 不是一个 wire 档位**：

| 语义档位 | 实际发出的请求体 |
| --- | --- |
| `off` | `{"thinking": {"type": "disabled"}}`，**不带** `reasoning_effort` |
| `low` / `high` / `max` | `{"thinking": {"type": "enabled"}, "reasoning_effort": "<档位>"}` |

Python SDK 侧（openai 2.44.0）实测：`reasoning_effort` 是 SDK 已知参数可直接传；
`thinking` 不是，必须走 `extra_body={"thinking": {...}}`（SDK 会把 extra_body 的键
合并到请求体顶层，正好满足「顶层字段」的要求）。

## 目标

把抽取类调用的思考档位从「prompt 里劝」改成「协议层定」，并且**可度量、可回退**。

非目标：不动生成类调用（攻略正文/直答/深度研究）的思考档位——那些任务的思考链是产品的一部分
（前端「已深度思考」折叠面板），且 Phase 11 的纪律已经把它压到合理长度。

## 最大的未知（所以排在第一步）

**真实 API 认不认这两个字段、对我们这三个模型认不认**，这决定方案形态：

- 若 400 拒绝未知字段 → 整个方案作废，回到 prompt 纪律；
- 若静默忽略 → 会拿到「改了但没效果」的假成功，**必须用 usage 的 reasoning token 数验证**，
  不能只看 HTTP 200；
- 若生效 → 才谈默认档位怎么定。

⚠️ **本机连不上 `api.deepseek.com`，探测必须在服务器上跑**（CLAUDE.md 已记）。

## 方案

### 第 1 步：协议探测（服务器）

一次性脚本 `backend/scripts/probe_reasoning_effort.py`（不进主代码路径），对
`deepseek-v4-pro` / `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` 三个模型，
用**同一个真实抽取 prompt**跑 4 组：基线（不带字段）/ `off` / `low` / `high`，记录：

- HTTP 是否成功、是否报未知参数；
- `usage.completion_tokens_details.reasoning_tokens`（**判定生效与否的唯一硬证据**）；
- 端到端延迟、正文 token 数、JSON 是否合法。

### 第 2 步：落地到 `LLMClient`

- `client.py` 新增内部函数 `_thinking_kwargs(effort)`，把语义档位翻译成上面那张表的请求字段
  （**这段翻译逻辑必须单独可测**：`off` 不得出现在 `reasoning_effort` 里，这是最容易写错的一格）；
- `parse()` / `classify()` / `parse_image()` / `generate*()` 增加 `effort` 参数；
- 抽取类调用点默认档位由新配置项 `extract_reasoning_effort` 决定，默认值**待第 1 步数据定**；
- 配置项支持 `none` 表示「完全不发这两个字段」= 行为与改造前逐字节相同（回退开关）。

### 第 3 步：对照评估（服务器）

用现成的 `evals/extract_eval`（5 篇固定攻略、只调 `build_trip_object` 一步，
天数 3/3/5/7/10 覆盖单次与分块两条路径）跑 `--tag before/after` 对照，看
**准确率不掉 + 耗时降**。这是现成的度量口径，不新造。

## 涉及模块

| 文件 | 改动 |
| --- | --- |
| `backend/app/llm/client.py` | `_thinking_kwargs()` + 各方法的 `effort` 参数 |
| `backend/app/config.py` | `extract_reasoning_effort` 配置项 |
| `backend/app/ontology/extract.py`、`poster.py`、`budget.py`、`api/trip_api.py` | 抽取调用点传档位 |
| `backend/scripts/probe_reasoning_effort.py` | 一次性探测脚本 |
| `backend/tests/test_reasoning_effort.py` | 翻译逻辑与调用点的回归测试 |

## 验收标准

1. 探测脚本在服务器上跑通，且**用 reasoning_tokens 证明档位真的生效**（不是 HTTP 200 就算数）；
2. `_thinking_kwargs` 的四个档位映射有单测钉死，尤其 `off` 不出现在 `reasoning_effort`；
3. 配置项设为 `none` 时请求体与改造前**逐字段相同**（有测试断言不含这两个字段）；
4. `extract_eval` 前后对照：准确率不下降，耗时下降；
5. 全部后端单测通过。

## 风险与预案

- **API 静默忽略未知字段** → 第 1 步就能识别（reasoning_tokens 不变），届时方案退回 prompt 纪律，
  并把「探测发现它不生效」写成踩坑文档，避免以后有人再试一遍。
- **`off` 让抽取质量下降**（有些抽取确实需要一点推理，如把「两人合计 600」换算人均） →
  这正是 `extract_eval` 的 `ext_headcount`/`ext_total_as_item` 检查项覆盖的场景，
  对照跑不过就退到 `low` 而不是 `off`。
- **视觉模型不支持该字段** → 视觉链路单独保留 `json_object` 那条已验证的路径，不强行统一。

## 执行结果

### 第 1 步：协议探测 —— 三个模型均确认生效

服务器实测（同一段抽取 prompt，`max_tokens=3000`，每格 3 次取中位）：

| 模型 | 档位 | 延迟 | 思考 token | 正文 token | 合法 JSON |
| --- | --- | --- | --- | --- | --- |
| v4-pro | 基线 | 55.2s | 3000（吃满） | 3000 | **0/3** |
| v4-pro | `off` | **4.4s** | 0 | 464 | **3/3** |
| v4-pro | `low` | 30.4s | 1455 | 1870 | 3/3 |
| v4-pro | `high` | 54.0s | 3000 | 3000 | 0/3 |
| v4-flash | 基线 | 23.6s | 2942 | 2998 | 1/3 |
| v4-flash | `off` | **2.3s** | 0 | 400 | **3/3** |
| v4-flash | `low` | 19.7s | 2360 | 2746 | 3/3 |
| vision-exp | 基线 | 27.2s | 2999 | 2999 | 1/3 |
| vision-exp | `off` | **3.1s** | 0 | 335 | **3/3** |
| vision-exp | `low` | 15.5s | 1458 | 1730 | 3/3 |

两个高于预期的发现：

1. **基线那行不只是慢——它是错的。** 思考链吃满 3000 预算把正文挤掉，JSON 三次全不合法。
   `off` 在这个场景是**从错到对**，不是单纯提速。这正是 Phase 102 那个失败模式的完整复现。
2. **`high` 与基线一致，因为 `high` 就是默认档**，不是「字段被忽略」。探测脚本第一版的判据
   （「与基线相同 → 很可能被静默忽略」）在这里误报了——见
   `docs/pitfalls/用与基线相同来判定字段未生效会误报默认档.md`，脚本判据已修。

### 第 2 步：落地 —— 作用域比计划时收窄了

计划原本写「抽取类调用点默认档位由配置决定」，实现时**没有**把默认放在 `parse()` 里，
原因是探测数据让 `off` 变成了一个很激进的档位（思考完全关闭）：

- `parse()` 是结构化输出的边界，但**结构化 ≠ 机械**——需求解析（`orchestrator`）、
  自检 critique（`nodes`/`poster`）、记忆增删（`memory`）同样走 `parse()`，
  它们的质量**依赖**推理；
- 全局默认还有一个长期问题：将来任何新增的 `parse()` 调用会**静默**继承一个它未必该有的档位。

所以改为**调用点显式 opt-in**，范围与 Phase 102 给 `EXTRACT_THINKING_DISCIPLINE`
圈定的完全一致，共 6 处：`ontology/extract`(1)、`budget`(1)、`poster` 主抽取+补点(2)、
`trip_api` 导入摘要+分天(2)。**poster 的 critique 刻意不在其中**——那是自检，要的就是模型动脑子。

配置项：`extract_reasoning_effort`（默认 `off`）、`vision_reasoning_effort`（默认 `none`，
视觉侧缺对照数据，不跟着文本链路一起翻）。设成 `none` = 请求体与改造前逐字节相同。

### 单测

`backend/tests/test_reasoning_effort.py` **17 条全部通过**，含一条 AST 护栏钉住那 6 个调用点
（漏传 effort 是静默失效：功能照跑、日志干净，只是又变回长思考）。

⚠️ 顺带修了 5 个测试替身：`_FakeLLM.parse()` 的签名是写死的，给共享调用点加关键字参数
会让它们 `TypeError`（27 个用例同时红，全在 `test_ontology.py` / `test_trip_import.py`）。
已加 `**_kw`。**这次是响亮失败所以好查**；如果那些替身当初写的是 `**kwargs`，
测试会照常绿、而新参数一个字都没被断言到——这也正是要那条 AST 护栏的理由。

全量：`1332 passed`（另有 13 条因本机 DNS 把 `example.com` 解析到内网、`url_guard` 拒绝而
deselect，与本次改动无关，改动前后同样失败）。

### 第 3 步：抽取质量对照 —— 结论经历了两次反转

**第一版结论（错的）**：按「抽取就关思考」一刀切，`extract_eval` 5 篇 596.5s → 62.5s（9.5×），
闸门 5/5。但连跑三轮时抓到一次 `ext_headcount` 失败（马来西亚样本认成 1 人，正文是 2 人）。

**第二版结论（也是错的）**：换成机械/判断分档后，实测 557.9 / 550.8 / 555.6s——**只比基线快 7%**，
落在噪声里。原因是时间大头在 cost lane 与 ≤6 天的单次 itinerary，两者都被划进保守档。
随后针对海报路径量召回率，得到「off 会漏地点（召回 57.8% vs 基线 88.9%）」——
**这个结论是探针缺陷造成的假象**，见下。

**第三版（当前，有数据支撑）**：修正探针后重测 `build_trip_object`（真正受影响的那一层），
把 foods/lodgings/specialties 一起并入命名实体集合：

| 档位 | 中位耗时 | 实体数(均) | 召回率 | 稳定核心 | 人数 |
| --- | --- | --- | --- | --- | --- |
| none | 130.3s | 46.0 | 51.1% | 37 | 2/2/2 ✓ |
| low | 82.8s | 44.0 | 48.9% | 32 | 2/2/2 ✓ |
| **off** | **12.0s** | **58.0** | **64.4%** | **41** | 2/2/2 ✓ |

**`off` 抽得更多，不是更少。** 思考链关掉后整个 token 预算都留给正文；基线反而会被自己的
思考链挤爆输出（同一探针里 none 三轮有两轮 `8000 上限 JSON 截断`）。

⚠️ 前一版探针错在两点，都值得记住：
1. **测错了层**。本体架构下常规体验走 `ensure_trip_object` 缓存投影，海报/预算/导入
   命中缓存时**零 LLM 调用**；我测的 `_extract_poster_data` 是注释里写明的「回退路径」。
   真正受本次改动影响的只有**第一次抽取**。
2. **只数了 stops**。漏掉的那批全是餐馆茶馆（佩姐老火锅/鹤鸣茶社/陈锦茶铺…），
   它们只是被归进了 `foods`。**分类差异被读成了数据丢失，结论正好相反。**

### 第 4 步：人数单独兜底

`off` 唯一实测会失手的字段是人数（11 次 off 运行里错 1 次，认成 1 人）。它同时是整份抽取里
**最便宜**的一个数，而错了会顺着「金额一律人均口径」（Phase 67）把整个预算面板一起弄错且不报错。
代价不对称 → 单独一路：

- `HeadcountExtraction`（新 schema，只有一个字段）+ `_headcount()` lane，`max_tokens=200`，
  输入只给正文头 1500 字 + 尾 2500 字（人数信息基本都在行程概览或预算表里）；
- **永远走 `headcount_reasoning_effort`（默认 none）**，不跟提速旋钮；
- 与两条主路**并发**，不在关键路径上；只在跑 cost 路时才启用（不点预算面板就没有金额要配人数）；
- 合并用 `max()`——观测到的失手方向是**偏小**，max 天然防小；兜底路自己失败返回 1，对 max 中性。

### 第 5 步：抽空的路不许登记（本次最有价值的发现，且与档位无关）

连跑验证时抓到一次**严重**故障：重庆 5 天攻略抽出 **0 天 0 点**，而 `lanes` 仍登记成
`cost+itinerary` → 会被 `save_trip_object` 缓存，`source_hash` 不变就**永不重试**，
用户看到一个永远空白的行程板，重开也没用。

针对性重跑 8 次**未复现**（off 0/8 空），所以**不能归因给 `off`**——这是既有的架构缺口：
原来的 `done` 只排除抛异常的路，「调用成功、返回空数组」照样登记。

修法与既有决策的关系要说清楚：`test_empty_result_is_cached_to_avoid_rework` 编码了一条
有意的旧决策「抽不出东西的攻略也要记下来，否则每点一次按钮就白抽一遍」。本次是**细化不是推翻**
——判据从「抽出来是空的」改成「**攻略正文里本来就没东西可抽**」：

- 没有 Day 标题的正文抽不出地点 = 正常结果，**照旧缓存**；
- 有 Day 段落却抽出 0 点 = 故障，**不登记，下次重试**。

代价不对称：多抽一次是几秒几分钱，固化一次是这份攻略永久废掉。

### 最终配置

```
extract_reasoning_effort          = off    # 机械：逐日分块 / poster / IMPORT_DAYS
extract_judgment_reasoning_effort = off    # 判断：profile / cost / budget / IMPORT_SUMMARY
headcount_reasoning_effort        = none   # 人数兜底路，永不跟随提速旋钮
headcount_lane_enabled            = True
```
