# Phase 84 · 统一通知中心与社交提醒

日期：2026-08-11

## 目标

把顶部铃铛从单一公告提示升级为统一通知中心。好友申请、好友接受、接力获得反馈等社交事件应产生
真实、可持久化、按用户隔离的未读提醒；现有平台公告仍保留入口。

## 通知范围

- 收到好友申请：通知接收方，可直接进入好友申请列表；
- 好友申请被接受：通知原申请人，可进入对方主页/好友页；
- 接力获得“有用 / 我也到过·属实 / 已失效”：通知接力作者，可进入对应目的地接力站；
- 用户取消反馈：撤销尚存在的对应通知；切换反馈：更新同一条通知并重新标为未读；
- 自己的行为不产生自己的通知；拒绝好友申请不通知，避免负向打扰；
- 平台公告继续通过通知面板进入，不混进社交通知表。

## 数据模型

新增 `travel_notification`：

- `id`、`user_id`（接收者）、`actor_id`（触发者，可空）；
- `type`：friend_request / friend_accepted / relay_reaction；
- `title`、`body`、`target_kind`、`target_id`、`meta_json`；
- `dedupe_key` 唯一，用于好友关系或“同一用户对同一接力”的通知去重；
- `read_at`、`created_at`、`updated_at`。

通知是业务数据，使用现有 PostgreSQL 与账号鉴权，不使用 localStorage 作为真相来源。

## API

- `GET /api/notifications?limit=40`：返回当前用户通知与未读数；
- `GET /api/notifications/unread-count`：顶部铃铛低频轮询；
- `POST /api/notifications/{id}/read`：读取单条；
- `POST /api/notifications/read-all`：全部已读。

所有 API 必须登录，只能读取/修改当前用户自己的通知，响应字段白名单不暴露账号敏感信息。

## 前端方案

- 顶栏铃铛显示统一未读红点/数字，社交未读与现有公告未读合并；
- 点击铃铛打开轻量通知浮层：顶部“通知”与“全部已读”，下方为社交通知列表；
- 每条显示触发者头像、事件文案、相对时间和未读状态；
- 点击好友申请 → 打开 SocialHub 好友页；点击接力反馈 → 打开对应目的地；
- 面板底部保留“平台公告”入口及公告未读数；
- 移动端通知浮层占满可用宽度，不挡住底部导航。

## 验收标准

1. 好友申请、接受、接力反馈产生正确接收者通知；
2. 重复/切换反馈不堆积通知，取消反馈撤销通知；
3. 未读数跨刷新持久存在，单条/全部已读正确；
4. 不存在跨用户读取或修改通知的越权；
5. 铃铛同时提示社交和公告，点击通知能进入正确上下文；
6. 桌面与移动端可读，Escape/外部点击可关闭；
7. 后端全量、前端测试、lint 与生产构建通过后部署。
