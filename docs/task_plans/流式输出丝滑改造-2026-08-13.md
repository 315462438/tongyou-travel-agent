# 流式输出丝滑改造

- 日期：2026-08-13
- 目标：消除攻略/直答流式输出「一段一段跳」的观感，让正文连续平滑地流出
- 涉及模块：`backend/app/config.py`、`backend/app/agent/orchestrator.py`（后端节拍）、
  `frontend/src/pages/Home.tsx`、`frontend/src/interaction.ts`、`frontend/src/hooks/useTypewriter.ts`（前端渲染）

## 问题

当前流式链路是「后端定时落库 + 前端轮询整体替换」：

1. 后端 `_stream_into` / `run_direct_answer` 每 **1.2s** 才把增量写库一次；
2. 前端每 **1.5s** 轮询一次（`Home.tsx` `poll`），两个时钟叠加，最坏 ~2.7s 才看到一次跳变；
3. 每次轮询 `setMessages(data.messages)` **全量替换**消息数组，未变化的消息也整体重渲染，
   `GuideBody` 每次用 react-markdown 全量解析正文——长攻略下渲染本身卡顿，加剧「跳块」感；
4. 模型输出本身是「一段输出→停顿→再一段」的突发模式（DeepSeek 思考模式特性，不可改）。

结论：1-3 可改；第 4 点用前端打字机平滑缓冲抹平。

## 方案

### ① 后端 flush 节拍：1.2s → 0.5s（配置化）

- `config.py` 新增 `streaming_flush_interval_s: float = 0.5`；
- `orchestrator.py` 两处 `_time.monotonic() - last_flush > 1.2` 改用该配置；
- 单条 UPDATE 很轻（本地 PG），0.5s 粒度无压力；流式中 `_embed_images(streaming=True)`
  已有残片剥离，增量更频繁不引入新问题。

### ② 前端轮询：1500ms → 800ms

- `Home.tsx` `poll` 的 `setInterval` 间隔改 800ms；
- 单会话轮询仍是极轻请求，量级无压力。

### ③ 增量渲染 + memo 化

- `poll` 的 `setMessages` 改为**按 id 合并**：内容签名（role + content 长度/尾串 +
  reasoning 长度 + meta 长度）未变的消息**保持原对象引用**，只有变化的换新对象；
- `GuideBody` 用 `React.memo` 包裹（props 只有 `content`，引用相等即跳过 react-markdown 重解析）；
- 收益：未变化消息零重渲染开销，流式消息也只因 content 变化而重渲染。

### ④ 打字机平滑（核心）

- `interaction.ts` 新增纯函数 `typewriterStep`（可离线单测）：
  - 输入 `(shown, target, now)`，输出新的 `shown` 与是否完成；
  - **自适应速率**：积压（`target.length - shown`）越大播放越快（档位 1/2/4 字符每 tick），
    保证不落后于生成速度；无积压即完成；
  - `inactive`（流式终稿）时直接追平全量，零延迟收尾。
- 新 hook `frontend/src/hooks/useTypewriter.ts`：`useTypewriter(target, active)` 返回逐步
  揭示的文本；40ms tick；`document.hidden` 或用户已上滚阅读（不跟随底部）时不动画、直接给全量；
- `Message` 中流式消息的 `GuideBody content` 换用 hook 输出；`stream-cursor` 保留。

### 不做

- 不做 SSE（架构级改造，另立项）；不做后端逐 token 落库（DB 压力不值）。

## 验收标准

1. 轮询 800ms、flush 0.5s：正文可见粒度 ≤ ~1.3s（改造前 ~2.7s）；
2. 打字机播放连续、速率自适应、终稿瞬间追平；
3. 未变化消息不重渲染（memo 生效），长会话轮询无卡顿；
4. 全部既有测试通过（后端 pytest、前端 node --test）；
5. 新增 `typewriterStep` 纯函数单测覆盖：无积压即完成 / 积压加速 / 终稿追平。

## 追加：真实提速（2026-08-13 晚，服务器日志诊断后实施）

线上实测一轮 guide 耗时 6 分 52 秒（Langfuse trace 精确还原）：分类 7s + parse 6s +
**小红书详情串行 ~163s** + 必应 50s + **生成 200s（思考链 14878 字符吃满 16000 token 预算）** + 收尾 6s。

### ⑨ 小红书 × 必应并行采集（代码，已完成）

`collect_sources` 重构：未复用时 `asyncio.create_task(_collect_xhs(...))` 与浏览器
（必应 light + 携程路由）**同时跑**——两条通道独立（xhs=HTTP MCP、必应=ChromeMCP），
采集段从 ~213s 降到 ≈ max(xhs, 必应)。xhs 收成 0 篇时浏览器内补跑 full 第 2 查询。
hotel 意图 / 复用命中仍走原串行路径（行为不变）。

### ⑩ 生成思考精炼（代码，已完成）

`ITINERARY_SYSTEM` / `HOTEL_SYSTEM` 追加「思考纪律」：思考两三行要点即可，把输出预算
留给正文。目标：思考链 1.5 万字 → 2-3 千字，生成 200s → ~120-140s。

### ⑪ quick take 空 content 修复（代码，已完成）

线上 trace 发现 quick take 的 LLM 调用执行了但**没落 preliminary 消息**——DeepSeek
思考模式在 max_tokens=400 下 token 全花在思考链、content 为空。修复：max_tokens 400→1000
+ content 空时用 reasoning 前 200 字兜底（guide 与 deep_research 两处同修）。

### ⑫ 服务器配置（.env，已实施）

`XHS_NOTES_PER_TURN=3`（详情 5→3 篇，省 ~40s）、`XHS_REUSE_MAX_DAYS=14`（复用窗口
7→14 天，命中即省全部小红书详情 ~120s）。

## 追加：故障韧性修复（2026-08-14 凌晨，线上事故）

用户报告：xhs MCP 垮了之后 agent "无限死循环"、停止按钮无反应。日志实证根因四层
（详见 `docs/pitfalls/小红书MCP故障触发LangGraph重试与停止失效.md`）：

### ⑬ 五处修复

| # | 改动 | 效果 |
| --- | --- | --- |
| ① | collect_sources 浏览器块消化所有非取消异常，绝不冒进 LangGraph 默认重试 | 故障轮次 ~1 分钟内正常终止（apologize），不再 10 分钟转圈 |
| ② | `_ensure_stopped_message(cid, text)` 参数化，异常 failed 路径同样终稿残留 streaming 占位 | 前端不再"无限运行中"，停止/失败都有明确收尾 |
| ③ | `await xhs_task` → `wait_cancellable`；`_collect_xhs` 每查询加取消检查点 | xhs 等待期间停止立即生效 |
| ④ | xhs_mcp 连续 2 次详情失败熔断 break | MCP 垮时不再 5×40s 逐篇等超时 |
| ⑤ | BrowserPool.acquire 支持 cancel_check（排队循环内检查），ChromeMCP 透传 | 浏览器排队 120s 期间停止也立即生效 |

测试：熔断只读 2 篇 / cancel_check 排队立即中止且池状态不坏 / 失败文案终稿全分支。
全量 932 passed / 6 环境性失败。已部署（01:1x）。
