# 长截图视觉读取修复（Phase 111）— 2026-08-27

## 现象

用户上传一张行程长截图 + 一段有具体诉求的话（「分析一下这个图片我的行程，现在每天的
晚饭还没定，帮我确定下周边有什么好吃的，以及小吃等等，还需要看看我规划的路线是否合适？
有没有什么特别要注意的？」），助手回：

> 请问您这次行程的目的地是哪里？方便告诉我具体城市或景点吗？

用户连试两次，两次都一样。用户的判断是「逻辑限定得太死板」。

## 根因：不是死板，是硬失败

线上日志里每一次带图的对话都有：

```
vision user image failed id=1e15946939014d068733825b686c7c54
openai.BadRequestError: Error code: 400 -
  '.messages[1].image[0]: You have uploaded an unsupported image.
   Please make sure your image is valid and has one of the following formats:
   webp, png, jpeg, and gif.'
```

那张图是 `image/png`，格式明明在白名单里。真正越界的是**尺寸**：

| 尺寸 | 字节 | 结果 |
| --- | --- | --- |
| 1800 × 25242（原图） | 3873KB | FAIL |
| 1024 × 14360（整图等比缩到宽 1024） | 1207KB | FAIL |
| 1800 × 1800 | 232KB | OK |
| 1800 × 6000 | 689KB | OK |
| 1800 × 8000 | 915KB | OK |
| **1800 × 8192** | 941KB | **OK** |
| **1800 × 8500** | 988KB | **FAIL** |
| 1800 × 9000 | 1046KB | FAIL |

结论：**上限是单边 8192 px**。

三个排除项同样重要，因为它们决定了修法：
- **不是文件大小**——941KB 过、988KB 挂，而 1207KB 与 1046KB 同样挂；三档字节数交错，
  字节不是判据。
- **不是宽高比**——1024×14360 的比例比原图更极端却也只是同样挂在高度上；
  把宽压下去一点用没有。
- **不是格式**——报文里那句 "unsupported image / 请确认格式" 是**误导**：格式白名单
  它自己就列着 png。照着报文去查格式会一路走错。

于是链路是：视觉 400 → `describe_user_images` 吞掉异常返回空串 → `user_text` 里一个字
都没多 → `Preference.destination` 为空 → Phase 68 的澄清闸门触发 → 反问目的地。
**用户看到的「死板」是一次静默的硬失败，不是设计取舍。**

## 为什么不能靠「等比缩小」

25242 缩到 8192 是 0.32 倍，行程单上的文字直接糊掉，抽出来的东西不可信。
长截图必须**切片**，不能整体缩。

## 方案

### 1. 新增 `app/agent/image_prep.py`

`prepare_for_vision(data, mime) -> list[str]`：原始字节 → 一组按上下顺序排列、每张都
在规格内的 data URI。

- 在规格内（两边都 ≤ `vision_max_image_side`）→ **原样返回，不重编码**。
  不做无谓的有损转码，也不浪费 CPU。
- 太宽 → 等比缩到宽度合规（横向没有「切片」的语义，网页截图也几乎不会超宽）。
- 太高 → 按高度切片，相邻片**重叠 `vision_tile_overlap_px`**，
  避免正好卡在切口上的那行字两片都不完整。
- 需要的片数超过 `vision_max_tiles` → **先等比缩小，再切片**，让整页都被覆盖。
  ⚠️ 这里刻意不选「切前 N 片、剩下丢掉」：那会让模型拿着半份行程自信地描述，
  8 天行程说成 5 天，而且不报错。**静默的部分读取比读不出来更糟。**

### 2. 切片走**一次**调用，不是 N 次

`parse_image` 本来就收 `images: list[str]`。实测 4 片一次调用 21.5s，
完整读出了 8 天行程（南京→吉隆坡→仙本那→亚庇）。分成 N 次调用要付 N 份 prompt，
还会把同一份文档的上下文割裂开——第 3 天的「续住」在片 2、酒店名在片 1。

切片时 prompt 要**明说这是同一张长图的上下切片**，否则模型会当成几张互不相干的图。

### 3. 失败必须让用户看见

现在 `describe_user_images` 的每一处失败都是 `logger.warning` + 返回空串，
对用户完全隐形——而前面刚播过一条「正在看你发的 1 张图…」。
**进度条说读了，实际没读**，用户只能理解成「它很蠢」。

改为：带了图但一个字都没读出来时，落一条带 meta 的 progress 说明读不了，
请用文字补充关键信息。带 meta 才不会被 `clear_plain_progress` 清掉。

### 4. 依赖

新增 **Pillow**。切片必须解码，stdlib 没有图像编解码器。
（服务器上有 ffmpeg，但那是未声明的系统依赖，且要对用户上传的文件起子进程，面更大。）

内存：1800×25242 解码约 180MB。服务器 `available 4.3G` + 10G swap，可接受；
Pillow 自带的 decompression bomb 保护（~178M 像素）保留不动。

## 涉及模块

| 文件 | 改动 |
| --- | --- |
| `app/agent/image_prep.py` | 新增：规格化 + 切片 |
| `app/agent/vision.py` | `describe_user_images` 走规格化；切片时换 prompt；`judge_page_image` 同样过一遍 |
| `app/agent/orchestrator.py` | 读不出图时落一条可见的 progress |
| `app/config.py` | 4 个新配置项 |
| `backend/requirements.txt` | Pillow |

## 验收标准

1. 1800×25242 的行程长截图能被读出目的地与逐日安排，且**天数与原图一致**（不缺尾部）。
2. 规格内的普通图**不被重编码**（字节与输入一致）。
3. 需要的片数超过上限时，覆盖的是**整页**而不是前几片。
4. 视觉读不出来时，用户看得到一条说明，而不是一个无视图片的反问。
5. 单边上限、重叠、片数上限都可配置；`VISION_ENABLED=false` 时行为与改造前一致。

## 不做

- **不在前端压缩后再上传**：约束属于视觉 API，不属于上传。前端压了，别的客户端
  （或将来的 API 调用方）传原图照样挂；而且聊天气泡里显示的就是存下来的这张，
  为了迁就模型去损伤用户看到的图，方向反了。
- **不给小红书笔记图做规格化**：那条路传的是 xhs 的 http URL，我们不下载字节，
  也无从切片；而笔记配图是正常照片，从未撞过这个上限。
- **不动澄清闸门**：这一例的「死板」由视觉失败完全解释。闸门本身是否该更灵活
  （用户明明问了四个具体问题，只回了一个反问）是另一个问题，单独判断。

## 追加（同日）：反问要对得上原因，且不许重复

用户看完第一版修复后指出：

> 这个的回复应该注意，比如图片读不了，目的地获取不到，而不是一直反问同一个问题

复查发现两个**独立于视觉**的缺陷，都在澄清这条路上。

### 缺陷一：追问熔断从来没生效过

`_recent_clarify_rounds` 用「≤60 字且问号结尾」认自己发过的反问，而线上那句是

> 请问您这次行程的目的地是哪里？方便告诉我具体城市或景点吗？我好帮您推荐周边美食和检查路线。

句尾是「。」、长度也过了 60 → 判为「不是追问」→ 计数恒为 0 → `clarify_max_rounds`
永远够不着。**问 10 次也是第 0 轮。**

修法：发的时候写 `meta.clarify`，读的时候读它；文案启发式降级为只认改造前的老消息。
`_is_clarify_continuation` 与 `memory._first_guide_reply` 一并改用同一判据。
详见 `docs/pitfalls/别靠文案认出自己发过的消息.md`。

### 缺陷二：反问不看原因

目的地拿不到的原因不止一种，而措辞必须对得上原因。用户明明发了行程截图，
回一句「请问目的地是哪里」，在他看来就是没听见。

新增 `_image_unreadable_this_turn(cid)`（读 `_image_unreadable` 落的那条 progress 标记，
轮次边界与 `clear_plain_progress` 同一套），命中时走 `_BLIND_ASKS` 逐轮升级文案：

| 轮 | 说什么 | 给什么出路 |
| --- | --- | --- |
| 0 | 图没读出来 | 直接打城市名 |
| 1 | 还是没拿到 | ① 打城市名 ② 拆成单页重发 ③ 说「你定」 |
| ≥2 | **这轮不猜**，并说明为什么 | 一行城市名，或「你定」 |

### 一个刻意的例外：读不出图时**不代选**

Phase 68 的熔断是为「用户没想好去哪」设计的，那时替他挑是帮忙。
这里不一样——用户上传了行程截图，**我们有正面证据说明他手上有确定的目的地**，
只是我们没读出来。此时替他挑一个城市，是拿几分钟生成去产出一份必然不相干的行程。

代价不对称：再问一句是一次往返；猜错是整轮作废，而且用户会更确信「它没看我的图」。
所以 `forced` 加了 `and not blind`——**但用户明确说「你定」（`let_agent_decide`）
仍然照常代选**，那是他自己的授权，与我们读没读出图无关。

### 覆盖

`backend/tests/test_clarify_escalation.py`（14 条）。三处变异检验：
去掉任一处 `meta.clarify` → AST 护栏红；去掉 `and not blind` → 布尔形状用例红。
其中一条用例**直接用线上那句原文**做输入，不再造一句「像追问的话」——
原来的单测正是因为喂了教科书式的短问句才一直是绿的。
