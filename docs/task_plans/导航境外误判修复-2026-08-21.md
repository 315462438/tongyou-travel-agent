# 导航把整片东南亚判成「境内」— 修复计划（2026-08-21）

## 现象

马来西亚仙本那的酒店（DBC Hotel Semporna）点「🧭 导航」→ 打开**高德**，
高德没有该地数据 → 地图停在北京 + 「抱歉，服务超时」。

## 根因

Phase 100 的 `nav_links.out_of_china()` 用**单个经纬度矩形**判定境内外：

```python
return not (73.66 < lng < 135.05 and 3.86 < lat < 53.55)
```

纬度下界 **3.86°N** 把整片东南亚圈了进来。实测：

| 地点 | 坐标 | 判定 |
| --- | --- | --- |
| 仙本那（马来西亚） | 118.61, 4.48 | ❌ 境内 |
| 亚庇（马来西亚） | 116.07, 5.98 | ❌ 境内 |
| 曼谷 | 100.50, 13.75 | ❌ 境内 |
| 河内 | 105.85, 21.03 | ❌ 境内 |
| 马尼拉 | 120.98, 14.60 | ❌ 境内 |
| 吉隆坡 | 101.69, 3.14 | ✅ 境外（纬度刚好低于 3.86） |
| 新加坡 | 103.82, 1.35 | ✅ 境外 |

**同一个行程里吉隆坡判对、亚庇/仙本那判错**——因为分界线恰好从中间穿过。

## 两个后果（同一个根因）

1. **选错地图**（用户报的这个）：`domestic=True` → 前端开高德 → 境外数据弱 → 空白/超时。
2. **坐标被错误偏移**（潜伏）：`gcj_to_wgs84` 对「境内」坐标做 GCJ→WGS 反解。海外坐标本就是
   WGS-84（Phase 62：海外走 Open-Meteo/GeoNames/Photon），再减一次偏移 = 凭空偏移约 **380m**。
   仙本那实测 `118.61,4.48` → 苹果链接给的是 `4.481449,118.606570`。

## 讽刺的是：仓库里早就写着不能这么用

`app/tools/geocode.py:166` 的 `coordinates_probably_overseas` 用的是同类矩形，
但它的 docstring 明写：

> 粗边界**只用于决定是否调用国内路径 API，不用于判定坐标正确性**。

Phase 100 恰恰拿粗边界做了需要正确性的判断。

## 方案：换成简化国界多边形 + 射线法

矩形从根本上做不到——河内(21.03N,105.85E) 与南宁(22.8N,108.3E) 靠得太近，
任何轴对齐矩形都无法把越南北部与云南/广西分开。

用**简化的中国国界多边形**（几十个顶点，纯常量、零依赖、零网络）+ 标准射线法判点。
边界处几公里误差无所谓——比现在 1000+ 公里的误差好得多。

- 主多边形：大陆（含港澳沿海）
- 补充框：海南岛、台湾（高德对两地都有数据）

## 误判方向的代价不对称——要往「境外」偏

原实现的注释写反了。真实代价：

| 误判 | 后果 |
| --- | --- |
| 境外→境内 | 开高德，**没有数据**，用户看到北京+超时。就是本 bug |
| 境内→境外 | 开苹果地图。苹果在中国大陆用的正是高德数据，**仍然可用** |

所以边界拿不准时应当判**境外**，多边形宁可收紧不要放宽。

## 验收

`tests/test_nav_links.py` 增加**跨境城市对照表**：每条陆地边界两侧各取真实城市，
断言分类正确。重点覆盖矩形做不到的中越/中老/中缅/中泰边境带。

## 刻意不做（本次）

**不加 `travel_trip_stop.country_code` 列**。坐标系与国别本该是数据的属性、在地理编码时
就该落库（`GeocodeContext.country_code` 那时是拿得到的），事后从坐标反猜是二等做法。
但 `stop.location` 有 **8 处写入点**，逐个透传 country 改动面大、易漏；而多边形方案
零迁移、**对存量行程立即生效**（用户现在这个行程不用重新定位就好了）。
留作后续结构性改进，届时多边形降级为缺 country 时的兜底。
