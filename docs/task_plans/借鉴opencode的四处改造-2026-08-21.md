# 借鉴 opencode 的四处改造（2026-08-21）

扫描 `~/Desktop/opencode`（opencode 上游仓库，anomalyco/opencode，66.8 万行 TS）后挑出的
四处可移植设计。每一处都对着我们已有的一个具体缺口，不是「它有我们也来一个」。

## 背景：为什么是这四处

opencode 的 `core/session/*`、`core/tool/*`、`core/system-context/*` 有不少成熟设计，
但大部分我们已经有等价物（分段压缩 Phase 30/91、工具输出按结构裁剪 Phase 96、
重复调用守卫 Phase 89/95、外部内容走 tool 角色 Phase 31/69）。**刻意只挑我们真正缺的。**

明确**不做**的：**Context Epoch**（`core/system-context/index.ts`，把系统提示建模成
一组可独立刷新的 typed source，变更以「mid-conversation system message」追加而 baseline
永不改写，从而让 provider 前缀缓存永不失效）。设计很漂亮，但落地要给会话加 snapshot 列、
给每类记忆写 baseline/update/removed 三个渲染器、还要处理 `unavailable`（观测失败时保留
旧值而非当成"被删了"——这个区分最容易写错）。收益是省 token + 缓存命中，属优化；成本是
一套新状态机 + 迁移。**单独立项**，理由同 Phase 102 对「跨用户目的地缓存」的判断。

## 改造 ① 轮末压缩挪出关键路径（最小改动，先做）

### 现状

`update_history_summary()` 在三条链路的轮末各调一次，但**位置不一致**：

| 链路 | 位置 | 在终稿的哪一侧 |
| --- | --- | --- |
| guide | `finalize_guide()` `orchestrator.py:1470` | 终稿**之前** ❌ |
| direct | `run_direct_answer` `orchestrator.py:2115` | 终稿**之前** ❌ |
| research | `deep_research.py:222` | 终稿**之后** ✅ |

它是一次同步 v4-flash 调用（输入最多 60 条 × 300 字 + 旧摘要），实测量级 2-5 秒。
这几秒里流式消息还挂着 `meta.streaming=true`，前端还在轮询转圈，**而用户其实早就
把攻略读完了**。

### 判据：它和终稿没有数据依赖

`update_history_summary` 无返回值、不进 `meta`。同一位置的 `extract_and_save` **有**依赖
（`saved` 要进 `meta.memories_saved`），必须留在前面。

### 方案

guide / direct 两处把 `update_history_summary(cid)` 挪到 `_finalize_streaming_message(...)`
**之后**，与 research 链路对齐。不开线程（Phase 101 那次要开线程是因为 quick_take 挡在
**采集**前面、后面还有活要干；这里终稿已是本轮最后一步，挪位置即可）。

### 验收

- 终稿落库时 `update_history_summary` 尚未被调用（顺序断言）
- 压缩抛异常不影响终稿已落库这一事实

## 改造 ② 摘要提示词补两条纪律 + 标签分区

### 现状

`HISTORY_SUMMARY_SYSTEM`（`orchestrator.py:857`）的四小节模板本身是好的——
「已排除的选项（连同原因）」这一节 opencode 都没有，对旅行场景恰恰关键。

问题在 `:902`：

```python
if prior:
    listing = f"（此前的摘要）{prior[-1].content}\n\n{listing}"
```

旧摘要作为普通一行混进原文 listing，而 system 从头到尾没提过它的存在。模型不知道两件事：

1. **这份旧摘要马上要被丢弃**（`shadow_from = prior[-1].id`，下一轮 `derive_surface`
   就把它遮蔽了）→ 没被写进新摘要的信息，在模型视野里**永久消失**；
2. **旧摘要比下面的对话更老**，冲突时该以对话为准。

我们的压缩是「**增量范围 + 全量重写**」：范围上只折叠掉出近窗的早期消息（近 5 轮永远
逐字保留），但产物上每次都整篇重写去顶替旧摘要。正因为是全量重写，第 1 点才字面成立——
一个 20 轮会话里最早那条「忌口香菜」已经被逐轮重写过好几遍，每遍都是一次有损传递。

### 方案

抄 opencode `core/session/compaction.ts:38` 的 `SUMMARY_UPDATE_INSTRUCTIONS` 两句：

> The `<prior-summary>` is discarded after this: anything you do not carry into the new
> summary is lost.
> The `<conversation>` is more recent than the `<prior-summary>`. Where they conflict,
> the conversation wins.

落地为：
- `HISTORY_SUMMARY_SYSTEM` 末尾追加中文版两条纪律（仅在有旧摘要时才有意义，但常量静态
  更简单，且无旧摘要时该段是无害的空指令）；
- `listing` 拼装改为 `<prior-summary>…</prior-summary>` + `<conversation>…</conversation>`
  两块，取代裸的「（此前的摘要）」前缀。

### 验收

- 有旧摘要时两个标签都出现且内容归位
- 无旧摘要时不出现 `<prior-summary>`（不给模型一个空标签去脑补）
- 标签内容做属性/闭合转义（旧摘要正文若含 `</prior-summary>` 不得穿透，同 Phase 69 ④）

## 改造 ③ LLMClient 传输层重试（收益最大）

### 现状

```
grep -rn "tenacity|max_retries|APIError|RateLimit|APITimeout" app/   →  0 结果
```

`LLMClient.parse()` 里的 `for _ in range(2)` **只重试「JSON 校验失败」和「输出截断」**；
`generate_with_reasoning` / `stream_generate_with_reasoning` 一次都不重试，OpenAI client
也没设 `timeout`（默认 600s）。

一轮 guide 要打 6-10 次 DeepSeek（parse → quick_take → 流式生成 → critique → 记忆提炼
→ 历史摘要），**任何一次撞上 429/503/连接重置，整轮 4-6 分钟直接作废**——而 Phase 70/71
花大力气解决的正是「用户等太久会跑掉」。

它还悄悄打开了一个保真度漏洞：轮末压缩失败被 `except` 吞掉只记日志（`:930`），下一轮
装配走到 `_assemble_history:746` 发现超限且 `summary` 为空 → 回退读兼容字段 → 新会话里
它是空的 → `return msgs[-10:], ""`，**第 11 条往前的历史既没进摘要也没进窗口，静默消失**。
正常路径没有这个洞（时序是对的），它只在压缩失败时打开。

### 方案：移植 `opencode/src/session/retry.ts` 的判断，落成 `app/llm/retry.py`

纯函数模块（无 I/O，可离线单测）：

| 设计 | 来源 | 为什么要 |
| --- | --- | --- |
| `RETRYABLE_PATTERNS` 正则表 | `retry.ts:36` | SDK 的 `isRetryable` 常漏标，用**错误文本**兜底 |
| 5xx 一律重试 | `retry.ts:105` | 显式绕过 SDK 判断 |
| 优先 `Retry-After` / `retry-after-ms` 头 | `retry.ts:70` | 服务端说了等多久就等多久 |
| 指数退避 2s × 2^n + **25% 抖动**，无头时封顶 30s | `retry.ts:47` | 抖动防惊群 |
| 最多 5 次 | `retry.ts:53` | |
| **context overflow 永不重试** | `retry.ts:100` | 重试只会再超一次，纯浪费 |

我们这边**额外**必须有的两条（opencode 没有对应约束）：

1. **退避等待必须可被停止按钮打断**。裸 `time.sleep(30)` 会让停止在退避窗口里失灵。
   做法：切成 0.5s 片，每片查一次 `is_cancelled(cid)`。`cid` 由调用方按需传入，
   不传则退化为普通分片 sleep（行为不变）。
2. **流式只在「尚未吐出任何内容」时重试**。一旦已经 yield 过 delta，调用方
   （`_stream_into`）已经把它累进 `content_parts` 并落库了，重开一条流会重复输出。
   用 `produced` 标志守住。

顺带给 OpenAI client 加显式 `timeout`（现在是默认 600s，一个卡住的连接能吃掉整轮预算）。

### 刻意不做

- **不上 tenacity**：判断逻辑（读 header、认错误文本、区分 overflow）都要自定义，
  装饰器帮不上，反而多一个依赖。纯函数 + 一个 `for` 循环更好测。
- **不把重试状态推给前端**。opencode 的 `policy()` 每次退避前调 `opts.set({attempt, next})`
  让 UI 显示「12 秒后第 2/5 次重试」，跟 Phase 71「静默空隙才是流失原因」完全对味——
  但接进来要动 `_progress` 的调用链和前端渲染。**下一步做**，本次先把可靠性补上。

### 验收

- 各类错误的可重试判定（429/5xx/网络文本/超时文本 → 重试；4xx/校验错 → 不重试）
- context overflow 类错误**绝不**重试
- `Retry-After: 3` → 等 3s；`retry-after-ms: 1500` → 等 1.5s；无头 → 指数+抖动且 ≤30s
- 抖动落在 [base, base*1.25] 内
- 取消：退避期间标记 cid → 抛 `TurnCancelled`，且**不再发起下一次请求**
- 流式：首块之前失败 → 重试且输出完整；已吐过内容后失败 → 直接抛，**不重复输出**

## 改造 ④ 来源全文落库 + 多轮按需重取

### 现状

`_search_and_collect_queries` `orchestrator.py:1928`：

```python
sources.append({..., "summary": _excerpt(page.text)})   # limit=1500，page.text 随即丢弃
```

而多轮复用（`collect_sources` 的 `is_revision` 分支 `:1230`）复用的**就是这 1500 字**。
用户追问「第 3 家酒店的取消政策」，原页面其实有，但已经不在了——要么重爬（慢），
要么模型编（更糟）。

有意思的是**我们自己在深度研究链路已经解决了这个问题**：`research_tools.py:208` 的
`_stash_source` 把全文存进 `source_store`、只回摘要，配 `read_source(source_id, offset)`
按需取（`:270`）。opencode 是同一模式做到了全局（`core/tool-output-store.ts` 落盘 +
预览里带一句「full content saved to {path}」）。

**guide 链路缺的就是这一半。**

### 方案

新表 `travel_source_page`：

| 列 | 说明 |
| --- | --- |
| `id` | uuid |
| `conversation_id` | 按会话隔离（复用只发生在会话内） |
| `url` | 与 conversation_id 组成唯一键，重复抓取覆盖 |
| `title` | |
| `full_text` | 上限 `source_full_text_max_chars`(40000)，防 DB 膨胀 |
| `created_at` | |

- 采集时写入，`sources` dict 增加 `page_id` 字段；
- 复用分支调用新函数 `refresh_reused_summaries(cid, sources, user_text)`：
  对有 `page_id` 的来源，从全文按**本轮关键词**重新取窗口（命中处前后各取一段），
  取不到就退回已存的 `summary`；
- 每会话保留最近 `source_page_keep`(24) 条，超出剪枝。

### 关键取舍

- **不复用 `travel_page` 表**：那是 Phase 1 的 task 维度（`plan_id`/`task_id` 外键），
  塞会话来源要把两个外键都置空，语义混乱。新表更干净。
- **不做向量检索**：关键词窗口足够。量级是「一个会话几十个页面」，上向量库是杀鸡用牛刀
  （同 Phase 4 对记忆检索的判断）。
- **重取是幂等的纯函数**：`focus_excerpt(full_text, keywords, limit)` 不依赖调用上下文之外
  的状态，可离线测。这条是 Phase 96 的教训——相关性裁剪会破坏幂等，所以**只在复用路径**
  用它，采集期仍是无关键词的 `_excerpt`（保持 Phase 96 的结构化裁剪不变）。
- **新表靠 `create_all` 建，但仍在 `migrate.py` 里显式建一次**：`create_all` 只建缺失的表、
  不给已有表加列（`docs/pitfalls/create_all只建表不加列.md`）。本次是纯新增表，
  create_all 够用；显式写一份是为了后续加列时有地方落。

### 验收

- 采集后全文入库，`sources` 带 `page_id`
- 复用轮：关键词命中 → 摘录窗口包含命中段且长度受控；未命中 → 退回原 summary
- 无 `page_id` 的老来源（存量消息）走原路径不炸
- 全文超上限被截断入库；每会话超 `source_page_keep` 触发剪枝
- `focus_excerpt` 幂等：对同一输入两次调用结果一致
