# 重复调用守卫按调用方分链（Phase 95）

2026-08-18

## 背景

Phase 89 从 dsh（DeepSeek Harness）移植了「连续重复工具调用守卫」
（`app/agent/repeat_guard.py`）：同一个工具连续用完全相同的参数被调用达到阈值时，
在工具返回值后追加一段升级式提醒，建议模型换思路或收敛出稿。**只提醒不阻断**。

移植时留了一处已知差异，写在模块 docstring 里：

> dsh 用 `WeakMap<Agent, Chain>` 按**活的 agent 对象**分链，一个 agent 的重复不会
> 触发另一个的提醒。本项目的工具闭包是**主 agent 与全部 subagent 共享**的，
> 拿不到调用方身份，所以并发子代理调同一个工具同一参数时会误判成重复。
>
> 代价可接受：提醒是**建议性**的，误报的成本只是多一句无害的提示；
> 阈值相应放宽（3/6/10 而非 dsh 的 3/5/8）以降低并发误报。

现在要把这个差异补上。

## 为什么值得做（对「误报无害」的修正）

原判断是「误报只是多一句无害的提示」。复核后认为这个判断偏乐观：

误报注入的是一句**事实错误**的系统提示——「你已经连续 3 次用完全相同的参数调用
`amap_city_brief`」，而该子代理其实是**第一次**调。模型没有能力核对这句话的真伪
（它看不到别的子代理的调用记录），只能采信。后果是它可能放弃一次完全合法的首次查询，
或提前收敛出稿。这不是「多一句话」，是**降低产出质量**。

同时复核也**缩小了**问题的实际影响面。`research_tools.build_tools` 的两组工具是不相交的：

```python
main_tools = [web_search, open_page, read_source]
sub_tools  = [amap_city_brief, amap_poi, fetch_url, read_source, xhs_search, xhs_detail]
```

唯一重叠的 `read_source` 恰好在 `exclude` 里。所以模块 docstring 说的
「主 agent 与全部 subagent 互相干扰」**当前不会发生**。真实碰撞只剩一种：

> **并发的多个 `api-researcher` 用相同参数调 `amap_city_brief` / `amap_poi` /
> `fetch_url` / `xhs_search`。**

而 RESEARCH_SYSTEM 明确要求「一步里一次性发多个子任务」，几个子任务查同一个城市是常态，
所以这一种是实打实会发生的。

结论：做，但范围明确——**目标是把并发子代理彼此分开**，不是修一个泛泛的架构问题。

## 方案

### 身份从哪来（三条探针的实测结论）

不引入任何新依赖，用 LangChain 已有的 config 注入：工具函数多声明一个
`config: RunnableConfig` 参数，LangChain 在调用时注入，且**不会把它放进模型看到的
参数 schema**。三条探针（scratchpad，不入库）实测：

| 候选身份 | 同一子代理跨 superstep | 并发子代理之间 | 结论 |
| --- | --- | --- | --- |
| `config["callbacks"].parent_run_id` | **每步都变** | 不同 | ❌ 直接用会把一个子代理切成多条链 |
| `config["configurable"]["checkpoint_ns"]` 的**父链前缀** | **稳定** | **不同** | ✅ 采用 |

`parent_run_id` 要能用，必须顺 run 树往上找到派发它的那次 `task` run——也就是复用
`SubagentTracker._owning_run`，代价是让守卫耦合一个纯观测组件（tracker 失败时降级为
不显示面板，守卫却会跟着失去身份）。不采用。

`checkpoint_ns` 形如 `task:<uuid>|1|tools:<uuid>`，去掉最后一段 node 标识后的前缀，
就是「哪一次子代理调用」的稳定标识。主 agent 在顶层图，前缀恒为空串。

真实执行路径（`langgraph.prebuilt.ToolNode`，deepagents 子代理内部走的就是它）实测：

```
模型可见 schema： {'city': {'title': 'City', 'type': 'string'}}     ← config 不在里面
  杭州 | got_config=True | ns_prefix='task:9fc75de6-…'
  苏州 | got_config=True | ns_prefix='task:9fc75de6-…|1'            ← 并发两个子代理，前缀不同
```

### 不用 WeakMap

dsh 用 `WeakMap` 是因为它那张链表长生命周期，需要靠 agent 对象被 GC 来自动清理。
我们的 `RepeatGuard` 由 `build_tools` **每轮新建**、轮末整体丢弃，一个普通
`dict[str, _Chain]` 就够，不存在泄漏。照抄 `WeakKeyDictionary` 是把别人的约束搬进来。

仍加一个 `_MAX_OWNERS = 64` 的兜底上限（FIFO 淘汰最旧）——防止异常情况下 owner 键
无限增长。淘汰一个活跃 owner 的后果只是它的链清零，无害。

### 阈值改回 dsh 的 3/5/8

放宽到 3/6/10 的**唯一理由**是并发误报。该理由消失后放宽就变成了纯粹的迟钝，
改回 dsh 验证过的 `(3, 5, 8)`。

残留风险：若某条执行路径没有传 config，owner 一律为空串 → 退化成今天的共享单链，
此时更紧的阈值会比现在多一点误报。已用 ToolNode 集成测试钉住「真实路径确实传 config」，
接受该残留风险。

### 改动清单

**`app/agent/repeat_guard.py`**

- 抽出 `_Chain` dataclass（key / count / fired），`RepeatGuard` 持有
  `_chains: dict[str, _Chain]`。
- `check(tool_name, kwargs, owner="")` 增加 `owner` 参数，默认空串（= 主 agent /
  无 config），**向后兼容**：老调用方式行为不变。
- 新增 `owner_from_config(config) -> str`：从 config 取 `checkpoint_ns` 父链前缀，
  任何脏输入都返回空串，绝不抛。
- `reset()` 清空全部链。
- `DEFAULT_THRESHOLDS` 改回 `(3, 5, 8)`。
- `guard_tool` 的 wrapper 接受并吞掉 `config`（除非原函数自己声明了 config，则透传），
  用它算 owner；`config` **不进链键**。
- 重写模块 docstring 的「与 dsh 的差异」段。

**`app/agent/research_tools.py`**

- `build_tools` 末尾的注释同步更新（说明守卫已按调用方分链、配额仍是全轮共享——
  这是两件不同的事，配额共享是有意的预算设计）。

**`CLAUDE.md`**

- Phase 89 那条 `3/6/10` 的描述同步订正。

### 实现上必须避开的三个坑

这三处只要漏一个，功能就会**静默失效**（不报错、但守卫再也不触发或再也不准）：

1. **`functools.wraps` 会让 `inspect.signature` 跟随原函数签名**（它设了
   `__wrapped__`），wrapper 上新加的 `config` 参数不会被 LangChain 看见 → 注入失败
   → owner 恒为空串 → 退回共享单链，且**没有任何报错**。
   对策：显式构造并设置 `wrapper.__signature__`（追加 config 参数），同时 `del
   wrapper.__wrapped__` 消除歧义。

2. **`functools.wraps` 复制的是 `__annotations__` 的同一个 dict 对象**
   （`update_wrapper` 是 `setattr(wrapper, attr, getattr(wrapped, attr))`）。
   直接往 `wrapper.__annotations__` 里塞 `config` 会**污染原函数的注解**。
   对策：先 `wrapper.__annotations__ = dict(fn.__annotations__)` 再改。
   （必须设置注解而不只是 `__signature__`：LangChain 建 schema 时会读
   `get_type_hints`，只改签名不改注解在部分路径下识别不到 RunnableConfig。）

3. **`config` 必须从链键里剔除**。它每次调用都不同（含随机 uuid），一旦进了
   `canonical_key`，每次调用的键都不一样 → 链永远长不到阈值 → 守卫**完全失效**。
   对策：wrapper 先把 config 摘出来，再用剩下的参数调 `_named_args`。

## 验收标准

`docs/test_cases/重复调用守卫按调用方分链-验收用例.md`，全部落进
`backend/tests/test_dsh_ports.py`（现有 repeat guard 测试同文件）。核心必须钉住：

1. 两个 owner 用相同参数交替调用 → 各自独立计数，都不触发提醒
2. 同一 owner 跨 superstep（ns 尾段不同、前缀相同）→ 链不断，正常累积到阈值
3. `config` 不进链键（带不带 config、config 内容不同，都判为同一次重复）
4. `config` 不出现在 LangChain 推出的模型可见 schema 里
5. 包装不污染原函数的 `__annotations__`
6. 原函数自己声明了 `config` 时透传，不吞
7. `owner_from_config` 对 None / 非 dict / 非字符串 ns / 缺键 一律返回空串不抛
8. `reset()` 清空所有 owner 的链
9. owner 数超上限时不无限增长
10. **集成**：真实 `ToolNode` 路径下 config 确实注入，且并发两个子图 owner 不同
11. **真实工具集**：对 `build_tools` 产出的 9 个工具逐个校验（能转成 LangChain 工具、
    签名含 config、schema 不含 config、原参数顺序不变）——新增研究工具时会直接红
12. 原有 8 条 repeat guard 测试全部仍通过（其中签名断言一条需按新签名更新）

外加全量 `pytest tests/ -q` 无新增失败。

## 刻意不做

- **不改硬配额的共享语义**。配额（`used` dict）是**整轮预算**，全轮共享是有意设计，
  不是缺陷，不要顺手一起「修」。
- **不给主 agent 与 subagent 分别建两个 guard**。那个改法只有一行，但挡不住唯一真实
  的碰撞场景（并发子代理之间），属于看起来在解决问题。
- **不引入 `WeakKeyDictionary`**，理由见上。
- **不让守卫阻断调用**。准确率会随并发下降的信号不能拿来做拦截决策，Phase 89 的这个
  判断依然成立。
