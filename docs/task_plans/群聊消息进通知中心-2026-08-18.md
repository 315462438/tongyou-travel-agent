# 群聊消息进通知中心（Phase 97）

2026-08-18

## 问题

协同行程的群聊（Phase 61）有未读徽标，但**只在行程板内部可见**：`Trips.tsx` 的
`unread` 是组件本地 state，靠轮询 `GET /trips/{id}/chat` 比对新消息算出来的。

后果：**人不进那个页面，就永远不知道有人说话。** 主页顶栏的铃铛（Phase 84 统一通知中心）
只汇总社交通知和平台公告，群聊消息完全不在其中。

同行的人在群里问「左边这个已花费 7220 是怎么定义的」，对方可能几天后才看到。

## 方案

把群聊消息接进已有的通知中心，不新建通道。

### 后端

**① 发消息时写通知**（`trip_api.add_chat_message`）

对该行程**除发送者外的每个 accepted 成员**调 `upsert_notification`：

| 字段 | 值 |
| --- | --- |
| `type` | `trip_chat` |
| `title` | `{发送者昵称} 在「{行程标题}」发了消息` |
| `body` | 消息摘录 |
| `target_kind` | `trip` |
| `target_id` | `trip_id` |
| `dedupe_key` | `trip-chat:{trip_id}:{接收者 id}` |
| `meta` | `{"trip_id":…, "trip_title":…, "count": N}` |

**`dedupe_key` 按 (行程, 接收者) 唯一**是关键：一个行程刷 20 条消息，每人只有**一条**
通知在刷新，不会把铃铛冲爆。这是 Phase 84 已经确立的模式（同一用户对同一接力的反馈
切换只更新一条），照搬。

**必须与消息写入同事务**——`upsert_notification` 内部只 `flush`，放在 `add_chat_message`
的 `db.commit()` 之前即可。理由见 `docs/pitfalls/事件通知必须与业务同事务且按事件去重.md`：
消息成功了通知没落（或反过来）比两者都失败更难查。

**② 未读条数**

`upsert_notification` 会把行覆盖成未读。若沿用它的默认行为，`meta.count` 永远是 1，
显示不出「有 5 条新消息」。所以先读一次现有行：

- 行不存在，或已读（`read_at` 非空）→ `count = 1`（这是新一轮未读的开始）
- 行存在且未读 → `count = 旧 count + 1`

**刻意不引入 `last_read_at` 列**：`TravelTripMember` 没有该列，加列要走迁移，而
通知行自带 `read_at`，语义完全够用（「这条通知读没读」≡「这批消息看没看」）。
少一张状态表就少一处不同步。

**③ 标记已读**：新增 `POST /api/trips/{trip_id}/chat/read`

用户打开群聊抽屉时调用，把自己那条 `trip-chat:{trip_id}:{uid}` 通知置为已读。

**刻意做成显式端点**而不是在 `GET /chat` 里顺手改状态：GET 带副作用会让「轮询」
和「已读」纠缠在一起——前端关着面板也在 8s 轮询检查未读，那样会自己把自己标成已读。

**④ 行程删除时撤销**：`delete_trip` 里调
`delete_target_notifications("trip", trip_id)`，避免点开通知跳到一个 404 的行程。

**⑤ 不做的**：删除单条消息**不撤销**通知。「有人说过话」这件事仍然成立，
而且撤销要判断被删的是不是最新一条、要不要回退 count，复杂度换不来价值。
（与 Phase 84「取消反馈时撤销」不同：那里事件本身被取消了，这里没有。）

### 前端

- `components/Notifications.tsx`：认识 `type === 'trip_chat'`（图标 💬）与
  `target_kind === 'trip'`；`count > 1` 时标题后缀「等 N 条」
- `pages/Home.tsx` 的 `openNotificationTarget`：`target_kind === 'trip'` →
  打开协同行程页并定位到该行程、直接展开群聊
- `pages/Trips.tsx`：打开群聊抽屉时 `POST /trips/{id}/chat/read`，并刷新铃铛未读数

## 验收标准

`docs/test_cases/群聊消息进通知中心-验收用例.md`，落到 `backend/tests/`。核心：

1. A 发消息 → B、C 各收到一条通知；**A 自己没有**
2. A 连发 3 条 → B 仍然只有**一条**通知，`meta.count == 3`
3. B 标记已读后 A 再发 → count 重置为 1、通知回到未读
4. 非成员 / pending 成员**不**收到通知
5. 通知与消息**同事务**：写通知失败时消息也不落库
6. `POST /chat/read` 只影响调用者自己的通知
7. 删除行程 → 相关通知全部撤销
8. 删除单条消息 → 通知**不**撤销（有回归测试钉住这个有意决策）
9. 铃铛未读数把 `trip_chat` 计算在内
10. 全量 `pytest tests/ -q` 无新增失败

## 刻意不做

- **不做每条消息一个通知**。会把铃铛冲爆，且没有信息增益。
- **不加 `last_read_at` 列**，理由见上。
- **不做浏览器推送 / 桌面通知**。铃铛 + 徽标是当前形态下的正确粒度；
  推送要处理权限、后台、多端一致，成本远大于收益。
- **不改群聊本身的轮询机制**（Phase 61 的 2.5s / 8s），它工作正常。
