# 工具输出按结构裁剪（Phase 96）

2026-08-18　借鉴 dsh 社区插件 [toolshrink](https://github.com/deepseek-ai/deepseek-harness/discussions/2834)

## 背景

Phase 90 从 dsh 移植了幂等中段截断（`app/agent/truncate.py`）：`head + marker + tail`，
保证截过一次再截不会变。它解决的是「**截断本身要幂等**」，没解决「**截哪里**」——
仍然是按**位置**下刀。

toolshrink 的思路是按**结构**下刀：它有 9 个 reducer，认出内容格式后套一条人写死的规则
（测试输出丢 PASS 留 FAIL、diff 丢上下文行留 ±行、JSON 保结构抽样记录、栈追踪折叠依赖帧），
认不出就退回 head/tail。**全程零模型调用**，实测 `find` 大仓库 64151 → 2942 字符（-95%），
适配器只 ~70 行。

关键澄清：这里的「语义」不是"理解内容"，而是"**认得这是什么格式**"。判断力是人在写
reducer 那一刻付出的，运行时只是模式匹配 + 套规则。所以零 LLM、零额外延迟——
这对我们尤其重要，用 LLM 压缩会把省下的时间还回去。

## 现状实测（决定范围的证据）

### ① `fetch_url` 链路：`_html_to_text` 有效率 8%

`research_tools._html_to_text` 现在是「正则去 script/style/所有标签 → 折叠空白 → `text[:limit]`」。
拿维基百科「西湖」词条实测（`limit=4000`，即真实生产参数）：

| 指标 | 数值 |
| --- | --- |
| 原始 HTML | 515966 字符 |
| 去标签后全长 | 42141 字符 |
| 实际喂给模型 | 4000 字符（占全文 **9.5%**） |
| 其中导航 + 目录 | **3681 字符** |
| 其中真正的正文 | **319 字符** |
| **有效率** | **8%** |

模型看到的前 500 字长这样：

```
西湖 - 维基百科，自由的百科全书 跳转到内容 主菜单 主菜单 移至侧栏 隐藏 导航 首页
分类索引 特色内容 新闻动态 随机条目 联络我们 关于维基百科 贡献 帮助 维基社群 编辑入门
互助客栈 IRC即时聊天 最近更改 特殊页面 搜索 搜索 外观 资助维基百科 创建账号 登录
个人工具 … 目录 移至侧栏 隐藏 序言 1 名称 2 沿革 开关沿革子章节 2.1 秦汉－唐代 …
```

携程游记列表页同样：前 ~800 字全是「酒店 机票 特价机票 … 携程金融 企业商旅 老友会
登录 注册 我的订单 联系客服」加筛选器。

**位置截断的真正问题不是「丢了后面」，是「前面全是导航」**——预算再大也先被 chrome 吃掉。

另外发现：HTML 实体**没有解码**，正文里是 `&#91; 註 1 &#93;`（本该是 `[註 1]`）。

### ② `open_page` 链路：喂的是**原始可访问性树**

`browser_tool._snapshot_to_text` 的 docstring 写着「从可访问性树提取正文文本」，
但函数体（`browser_tool.py:459-463`）实际只做了一件事：

```python
if len(snapshot) > settings.max_snapshot_chars:
    snapshot = snapshot[: settings.max_snapshot_chars] + "\n...[截断]"
return snapshot
```

也就是把带 `uid=`、role 名、引号标签、缩进嵌套的 a11y 树**原样头部截断**后喂进去。
a11y 树承载同样文字所需的字符数是纯文本的数倍，而头部截断意味着深处的正文永远到不了。

（旁证：`research_tools._gist` 里有一条 `re.sub(r'^(uid=\S+\s*|link\s+"[^"]*"\s*)+', ...)`
—— 已经知道这些是噪声，但**只在展示用的进度文案里剥**，进模型的那份没剥。）

### ③ 不在范围内的（复核后确认已经够好）

- **高德**：`amap.build_amap_source` 早就是手写 reducer——天气取前 4 天、POI 取前 10 条、
  每条只留 name/评分/address(截30字)/坐标（`amap.py:171-192`）。`amap_poi` 只返回一行。
  **不动。**（上一轮我曾把它当作最大收益点，是错的。）
- **`web_search`**：已经是 `1. 标题 | URL` 的紧凑行。**不动。**
- **小红书笔记正文**：是散文，没有可利用的结构。只做实体解码。

## 方案

新增 `app/agent/reducers.py`，**纯 stdlib**（`html.parser` + `html.unescape`），
**不引入任何新依赖**——服务器内存本来就紧（xhs-mcp 容器要 1.5GiB 才不 OOM）。

### 两个 reducer + 一个兜底

| reducer | 认出条件 | 规则 |
| --- | --- | --- |
| `html` | 含 `<html`/`<body`/标签密度够 | ①整块丢弃 `script/style/noscript/nav/header/footer/aside/form/select` 及 class/id 命中 `nav\|menu\|sidebar\|footer\|header\|breadcrumb\|toc\|comment\|advert` 的容器；②`h1-h6` 前后加换行当章节标记；③`li`/`tr` 各占一行；④解码 HTML 实体；⑤丢弃引用角标 `[12]`/`[註 1]`；⑥折叠空白 |
| `a11y` | 含 `uid=` 或 `RootWebArea` | ①剥掉 `uid=xxx` 前缀与 role 名；②取出引号里的可读标签；③丢弃无文字的纯结构节点；④连续重复行去重（导航常整块重复） |
| （兜底） | 都不认得 | 原样交给现有 `TruncateBudget`，行为不变 |

### 不变式（每条都要有测试钉住）

1. **幂等**：`reduce(reduce(x)) == reduce(x)`。链路里会多次截断，不幂等就会变成头尾拼盘
   （Phase 90 立这条的理由依然成立，不能因为换了下刀方式就丢掉）。
2. **只删不改**：绝不重写、绝不改写词句——那就是编造了。
   **唯一例外**：HTML 实体解码（`&#91;` → `[`）。它是无损还原而非改写，且不解码反而是
   把原文的错误形态喂给模型。这条例外要写在代码注释里。
3. **可回取**：原文照旧全量 spill 到 `source_store`，`read_source` 仍可翻页取全文。
   裁剪只影响**预览**那一段。（`_stash_source` 的「留存换引用」本来就是 spill 思路，
   我们缺的只是预览那段的下刀方式。）
4. **失败退化**：reducer 抛任何异常 → 退回现有 head/tail，绝不影响主流程。
   （同 `repeat_guard` 的处置原则：增强绝不能让主链路失败。）
5. **删了多少要留痕**：返回 `Reduction(text, dropped, kind)`，在结果里标注
   「已省略 N 处导航/重复」——toolshrink 的做法，也是排查时区分「原文就短」还是「被裁过」
   的唯一依据。

### 改动点

- **新增** `app/agent/reducers.py`
- **改** `research_tools._html_to_text` → 走 `reduce_html`，签名与返回类型不变（向后兼容，
  已有单测不动）
- **改** `browser_tool._snapshot_to_text` → 走 `reduce_a11y`，并**把 docstring 改成与行为一致**
- **不改** `truncate.py`（它是兜底层，继续存在）、`_stash_source` 的留存换引用逻辑、
  amap、web_search

## 刻意不做

- **不引入 readability/trafilatura/bs4**。stdlib 够用；服务器内存紧；且这类库的启发式
  在中文站点上未必更好，引入了就得跟着它的版本走。
- **不做「相关性裁剪」**（按当前任务目标决定留什么）。toolshrink 作者自己承认拿不到
  agent 的目标所以做不了。我们的流水线虽然知道自己在干什么，但那会让 reducer 依赖调用
  上下文、破坏幂等和可测性。先做无状态的结构裁剪，够用再说。
- **不碰 amap / web_search / 小红书正文**，理由见上面「不在范围内」。
- **不用 LLM 做摘要**。那是 Claude Code auto-compact 那一层的事，跟这里正交；
  而且会把省下的时间还回去。
