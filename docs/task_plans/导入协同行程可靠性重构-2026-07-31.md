# Task Plan · 导入协同行程可靠性重构（2026-07-31）

## 问题（用户实测报告 + 服务端日志定位）

同一篇 6 天攻略（大理、丽江）连续两次导入均失败，各等 1:54 / 2:17，留下两条 6 天 0 地点的空行程。
服务端日志一句话定位：

```
Day 2–2 分段抽取失败：LLM 结构化输出解析失败（重试后仍不合法）:
结构化输出达到 3000 tokens 上限，已在 JSON 中途截断
```

11 条现象，5 个根因，**全部确定性、无偶现**：

| 根因 | 位置 | 解释的现象 |
| --- | --- | --- |
| A. 单段 `max_tokens=3000` 过低 | `trip_api.py:832` | 「自动分段仍失败」——分段其实已生效（切到单天 Day 2–2），是输出上限不够 |
| B. `asyncio.gather` 未设 `return_exceptions` | `:838` | 一段失败 → 其余已成功的天全部丢弃 |
| C. 行程行在解析**之前**就 commit | `:964` 建行 → `:978` 才起后台任务 | 必然留空行程；无回滚、无草稿标记 |
| D. 无幂等键 | 每次 POST 都新建 TravelTrip | 重试变新建、两条重复空行程 |
| E. `destination` 只在成功分支写 | `:1078` | 「未定目的地」——而 summary 步骤其实**已成功拿到「大理、丽江」**，被整包丢弃 |

## 方案

### 1. 幂等（唯一导入任务 = 唯一行程行）
`POST /trips/import` 先按 `(source_message_id, owner_id)` 查已有行程：存在则直接返回它
（`reused: true`），永不重复建。这既是「唯一导入任务 ID」，也天然杜绝重复空行程。

### 2. 按天解析 + 保留部分成功
- `max_tokens` 3000 → `settings.trip_import_chunk_max_tokens`(8000)；
- `asyncio.gather(..., return_exceptions=True)`：失败的天记进 `failed_days`，**成功的天照常入库**；
- 逐天完成时更新 `ai_review` 为「已完成 3/6 天」——板上直接可见真实进度。

### 3. 草稿语义与恢复入口
- 全成功 → `ai_status=None`（正常行程）；
- 部分成功 → `ai_status="partial"`，`ai_review` 写明**哪几天**失败 + 可重试；
- 全失败 → `ai_status="failed"`，同样写明失败天；
- 无论哪种，`destination`/`title`/`days` 都从 summary 落盘（不再「未定目的地」）；
- 新增 `POST /trips/{id}/import/retry`：**只重跑失败的天**，成功则合并进去；
- 前端在 `partial/failed` 状态展示「继续重试」「删除草稿」两个按钮。

### 4. 顺带修（同类问题第三次出现）
`parse_request` 的 `llm.parse` 无取消检查点 → 修改攻略时点停止要等 27 秒。
用今天已建好的 `cancel.wait_cancellable` 包住（budget/poster 已是同一模式）。

## 不做

「先解析到临时数据、全成功再建正式行程」的字面实现——那样没有承载进度显示和幂等的锚点，
POST 也会阻塞 2 分钟。改用**显式草稿行**达成同样目的：行永远存在但状态明确、可重试、可删除、
不重复，绝不会再出现「静默的空行程」。

## 验收

- `tests/test_trip_import.py`：幂等、部分成功保留、失败天可重试、进度文案、destination 落盘。
- 线上用同一篇大理丽江 6 天攻略复测：导入成功或部分成功且目的地正确；重复点击不产生第二条。
- 现有 608 例不回归。
