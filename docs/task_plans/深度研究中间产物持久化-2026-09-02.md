# 深度研究中间产物持久化（Phase 112 计划）— 2026-09-02

## 缘起

复核 `openai/codex` 上游时问到一句：「deep_research 不挂 checkpoint 岂不是代表会话中断，
不能继续执行？」——查完发现**是的，而且我此前把这条描述得过轻了**。

## 现状（已在代码里逐条核实）

1. `_mark_inflight(cid, turn_id, user_id)` 在 `orchestrator.py:2380`，位置在**路由之前**，
   所以 research 轮**有**在途登记，重启后 `resume_inflight_turns()` 捞得到。
2. 但 `graph.resume_turn(turn_id)`（`graph.py:79`）只认攻略图：

   ```python
   snap = await app.aget_state(cfg)
   if snap is None or not snap.next:   # research 轮在这里返回 False
       return False
   ```

   research 轮的 turn_id 下**根本没有 checkpoint**（`create_deep_agent(...)` 不挂
   checkpointer），于是走 `_append_interrupted(cid)`：

   > ⚠️ 上一轮处理被服务重启中断了，内容没有生成完整，请把需求重新发一次。

**结论：不是挂死、不是静默丢失，是优雅降级成「让用户重发」。** 而且 Phase 71 的 quick take
是条已落库的普通 assistant 消息，用户手上至少还有那 150 字初步判断。用户主动点停止是另一条
路（`cancel.check` 协作式取消），与重启无关，那条行为是对的。

## 真正的代价

丢的是整轮 4–6 分钟的**工作面**：

```python
# research_tools.py:192
source_store: dict[str, str] = {}   # s1/s2/… → 留存全文（按轮，内存）
```

闭包里的内存字典。抓回来的网页全文、工具结果、agent 推理轨迹，重启后一起没。重发 =
再烧一次浏览器 + LLM 预算。

**一个此前没注意到的不对称**：Phase 103 ④ 已经建了 `travel_source_page` 表把来源全文落库，
但只接在 **guide** 链路（`_search_and_collect_queries`）。**最长、最贵的那条路，反而是唯一
没有中间产物持久化的。**

## 为什么不能直接给 research 挂 checkpointer

会掉进一个比现在更糟的坑：

1. `BrowserSession` 是 actor，持有活的 ChromeMCP。续跑能恢复消息状态，**恢复不了浏览器
   会话**（Phase 21 记过：mcp stdio_client 是 task-affine 的，跨 task 进出会炸 cancel scope）。
2. 更要命：`source_store` **不在 state 里**。续跑后模型手里的历史消息还写着
   `[来源 s3 | … ]`，它去调 `read_source("s3")` 会拿到「本轮还没有留存的来源」——
   **模型不知道自己的引用凭空作废了，而它已经在基于 s3 的摘要往下推理。**

这正是 codex `context_manager/normalize.rs::ensure_call_outputs_present` 想防的那类事
（悬空的 tool call 必须补一个合成 output，而不是留着让模型自己发现）。一般化成我们的话：
**半截恢复比干净重来更危险，除非被恢复的那一半自己能说清「我少了什么」。**

## 方案：分三步，每步独立成立

### 第 1 步（本计划的落地范围）：`source_store` 落库

复用 Phase 103 ④ 已建好的 `travel_source_page` 表（`(conversation_id, url)` 唯一、上限
40000 字、每会话留 24 页），把 `_stash_source` 的内存字典改成「内存 + 落库」双写：

- 写：`_stash_source` 落库时带 `source_id`（s1/s2/…）与 `turn_id`。
- 读：`read_source(sid)` 内存未命中时**回查库**。
- 复用：同一会话下一轮（含用户重发同一需求）命中同 URL 直接取库里的全文，不重抓。

**这一步单独就成立**——与 checkpoint 无关，收益是「重发时不用重抓同样的页」，把重发代价的
大头削掉；同时它是后面两步的**前置条件**（没有它，续跑一定会得到一个引用悬空的 agent）。

⚠️ 复用范围只到**同一会话**。跨用户/跨会话的目的地缓存是 Phase 102 已经单独立项的事，
不在这里顺手做。

### 第 2 步：中断时产出「部分结论」而非只说重发

照搬 Phase 102 xhs 部分收成的思路：`_append_interrupted` 之前，若本轮已有 ≥1 条落库来源，
用 v4-flash 就着**已收集到的来源**出一份带「基于部分资料」标记的初步结论，再附重发入口。
至少那几分钟不白烧。

### 第 3 步：真正给 research 挂 checkpointer

前提是第 1 步已落地（引用不再悬空）。届时还需要：
- `BrowserSession` 重建（或续跑时降级为「只用纯 API 工具」并明确告诉模型浏览器不可用——
  这是 codex 那条「降级要写进上下文」的直接应用）；
- 续跑入口从 `graph.resume_turn` 分出 research 分支，不要把两条图的恢复语义混在一个函数里。

## 涉及模块

| 文件 | 改动 |
| --- | --- |
| `app/agent/research_tools.py` | `_stash_source` 双写、`read_source` 回查库 |
| `app/agent/source_pages.py` | 复用现有写入/读取，按需加 `source_id` 列 |
| `app/db/models.py` + `app/db/migrate.py` | `travel_source_page` 加 `source_id`（幂等 `ADD COLUMN IF NOT EXISTS`，见 `docs/pitfalls/create_all只建表不加列.md`） |
| `app/db/maintenance.py` | 第 2 步才动 |

## 验收标准（第 1 步）

1. research 轮抓到的每个来源在 `travel_source_page` 里有一行，全文可读回。
2. `read_source(sid)` 在内存字典被清空后仍能返回全文（模拟跨进程）。
3. 同一会话重发同一需求，命中同 URL 时不再调用浏览器/HTTP 抓取。
4. 落库失败**不影响主流程**（降级回纯内存，与改造前一致）——与 Phase 103 「降级方向永远是
   和改造前一样」同一条纪律。
5. 库里读回的内容仍过 `wrap_external`（它是外部不可信内容，不因为经过我们的库就变可信）。

## 刻意不做

- **不在第 1 步动 checkpointer**。先落数据、后落恢复，两者的把握度完全不同
  （同 Phase 103 「先落数据、后落算法」）。
- **不做跨会话来源复用**（Phase 102 已单独立项）。
- **不改 `_append_interrupted` 的文案**，直到第 2 步真的能给出部分结论——现在改文案等于
  承诺一个还不存在的能力。
