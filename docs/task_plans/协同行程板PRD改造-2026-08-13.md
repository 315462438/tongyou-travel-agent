PRD 是给另一个原型（`travel-planner-final.html`，上海5日游）写的，它的 **P0「地基」在本项目已经存在**：

| PRD P0 项 | 本项目现状 |
| --- | --- |
| 账号登录 | ✅ Phase 15（`TravelUser`/`TravelSession`，非微信登录） |
| 数据持久化 | ✅ PostgreSQL，非 localStorage |
| 多行程首页 + 邀请码 | ✅ `TripList` + `invite_token` + `/trips/{id}/invite` |
| 实时同步 + 编辑人=当前用户 | ✅ 2.5s 轮询 + `TravelTripEvent` 留痕 |
| 内嵌群聊 | ✅ Phase 61 已自建（PRD 建议跳微信，本项目**保留自建**，见下） |

所以本次落地的是 PRD 的 **4.3 模块标签栏重排 + 4.4 缺失模块 + 4.2 头部增强 + 4.5 情境化悬浮按钮**。

### 两处**不采纳** PRD 的决定
1. **配色**：PRD 主张暖橙 `#C4612F`。本项目配色是 Phase 66「17同游」品牌统一的结果，
   只改结构不动色（用户确认）。
2. **群聊**：PRD 建议"不自建、跳微信"。本项目 Phase 61 已自建 `TravelTripChatMessage`
   且与成员校验/未读徽标打通，跳微信是**倒退**。保留自建，只把入口收进标签栏。
   相册仍按 PRD 走轻量（不自建）。

## 三、新增后端（4 张表 + CRUD）

| 表 | 字段要点 | 对应 PRD 模块 |
| --- | --- | --- |
| `travel_trip_food` | name/category(小吃·正餐·甜点)/city/price/note/is_top | 模块2 美食 |
| `travel_trip_task` | title/assignee_user_id(null=待认领)/due_date/status(todo·doing·done) | 模块5 任务分工 |
| `travel_trip_packing_item` | name/category | 模块6 行李（行） |
| `travel_trip_packing_state` | (item_id,user_id) 复合主键 + state(packed·unpacked·na) | 模块6 行李（三态格） |
| `travel_trip_tip` | level(important·notice)/content | 模块7 避坑 |

**行李为什么用独立状态表而不是 item 上挂 JSON**：三态格子是多人高频并发点击，
JSON 整体覆写会互相冲掉（本项目 2.5s 轮询，冲突窗口真实存在）；一行一个 (item,user)
让并发点击落在不同行上。

API 全部挂 `/api/trips/{trip_id}/...`，一律过 `_member(db, trip_id, user)` 成员校验，
写操作落 `_log_event`（复用现有动态时间线）。

## 七、实现中的两个具体决定

1. **行李三态只能改自己那一列**。接口没有「改谁的格子」参数——三态语义是「我带没带」，
   代别人打勾既无意义又会造成信任问题。前端把别人的格子设为 `disabled`。
2. **三态点击不写动态时间线**。它是高频操作，落 event 会把时间线刷爆（有回归测试
   `test_packing_state_toggles_do_not_flood_event_log` 钉住）。其余增删改照常留痕。
