# Task Plan — Phase 61：协同行程群聊

## 背景与目标

协同行程目前只有地点级留言，适合讨论某个景点，但同行者缺少一个讨论整体安排、集合时间、
预算取舍和临时变更的公共频道。本期增加「行程群聊」：

- 群聊归属于行程，所有已接受邀请的成员可读写；
- 不替代地点留言，地点留言继续承载局部上下文；
- 沿用现有 2.5 秒轮询协同模型，不引入 WebSocket；
- 桌面端使用右侧抽屉，移动端使用全屏聊天面板。

## 数据与 API

新增 `travel_trip_chat_message`：

- `id`：消息 ID；
- `trip_id`：所属行程；
- `user_id`：发送者；
- `content`：纯文本内容；
- `created_at`：发送时间。

接口：

- `GET /api/trips/{trip_id}/chat?after=`：成员读取消息；默认返回最近 100 条，
  `after` 存在时增量返回；
- `POST /api/trips/{trip_id}/chat`：成员发送消息，去除首尾空白，限制 1000 字；
- `DELETE /api/trips/{trip_id}/chat/{message_id}`：仅发送者可删除自己的消息。

所有接口复用 `_member`，非成员统一返回 404，不泄露行程存在性。群聊消息不写
`travel_trip_event`，避免修改记录被日常聊天淹没。

## 前端方案

- 行程板头成员头像旁增加「群聊」按钮和未读圆点；
- 点击后从右侧打开聊天抽屉，顶部展示行程标题与成员头像；
- 消息按发送者分左右气泡，展示头像、用户名和时间；
- 打开期间每 2.5 秒增量轮询，新消息到达后在用户接近底部时自动滚动；
- Enter 发送，Shift+Enter 换行；发送中禁用重复提交；
- 空状态给出适合群聊的提示文案；
- 关闭抽屉时记录最后已读消息 ID；抽屉关闭期间检测到新消息时展示未读圆点；
- 手机端抽屉占满屏幕，输入框避让安全区。

## 验收标准

1. 行程成员可发送并看到彼此的群聊消息；
2. 未接受邀请或非成员不能读取、发送、删除群聊消息；
3. 只能删除自己的消息；
4. 空消息被拒绝，消息正文最多保存 1000 字；
5. 打开抽屉时消息持续刷新，关闭后有新消息显示未读提示；
6. 地点留言功能保持不变；
7. 桌面端抽屉不遮挡关闭入口，390px 手机端无横向溢出；
8. 后端自动化测试、前端测试、lint、类型检查和生产构建全部通过。
