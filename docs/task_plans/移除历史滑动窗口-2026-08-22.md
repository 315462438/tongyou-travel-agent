# 移除历史装配的滑动窗口（2026-08-22）

## 背景：两套压缩叠在一起

Phase 91 把历史压缩改造成了**日志 + surface 投影**：摘要作为一条
`role='summary'`、`surface_op='replace'` 的消息追加进日志，遮蔽区间就是它折叠掉的
那批原始消息；`derive_surface()` 负责投影。原文一条不删、可完整回放。

但 `_assemble_history()` 里 Phase 34 留下的**滑动窗口**没跟着删：

```python
if sum(len(m["content"]) for m in msgs) <= settings.history_full_max_chars:
    return msgs, summary
return msgs[-settings.history_rounds * 2:], summary   # ← 这一行
```

于是同一条链路上有两套互不知情的压缩：

| | surface 投影（Phase 91） | 滑动窗口（Phase 34 遗留） |
| --- | --- | --- |
| 触发 | 轮末 `update_history_summary` | 每次装配现算 |
| 边界移动 | 只在写入 replace 消息时 | **每轮都可能移** |
| 被移除的内容 | 有摘要覆盖，原文可回放 | **无任何记录，静默丢弃** |
| 可回溯 | 是（日志里有 replace 事件） | 否 |

## 为什么必须删（三条，按严重性）

### 1. 静默丢弃（正确性）

`update_history_summary` 是轮末旁路、失败只记日志。它一旦失败（LLM 429/超时——
Phase 103 刚给传输层加了重试，正说明这类失败是常态而非意外），下一轮 surface 里
就有 11-12 条 live 消息且已超字数，滑动窗口直接 `msgs[-10:]` 砍掉最早那 1-2 条，
而**没有任何摘要覆盖它们**。用户在那 1-2 条里说的约束（"别安排早起"）当轮蒸发，
模型不知道自己少看了东西。

下一轮的 `update_history_summary` 会从 surface 出发把它们折进摘要，所以它**会自愈**
——这恰恰是最坏的一类 bug：偶发、单轮、自愈、无日志，事后完全无法复现。

### 2. 前缀缓存（成本）

超限后每轮窗口左边界右移一格，`history_msgs` 的**开头就变了**，DeepSeek 前缀缓存
从 system 之后立刻失效。Phase 58 费力把易变项末置到 user 保住的那段前缀，被这一行
从头部废掉。（注：稳态下窗口常常退化为 no-op——因为 `update_history_summary` 折叠后
恰好留下 `keep` 条——所以这条损失是间歇性的，与失效期重合。）

### 3. 追溯性移动（可观测）

`context_manifest`（Phase 89）的模块 docstring 里点名批评过这一行：改了
`history_rounds` 会**追溯性地移动**历史边界。清单只能记录当时的派生结果，治标不治本。
删掉之后边界由日志里的 replace 事件唯一决定，改配置不再影响既往。

## 改造方案

**一条原则：只有 `update_history_summary` 能改变模型可见的历史边界；
`_assemble_history` 退化为纯投影读取。**

### `_assemble_history()`

1. 删掉字数判断与 `msgs[-history_rounds*2:]` 切片，恒定返回全量 surface。
2. **同步兜底**：若超 `history_full_max_chars`，就地调一次 `update_history_summary(cid)`
   再重新投影。这是把折叠**记录下来**，不是静默砍。
   - ⚠️ 这与 Phase 103「把压缩挪出关键路径」不冲突：Phase 103 反对的是**无条件**每轮
     花 2-5s；这里只在旁路已经失败、否则就要丢消息时才触发，稳态下永不进入。
3. **紧急降级**：同步折叠也失败（连续 LLM 故障）且仍超限 → 才丢最早的消息，但打
   `logger.error` 带上丢了几条/多少字。与改造前的区别是**从静默变成有记录**。
4. 保留 `conversation.history_summary` 的存量回退（Phase 91 的理由不变：老会话日志里
   没有 summary 消息），但触发条件从「超限分支」改为「surface 里没有 summary 消息」。

### 不动的部分

- 摘要的注入位置（调用方包 `<conversation_summary>` 放在末条 user）。位置确实不合
  时序——摘要讲的是**更早**的事却排在近期消息之后——但那是另一个问题，改它要动
  `build_guide_messages`/`run_direct_answer`/`deep_research` 三处的 prompt 形态，
  与本次「删掉双轨」正交。**单独立项**。
- `_history_context()`（近 5 轮 + 每条截 500 字）：那是给 `credibility_directive` 等
  轻量场景用的，不进主 prompt，与本次无关。
- `settings.history_rounds`：仍被 `update_history_summary` 用作折叠时的保留轮数，
  只是不再在装配期二次生效。

## 验收标准

1. 未超限：全量 surface 逐字注入（原行为不变）。
2. 超限且旁路摘要正常：同步折叠一次 → 返回的消息数下降且**日志里多了一条 replace**，
   被移除的消息可通过 `derive_surface` 之外的全量查询回放。
3. 超限且折叠失败：仍返回全量（不静默砍），除非再次超限才降级，且降级必打 error 日志。
4. 连续两轮装配，若期间无 replace 写入，`history_msgs` 的**前缀逐条相等**
   （钉住"边界不会每轮移动"这个核心性质）。
5. 老会话（无 summary 消息、有 `conversation.history_summary`）仍能拿到摘要。
6. `tests/test_full_history.py`、`tests/test_surface_projection.py` 全绿。

## 风险

- 主要风险是**长会话的首轮变慢**：老的超长会话第一次进来会触发同步折叠（+2-5s）。
  一次性，之后由旁路维持。可接受。
- `update_history_summary` 内部自己也读 surface 并判字数，同步调用它是幂等的
  （已被 Phase 91 的幂等设计保证）。
