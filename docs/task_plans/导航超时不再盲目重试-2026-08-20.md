# 导航超时不再盲目重试（Phase 99）

2026-08-20

## 问题（线上 Langfuse 实测发现）

`browser_tool.open_page` 的导航重试：

```python
try:
    await self.chrome.call("navigate_page", {"url": url, "timeout": 30000})
except Exception:  # 慢站点重试一次
    await self.chrome.call("navigate_page", {"url": url, "timeout": 30000})
```

最近两轮完整 guide 各出现一个 **~62s 的 open_page span**（62.4s / 62.7s，数值整齐得
不像偶然）——正是「30s 超时 + 盲目重试再烧 30s + snapshot」的痕迹。一个打不开的页面
白烧一分钟。

更糟的是重试有**反作用**：导航超时 ≠ 页面为空。首次超时时页面往往已经**部分加载**，
直接 snapshot 常能拿到可用内容（Phase 96 的 reduce_a11y 还会把它清干净）；
重导航反而把已加载的内容重置掉。

## 方案

按失败类型分流，只改这一处：

- **超时类失败**（消息含 timeout/timed out，或 `TimeoutError` 实例）→ **不重导航**，
  记一条 warning，直接走 snapshot 兜底。最坏情形 62s → ~32s，且可能救回部分内容。
- **非超时失败**（CDP 抖动、连接断）→ 维持原样重试一次。这类失败是瞬时的且失败得快，
  重试是当初加这行的合理场景，别把它一起砍了。
- 判别函数 `_looks_like_timeout` 做成模块级纯函数，可单测。**识别不出来就当非超时**
  ——退化方向是回到今天的行为，不会更差。

## 验收

`tests/test_open_page_retry.py`：

1. 首次导航抛超时 → navigate 只调 **1 次**，仍走 snapshot 并返回结果
2. 首次导航抛非超时错误、第二次成功 → navigate 调 2 次（原行为保留）
3. 非超时错误连抛两次 → 异常照旧冒泡（不吞）
4. 首次成功 → navigate 只调 1 次
5. `_looks_like_timeout`：`TimeoutError()`（str 为空）/ 各种消息变体 / 非超时反例
6. 全量回归无新增失败

## 刻意不做

- 不缩短 30s 首次超时——慢站点真的需要它，改短会误伤能打开的页面。
- 不动 `wait_for` 的 5s 和 `_evaluate_current_page`。
- 不给 fetch_url/xhs 链路加同类逻辑——它们没有这个双重超时模式。
