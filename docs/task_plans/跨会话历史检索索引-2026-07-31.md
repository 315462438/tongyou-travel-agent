# Task Plan · 跨会话历史检索索引（2026-07-31）

## 问题

`recall_past_chats` 判断「哪个旧会话与本次目的地相关」用的是**标题子串匹配**
（`dest not in c.title`），而标题是用户第一句话的截断：

- **漏检**：第一句没报城市（「帮我规划十一去玩」）的会话永远检索不到；
- **多城必然失败**：`"武汉、开封、洛阳" in title` 几乎不可能成立；
- **N+1**：对每个标题命中的会话再单独查一次它的**全部** assistant 消息
  （单条 meta_json 最大 12KB、正文均 1.9KB），只为找出第一条「像样攻略」；
- 「哪条是攻略」靠读时启发式猜（跳过流式/海报/预算/过短），而 finalize 那一刻本来就知道。

## 方案：会话级结构化索引（不引检索引擎）

```
travel_conversation 加两列，在 finalize_guide 写入：
  destination       VARCHAR(64)   -- pref.destination（真实解析结果）
  guide_message_id  VARCHAR(32)   -- 首条确认是攻略的消息 id（只写一次，不覆盖）
```

检索变成**固定 2 次查询**（与会话数无关）：
1. 拉最近 50 个会话的 `(id, title, destination, guide_message_id)`——4 个短列；
2. Python 侧按城市拆分做重叠匹配，选 ≤3 个，一次 `where id in (...)` 取那 ≤3 条消息。

`recent_plan_hint` 同时改用 `destination` 列（原实现要拉 30 条完整消息 ≈150KB 只为读一个城市名）。

## 不做什么

不上 PG 全文检索（中文分词要装 zhparser/pg_jieba 扩展）、不上 pgvector
（DeepSeek 无 embedding 接口）、不用 v4-flash 挑会话（每轮 +1s、非确定性）。
当前单用户最多 9 个会话，缺陷是**取错字段**不是**排序不够聪明**。
升级线：会话量到几百且用户开始按主题而非地点找旧对话 → 先 pg_trgm 再 embedding。

## 验收

- `tests/test_history_index.py`：写入点、多城重叠匹配、漏检修复、查询次数固定、
  hint 改用列后行为不变。
- 迁移回填后线上存量会话的 destination 非空率 ≈ 有攻略的会话数。
- 现有 587 例不回归。

## 验收结果（2026-07-31 全部上线）

**索引**：后端 595→608 全绿；迁移回填 145 个会话中 92 个有攻略的全部拿到索引；
**实测旧的标题子串匹配在 92 个会话里漏检 11 个（12%）**，典型如「合肥出发去武汉途中有
什么好玩的」真实目的地是天堂寨、标题里根本没有。`recent_plan_hint` 同步改用列
（原来拉 30 条完整消息 ≈150KB 只为读一个城市名）。

**来源复用**：参数按「默认开启 + 明确告知 + 正文 7 天 / 图片 20 小时」落地。
线上端到端复测（同账号同目的地成都）：

## 后续（本计划的直接受益，另行决策）

跨会话**来源复用**：命中同目的地的近期会话时复用其 `sources`，跳过小红书重抓
（首轮 ~4min → ~40s）。实测约束（2026-07-31）：
小红书图片 URL 4 天前 403 / 14 小时前 200 → 图片复用窗口 ≈24h；
高德 POI 图 24 天前仍 200 → 不过期；天气必须重取；携程价格绝不复用。
