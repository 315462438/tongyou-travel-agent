# 图片降级必须告知模型（Phase 112）— 2026-09-02

## 缘起

复核 `openai/codex` 上游（`core/src/image_preparation.rs` +
`core/src/context/image_resize_notice.rs` + `core/src/context/unsupported_media.rs`）时
发现一条我们只做了一半的纪律：

- 图被缩了 → 往模型上下文塞一条 developer 消息：
  `Image 1 of 3 in the preceding user message was resized from 1800x25242 to 1200x8192 pixels.`
- 图处理失败 → **原地替换成文字占位符**进上下文：
  `image content omitted because it could not be processed` / `...exceeded the supported size limit`，
  而不是把它从列表里悄悄删掉。

Phase 111 ⑤ 已经立下「**失败必须可见**」的规矩，但**只做到了对用户可见**（progress 气泡 +
`_BLIND_ASKS` 反问文案）。**对模型仍然是不可见的。**

## 三个口子（均已在代码里核实）

### ① 缩图不告知（`image_prep.py:105` 与 `:117`）

```python
if width > max_side:                      # 太宽 → 等比缩
    ...
    im = im.resize((width, height), Image.LANCZOS)
...
if need > max_tiles:                      # 片数不够 → 先缩后切
    ...
    im = im.resize((width, height), Image.LANCZOS)
    logger.info("长图先缩后切: ...")      # ← 只有日志
```

`prepare_for_vision` 返回的是**一串 data URI**，没有任何降级信息。1800×25242 的行程单缩到
能切下时字会糊，而模型**不知道自己在看一张被压过的图**，会照样自信地念出价格和日期。
这是 Phase 111「报错说格式不支持其实是尺寸越界」的镜像：那次是**报文说谎**，这次是**根本
没说**。

### ② 部分失败不告知（`orchestrator.py:2393`）

```python
desc = vision.describe_user_images(image_ids, ...)
if desc:
    user_text += wrap_external(desc, source="user_image", ...)
else:
    _image_unreadable(cid)
```

`describe_user_images` 内部对每张图 `except: continue`。**传 3 张、读出 1 张 → `desc` 非空
→ 不走 `_image_unreadable`**，模型和用户都不知道有 2 张没读。而前面刚播过
「正在看你发的 **3** 张图…」。**这就是 Phase 111 ⑤ 那条规矩在单图粒度上的漏网。**

### ③ 渲染上限不告知（`vision.py:238`）

```python
if len(uniq) > cap:   # 真砍了就说一声，别让下游以为这就是全部
    logger.info(...)
lines.append(label + "：" + "；".join(uniq[:cap]))
```

注释写着「就说一声」，实际只对**日志**说了。Phase 111 已经把写死的 15 改成可配置，但
「砍了不说」这件事本身没修——下游仍然以为看到的是全部。

## 方案

一条共同的纪律：**凡链路对输入做了有损处理，处理结果必须自带一段说明，与内容一起进模型。**

### 改动一：`prepare_for_vision` 返回降级事实

```python
@dataclass(frozen=True)
class PreparedImages:
    uris: list[str]
    notices: list[str]        # 人话，可直接进 prompt
    tiled: bool
```

两处 `resize` 各记一条（原始尺寸 → 处理后尺寸 + 为什么）；解码失败 / 无 Pillow 的降级路径
也记一条。**返回类型改了，所有调用方必须同步**——`describe_user_images`、
`judge_page_image`、`extract_note_images` 三处。

### 改动二：`describe_user_images` 汇总「这批图发生了什么」

- 逐图记录三种结局：`ok` / `failed(原因)` / `resized(说明)`。
- 返回文本末尾追加一段**我方口径**的说明块（在 `wrap_external` 之外，因为这是我们自己的
  话，不是外部内容——同 Phase 31「来源编号、read_source 提示这些『我们自己的话』留在标签外」）：

  ```
  【读图说明】共 3 张，成功读取 1 张。
  第 2 张：解码失败，未读取。
  第 3 张：超出尺寸上限，未读取。
  第 1 张：原图 1800×25242，为适配上限已缩放至 1200×8192 后分 4 段读取，细小文字可能不准确。
  ```

- 新增 `describe_user_images` 的返回结构（文本 + 统计），让 orchestrator 能判断
  **部分失败**并据此播进度、必要时落 `_image_unreadable` 标记。

### 改动三：`uniq[:cap]` 截断写进产出

`lines.append(f"{label}：{'；'.join(uniq[:cap])}（共 {len(uniq)} 条，此处只列前 {cap} 条）")`

### 改动四：orchestrator 的进度与反问对齐

- 部分失败时播一条明确的进度（「3 张图里有 2 张没读出来」），不再只播「正在看你发的 3 张图…」
  然后装作无事发生。
- `_image_unreadable` 的触发条件从「一张都没读出来」放宽到「**有图没读出来**」，
  让 Phase 111 的 `_BLIND_ASKS` 升级文案在部分失败时也能对得上原因。
  ⚠️ **但代选规则不变**：Phase 111 ④ 的「读不出图时不代选」判据仍是
  `forced and not blind`，部分失败同样算 blind——我们仍有正面证据说明用户手上有确定目的地。

## 涉及模块

| 文件 | 改动 |
| --- | --- |
| `app/agent/image_prep.py` | 返回 `PreparedImages`，两处 resize + 降级路径记 notice |
| `app/agent/vision.py` | 逐图结局统计、说明块、截断写进产出、三处调用方适配 |
| `app/agent/orchestrator.py` | 部分失败播进度 + 落 `_image_unreadable` 标记 |

## 验收标准

1. 超宽图 / 需先缩后切的长图 → `notices` 非空且含原始与处理后尺寸。
2. 规格内的图 → `notices` 为空，且**字节与改造前逐字节相同**（不重编码这条不能破）。
3. 3 张图 2 张失败 → 返回文本含「成功读取 1 张」与逐条原因；orchestrator 落
   `_image_unreadable` 标记；本轮反问走 `_BLIND_ASKS`。
4. 全部失败 → 行为与改造前一致（`desc` 为空 → `_image_unreadable`）。
5. 截断发生时，产出文本里出现「共 N 条，此处只列前 M 条」。
6. 变异检验：把 notice 生成删掉 → 用例立刻红（否则测的是「函数被调用」而不是「事实被传达」）。
7. Pillow 不可用时不抛异常，退化为改造前行为 + 一条说明。

## 刻意不做

- **不给图片单开一条链路**。Phase 105 的判断没变：图 → 结构化文本 → 走现有路由。
  说明块也是文本，跟着同一条路走。
- **不把说明块放进 `wrap_external` 里**。那是外部内容的防线；这段是我们自己的话，
  混进去会让审计时分不清哪句是模型「看」出来的、哪句是我们说的。
- **不做 codex 那套 `max_patches` 面积预算**。我们只有单边上限这一个已知约束
  （Phase 111 实测排掉了字节数与宽高比），凭空引入第二个预算维度是无证据的复杂度。
