# 记忆时间戳语义修复：把「最后注入」从「最后更改」里拆出来（2026-08-24）

## 背景

`travel_memory.updated_at` 声明为 `onupdate=_now`（`app/db/models.py:182`）。SQLAlchemy 的
`onupdate` 对该行的**任何** UPDATE 生效，与改的是哪一列无关。

而 `_bump_hit_count`（`app/agent/memory.py:511`）是全系统唯一一处**纯记账写**——它只想给
`hit_count` 加一，却连带把 `updated_at` 推到当下。它每轮跑一次，对本轮注入的每条记忆都跑。

其余写路径（`memory.py:297-300` 的 upsert、`565` 的整理替换、各处 delete）全是真的内容变更，
只有这一处是记账。

**结果：`updated_at` 的实际语义是「最后一次被注入」，而全系统按「内容最后一次变化」在读它。**

本地实测（sqlite，只 +1 hit_count、内容未变）：

```
updated_at 变了吗 → True (07:31:55.549 → 07:31:56.658)
```

## 三个已确认的后果

### ① Phase 30 的年龄标签永久说谎（最严重）

`format_memories_block`（`memory.py:139`）给每条记忆在 prompt 里贴年龄：

```python
age = _age_label(m.updated_at)        # 「今天」/「昨天」/「47 天前」
```

`_age_label` 的 docstring 写明意图：「模型不擅长日期算术，『47 天前』比裸时间戳更能触发
**过期意识**」。这是专门造出来让模型对陈旧偏好起疑的信号。

但注入本身刷新了 `updated_at` —— 一条记忆只要上一轮被注入过，这一轮就标成「今天」/「昨天」。
**越活跃的用户偏得越狠**：天天聊的人，所有记忆永远是「今天」。

线上实测（2026-08-24，47 行中 25 行偏差 > 1 天）：

```
293cbea7 住宿偏好   prompt写「2 天前」，实际建于 25 天前
293cbea7 预算偏好   prompt写「2 天前」，实际建于 25 天前
（该用户 7 条全部如此）
4dd968c4 出行方式   prompt写「5 天前」，实际建于 24 天前
df1e2436 旅行足迹   prompt写「8 天前」，实际建于 20 天前
受影响 25/47 行
```

一年前说的「爱吃辣」和今天刚说的，在 prompt 里长得一模一样。Phase 30 建的过期意识，
模型从来没收到过。

### ② 记忆整理的触发条件不是它以为的那个

`_should_sleep_consolidate`（`memory.py:623`）：

```python
fresh_q = base if last is None else base.where(TravelMemory.updated_at > last)
return new_count >= settings.memory_consolidate_min_new   # 5
```

意图是「距上次整理后**新增/变更**达到 5 条才值得再整」，实际数的是「距上次整理后**被注入过**
的记忆」——注入是全量的，聊一轮就全部够数。门控退化成
`记忆数≥8 且 距上次整理≥6h 且 这期间聊过天`，「变更」这个条件被架空。

代价不是白跑一次：`consolidate_memories` 是 LLM 把全部记忆重写成规范三元组然后**整体替换**
（`memory.py:565` 的 `db.delete(old)`），**每次重写都是一次有损传递**（同 Phase 103 对
history summary 的判断）。什么都没变，也每 6 小时重写一遍。

今天影响面小（线上仅 1 个用户到 8 条），但这是随记忆增长而变糟的那类 bug，
而 `memory_consolidate_min_total=8` 这道门本来就设计成会被越过。

### ③ 几处退化成常量 / 显示错误

- `load_memories`（`memory.py:92`）排序 `weight↓ → hit_count↓ → updated_at↓`：全量注入下
  第三档所有行同时被刷，是常量；第二档同样（线上同一用户 6 条全是 `hit_count=84`，
  它记的是轮数不是相关性）。**实际只有 explicit 那一档在排序。**
- `GET /api/memory` 返回的 `updated_at` 给记忆面板，用户看到的「更新时间」其实是
  「最后注入时间」。
- Phase 17 的「时间更新优先」策略**失去数据基础**——无法再从 `updated_at` 区分
  「用户改了偏好」和「例行注入」。

### 为什么一直没被发现

字段一直有值、值一直在变、变的方向还合理（活跃用户显示「最近更新」看着完全正常）、
无报错无日志。只有拿它去回答一个具体问题——「这条偏好用户多久没提过了」——才发现它答的是
另一个问题。同 Phase 107 的 `color: transparent` 吞掉新颜色：规则命中、语法正确、
computed value 有值，就是不对。

## 方案

### 目标

三个时间各归各位，且**都能被人看到**：

| 语义 | 列 | 谁写 |
| --- | --- | --- |
| 这条记忆什么时候建立的 | `created_at` | 插入时（已有） |
| 内容最后一次变化 | `updated_at` | 只有真的改内容时（upsert / 整理） |
| 最后一次被注入进 prompt | `last_used_at`（新） | `_bump_hit_count` |

### 后端

1. **`models.py`**：`TravelMemory` 加 `last_used_at: Mapped[datetime | None]`（nullable，
   NULL = 从未被注入过）。
2. **`migrate.py`**：幂等加列 + 一次性回填（见下）。
3. **`memory.py::_bump_hit_count`**：改用 Core `update()`，**显式把 `updated_at` 列进 SET
   子句自赋值**——SQLAlchemy 的 `onupdate` 只在该列不在 SET 里时套用：

   ```python
   update(TravelMemory).where(TravelMemory.id.in_(ids)).values(
       hit_count=func.coalesce(TravelMemory.hit_count, 0) + 1,  # SQL 侧自增
       last_used_at=_now(),
       updated_at=TravelMemory.updated_at,     # ← 压住 onupdate
   )
   ```

   已本地实测两个方向都对（只记账不动 / 内容变更要动）。顺带把 Python 侧读改写换成
   SQL 自增——同一用户的 direct 链路不过浏览器池，并发轮次会丢计数。
4. **`memory_api.py`**：`GET /api/memory` 补 `created_at` / `last_used_at`。

### 回填（一次性，靠谓词幂等而非靠"只跑一次"）

`pending_schema_changes` 为空时整块 DDL 会被跳过，但**将来任何新列都会让这块重新执行**，
所以回填必须自带幂等谓词，不能依赖「只运行一次」：

```sql
UPDATE travel_memory
   SET last_used_at = updated_at,     -- 现在的 updated_at 恰恰就是「最后注入」
       updated_at   = created_at      -- 内容变更时间不可恢复，取保守下界
 WHERE last_used_at IS NULL;          -- ← 幂等谓词：跑过一次就永不再命中
```

单条语句：SQL 的 SET 右侧读的是**更新前**的行值，所以 `last_used_at = updated_at` 拿到的是
旧值，顺序无歧义。

**`updated_at` 的历史真值不可恢复**——真实的内容变更时间从来没有任何地方留过。回填成
`created_at` 对「从没改过」的行是准确的，对改过的行会**高估年龄**。选这个方向是因为
Phase 30 这个信号的目的就是触发过期意识：**偏老是安全的**（模型多问一句「这个偏好还作数吗」），
**偏新才有害**（拿一年前的口味当今天的）——同 Phase 104「拿不准时判境外」的不对称代价判断。
失真会在下一次真实内容更新时自愈。

⚠️ **2026-08-24 是时间戳语义的断点日期**：此日之前的 `travel_memory.updated_at` 不可用于
任何分析。

### 前端

5. **`interaction.ts`**：新增纯函数 `formatMemoryAge(iso, nowMs)`。不复用 `formatLastSeen`
   ——它 30 天以上一律「很久以前」，而记忆的价值恰恰在于分辨 25 天和 300 天。
   naive 时间串按**本地时间**解析（勿加 Z），沿用 `Home.tsx:219` 的既有约定。
6. **`Home.tsx`**：`MemoryItem` 补两个字段；`MemoryPanel` 每条下方加一行 meta：
   `建立 N 天前 · 更新 N 天前 · 最后使用 N 天前`。三个时间分开显示，用户能自己看出
   「这条建立很久、最近没被用过」。

## 预期的行为变化（不是回归）

修好之后，活跃用户的记忆在 prompt 里会从「今天」变成真实年龄（如「25 天前」）。
**模型开始对陈旧偏好起疑正是 Phase 30 的设计意图**，不要当成 bug 回退。

## 验收标准

- 只 bump hit_count 时 `updated_at` **不动**、`last_used_at` **动**、`hit_count` +1；
- 真改内容时 `updated_at` **动**；
- 回填语句重复执行结果不变（幂等）；
- `GET /api/memory` 三个时间都在；
- 前端面板三个时间分开显示；`formatMemoryAge` 边界有测试；
- 全量单测通过。

**两个方向的断言都要有**：只测「记账时不动」的话，把整列 `onupdate` 删掉也能过。

## 追加：「✨ 整理记忆」按 key 继承历史

改完上面那段后核实时发现的**第二扇门**：`consolidate_memories`（`memory.py:562`）是
**删旧建新**——

```python
for old in rows:
    db.delete(old)      # 旧行整体删除
...
db.add(row)             # 全新行：created_at / hit_count / last_used_at 全部重置
```

用户点一次「整理记忆」，半年前形成的偏好就变成 **「建立 刚刚 · 更新 刚刚 · 最后使用 从未」**，
刚修好的「年龄标签永远显示今天」从这扇门原样回来。线上已有两个用户整理过
（`4f6a9383` 08-18、`293cbea7` 07-30）。

**方案：按 key 继承。** key 是 Phase 17 归槽的主键，也是**唯一不含猜测**的祖先映射——
N 条合并成 M 条时，「这条新记忆的祖先是谁」没有别的可靠依据。

| 字段 | 规则 |
| --- | --- |
| `created_at` | 继承祖先；无祖先 = 真的新记忆，用现在 |
| `hit_count` / `last_used_at` / `source_conversation_id` | 继承祖先 |
| `updated_at` | **内容一字未改就保持原值**，改了才推到当下（整理常常只是原样带过某个 key，那不是内容变更） |
| `explicit` | **只升不降**（`or`），对齐 `_upsert_by_key` 的粘性语义 |
| 重复 key（不该出现，但要有确定归宿） | `created_at` 取最早、`hit_count`/`last_used_at` 取最大 |

`explicit` 这条单独说：LLM 只看得到内容，**判不出用户当初是不是亲口说的**，而
`CONSOLIDATE_SYSTEM` 还让它「拿不准填 false」。不继承就等于每次整理都在悄悄剥夺 Phase 17 的
「明确表达优先」——`weight` 2.0→1.0，还会丢掉 `select_relevant_memories` 里
「explicit 始终注入」的保底。

**无 key 的旧行历史只能丢**：没有可靠映射，硬猜比丢更糟。

验收见用例表 B11-B18，变异检验：把 `past = ancestry.get(key, {})` 换成 `past = {}` → 红 5 条。

## 刻意不做

- **不动 `_prune` / 不加热度衰减**：线上单用户最多 8 条（`memory_max_rows=40`、
  `memory_select_threshold=12` 都从没触发过），Phase 17 的归槽设计已经用一个 key 一行
  把累积问题解决在更前面。衰减重新有价值的触发条件是模型开始大量自造 canonical 集合外的
  key、单用户越过 12 条。
- **不修 `_should_sleep_consolidate` 的门控语义**：本次改动让它自动变对
  （`updated_at` 恢复真值后，「变更数」就真的是变更数了），不需要额外改代码。
- **不改 `load_memories` 的排序**：hit_count 是常量这件事由归槽设计导致，改排序解决不了，
  且会牵动注入内容——单独评估。
