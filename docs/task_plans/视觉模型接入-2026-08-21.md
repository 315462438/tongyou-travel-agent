# 视觉模型接入（Phase 105，2026-08-21）

DeepSeek 当天上线 `deepseek-v4-flash-vision-exp`。接入前先做了实测（脚本不入库），
**所有设计约束都来自实测数据，不是推测**。

## 实测结论（决定了下面每一条设计）

### ① 有必要：我们付过采集成本的东西，最值钱的部分没打开看

同一篇小红书笔记：

| | 内容 |
| --- | --- |
| `desc`（现在唯一读的） | 「谁懂啊！姐妹们，7-8月的杭州…不做攻略真的会变大冤种！😭」 |
| 图片（从没读过） | places `[九溪十八涧, 西湖风景区, 雷峰塔, 宋城]` / prices `[免费, 40R, 免费, 260R起]` / times `[全天开放, 08:00-20:00, …]` / tips |

4 篇样本里 **1 篇的 desc 是纯话题标签**（`#杭州[话题]##本地人做的攻略[话题]#`），
零信息。视觉救的正是这一类。

### ② 必须 `response_format={"type":"json_object"}` —— 这是性能开关不是格式讲究

| 模式 | 空正文 | 延迟中位 | out token 中位 |
| --- | --- | --- | --- |
| 裸 prompt（max_tokens=3000） | 2/6 | 23.7s | 2622 |
| json_object（同样 3000） | **0/6** | **7.4s** | **743** |

prompt 里**已经写了**Phase 101/102 那套思考纪律，它照样烧满预算。json_object 一开，
思考链自己收住。这给「结构化输出必须走 `parse()`」补了新证据：**在视觉输入下它还是
思考链的刹车**。（这是第四次撞 DeepSeek 思考模式过度推理：Phase 11 / 101 / 102 / 本次。）

### ③ 成本可预测

输入 token 恒定 **~490**，与图片大小无关（112KB 与 476KB 都是 487）。
截图 0.0–0.1s（18–110KB）。并发 6 张墙钟 26.8s / 串行 88.1s（加速比 3.3x，服务端有排队）。

### ④ 页面类型判定：视觉又快又准又省

| 页面 | 现有文本链路 | 视觉链路 |
| --- | --- | --- |
| 知乎问题页 | `content`、正文 55 字 ❌ | `error`「页面显示的是 JSON 格式的错误信息」✅ |
| 百度百科 | `content` ✅ | `content` ✅ |
| 携程登录页 | `login_wall` ✅ | `login_wall`「画面中央有账号密码登录表单」✅ |

视觉推理 1.2–1.7s、in=471 token，**比现有 `_detect_page_type`（喂 3000 字给 v4-flash）更便宜**。
知乎那条是当前存在的真实误判：55 字的 JSON 错误页被当正常来源放行，进 prompt 稀释信号。

### ⑤ 小红书图片 URL <30 分钟过期（顺带发现）

URL 路径里 `202608212202` 是生成时刻；40 分钟前取得的 URL 已 403，库里 660 条 xhs 图
URL 全部 403。**决策（用户拍板）：配图不管了**，`images` 字段留着不动。
但它硬性约束了视觉的接法：**必须在采集当时处理，不能事后补**。

## Stage 1 — 视觉调用基础设施

`app/llm/client.py` 加 `parse_image()`：复用现有 `parse()` 的 schema 校验 + 传输重试
（Phase 103），**强制 `response_format=json_object`**（见实测②），走 `settings.model_vision`。

`app/agent/vision.py`：
- `extract_note_images(urls, ...)` — 小红书图抽取
- `judge_page(screenshot_bytes)` — 页面类型判定
- 统一的失败静默降级：任何异常返回 None，调用方当作「没有图」继续

**开关**：`vision_enabled`（总开关，默认 **True**）、`vision_xhs_enabled`、`vision_page_type_enabled`。
`exp` 模型随时可能变，必须能一键退回。

## Stage 2 — 小红书图抽取（独立车道）

**接在哪**：`collect_xhs_sources` 的 `sink` 回调里，每篇详情落地就把它的图并行发出去。
不塞进 xhs 那 75 秒预算（会挤掉笔记详情额度，触发 Phase 102 的部分收成丢笔记）。

**三条省时纪律**（实测驱动）：
1. **只对 desc 信息量低的笔记跑**（`_desc_is_thin`）。样本里 1/4 命中，成本降 ~75%，
   而且精准命中收益点——desc 本来就是干货的笔记，视觉是纯浪费。
2. **快路径不跑**：`search_mode == "skip"`（资料已足够、不开浏览器）时整段跳过。
   那条路径是全流程最快的一条，加 27s 是倒退；而它成立的前提正是「资料已经够了」。
3. **自己的预算 + 部分收成**（照搬 Phase 102）：`vision_budget_s`(20) 封顶，
   超时交回已完成的，迟到的丢掉。

**产出**：并进 `source["summary"]`，包在 `<note_image_text>` 标签里。

**总时长影响**：常规轮次 **0**（浏览器道始终是长杆——实测三轮 272s/208s/457s vs
xhs 96s/120s/96s）；快路径按纪律 2 直接跳过。

## Stage 3 — 页面类型判定（互补通道，不替换）

`_evaluate_current_page` 里与现有文本判定 **`asyncio.gather` 并行**，
墙钟 = max(文本, 截图 0.1s + 视觉 1.3s) ≈ 不变。

**刻意不直接替换**：文本判定是 Action Guard 三层守卫的一环、跑了很久。先让两者打对台：
- 一致 → 用现有结果，行为完全不变
- **不一致 → 记 warning 日志 + Langfuse span**，仍以文本判定为准
攒够真实数据再决定谁说了算。这是我们在 Phase 93 学到的：**生产里有「失败静默降级」的
地方，不能直接换掉那条路径**。

## Stage 4 — 对话框上传图片

**复用 Phase 74 的上传设施**（`POST /api/uploads`，magic byte 探测真实类型、
边读边判大小、uuid 文件名、`GET /api/uploads/{id}` 故意不鉴权因为 `<img>` 不带 header）。
一行都不用改。

- 前端 composer 加图片按钮 + 粘贴/拖拽，缩略图预览，发送时把 `upload_ids` 一并提交
- `SendMessageRequest` 加 `image_ids: list[str]`（上限 `vision_max_user_images`=4）
- 落库：`travel_message.meta.images`；归属校验（只能用自己上传的图）
- 进模型前：视觉抽取成结构化描述 → 作为**外部内容**注入

## 安全（不能省）

**图片输入绕过了 Phase 69 的全部文本防线。** `wrap_external` 与 `EXTERNAL_POLICY`
都作用在文本上；一张图里印着「忽略之前的指令」是直接进模型的。

两层防：
1. **schema 约束**：视觉模型只能往固定字段填（places/prices/times/tips 等数组），
   塞不进自由文本指令；
2. **输出当外部内容**：视觉产出的 JSON 一律过 `wrap_external` 包裹后再进 prompt，
   与网页正文同等待遇。

用户上传的图额外：只能引用**自己** `user_id` 名下的 upload（越权引用他人图片）。

## 关于「agent runtime 要不要更开放」

用户提的架构问题。**结论：开放输入端，不动控制流。**

想换成开放式 agent（让它自己决定看图/搜索/规划）的话——你们**已经有那个东西**了，
就是 Phase 21 的 deep_research（deepagents）。而它的实际教训写在 CLAUDE.md 里：
弱模型会挥霍浏览器超时，只能靠 system_prompt 里写「硬性资源纪律」硬压。
固定流水线换来的是**可预测、可观测、可停止、有 checkpoint 续跑、有部分收成**——
这些是 Phase 14/16/101/102 一路攒出来的，不该为了「更开放」丢掉。

真正该放开的是两处，都在**输入端**：
1. **`Preference` 的来源**：现在 destination/days/budget 只从文本解析。一张行程截图
   包含全部这些字段——应该允许 `parse_preference` 吃图。
2. **路由的判别力**：`resolve_route(text, ...)` 只看文本。图片进来后意图可能**藏在图里**
   （行程截图=导入、景点照=识别+规划、菜单=记账）。做法是先把图变成结构化线索，
   再喂给现有路由——**不是给路由新增一条「图片链路」**。

本次先做到「图 → 结构化描述 → 进现有链路」。Preference 吃图、路由认图作为
**Phase 106 单独立项**，等上传功能有真实使用数据再定。
