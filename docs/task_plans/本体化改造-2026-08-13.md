# 本体化改造（Phase 86）— Task Plan

日期：2026-08-13　　状态：已完成
面向用户的说明文档：`~/Desktop/working/本体论改造说明.md`（仓库外）

## 一、目标

消除「攻略 Markdown 被三个下游功能各用 LLM 再解析一遍」的结构性问题，
建立规范对象层作为唯一事实源；并把记忆写入收口到带校验的 Action 层。

## 二、问题诊断

攻略以 Markdown 形式生成，而三个消费者都需要它的结构：

| 消费者 | 改造前取结构的方式 |
| --- | --- |
| `app/agent/poster.py` | `llm.parse(guide[:6000], PosterData)` |
| `app/agent/budget.py` | `llm.parse(guide[:6000], BudgetData)` |
| `app/api/trip_api.py` 导入 | 分块 `llm.parse(..., TripImportSummary/Days)` |

后果：
1. 三份互不一致的解读，无法收敛（不是 bug，是三次独立生成的必然结果）；
2. `[:6000]` 截断——预算表通常写在攻略结尾，整表丢失，面板总额远低于正文；
3. 每点一次按钮就是一次完整抽取（数秒~数十秒）；
4. 记忆写入无结构校验，而它是全系统唯一跨会话持久生效的写入，
   且 `plan_memory_ops` 的输入含攻略正文（源自不可信网页）。

## 三、方案

对照 Palantir 本体三原语（Object / Link / Action）。本项目在**协同行程板**链路上已有
大半（`TravelTripStop` 对象、`ChangeOp` 带 `reason` 的 Action、`build_issues` 校验、
`TravelTripSuggestion` 的人工审批），本次是把该模式推广到对话/攻略主链路并补齐 Action 层。

### 涉及模块

| 文件 | 内容 |
| --- | --- |
| `app/ontology/objects.py`（新） | Trip/Day/Stop/Expense/Reservation/Lodging/Food/Specialty；内容派生稳定 id；LINKS 显式声明 + 访问器；`normalized()` 归一去重重排序 |
| `app/schemas/ontology_schema.py`（新） | 唯一的抽取 schema，Summary / Days / Full 三个模型 |
| `app/ontology/extract.py`（新） | 短攻略单次抽取；长攻略按 Day 切块（全局一次 + 逐日分块）；单块失败只记 `failed_days` |
| `app/ontology/store.py`（新） | `ensure_trip_object()` 抽一次+缓存；`source_hash` / `schema_version` 双重失效 |
| `app/ontology/projections.py`（新） | `to_poster_data` / `to_budget_data` / `to_trip_draft` / `to_outline`，纯函数零 LLM |
| `app/ontology/actions.py`（新） | `Action` 基类、`SetMemory` / `DeleteMemory`、`apply_actions` 校验→应用→审计 |
| `app/db/models.py` | 新表 `TravelGuideObject`（message_id 唯一） |
| `app/config.py` | `ontology_enabled` / `ontology_extract_max_chars`(24000) / `ontology_day_batch`(4) |
| `app/agent/poster.py` | 抽出 `_poster_data()`：优先投影，异常/关闭时回退旧路径 |
| `app/agent/budget.py` | 抽出 `_budget_data()`：同上 |
| `app/agent/memory.py` | `apply_ops` 改为构造 Action 交给 `apply_actions` |
| `app/api/trip_api.py` | `_draft_from_ontology()` 快路径（只用已缓存对象图；`only_days` 重试仍走原路径） |

### 关键设计决策

- **投影目标是既有视图模型**（`PosterData`/`BudgetData`/`TripDraft`），
  所以 poster 的补坐标流水线、budget 的服务端汇总、导入的落库逻辑一行不用改。
- **懒构建不预热**：用户未必点海报/预算，为每份攻略预抽是白花成本。
  第一个点击者承担抽取，之后全部命中缓存。
- **导入快路径只读缓存、不触发抽取**：`_extract_import_draft` 那条路更成熟
  （逐天进度回调、按天重试、分块并发），没缓存时应当走它。
- **保留 keyless add 旧行为**：归槽是目标，但静默丢一条合法记忆比多一条散条更糟。

### 明确不做

运行时本体注册表、marking/ACL、数据血缘、kinetic writeback、独立审计流水表。
理由与「本体只覆盖持久实体、不覆盖易腐的爬取数据」一并见 `~/Desktop/working/本体论改造说明.md`（仓库外）第七节。

### 中途修正（值得记录）

初版 Action 层加了两条基于来源可信度的防线：①外部来源不得覆盖 explicit 槽位；
②外部来源写入不得标 explicit。跑测试时 `test_explicit_is_sticky_and_weighted` 失败，
复核发现该测试明确断言「后续推断内容覆盖，但 explicit 粘性不降级」——这是 Phase 17
有意的产品决策。且防线①还有反效果：注入若先抢占槽位并标 explicit，用户之后在对话里的
更正也会被挡住（对话链路的写入同样是模型规划的）。**两条防线均已撤回**，只保留与措辞
无关的纯结构校验。该张力记在说明文档第六节，留给产品决定。

## 四、验收标准

1. `tests/test_ontology.py` 全绿；全量套件不新增失败。
2. 点海报后再点预算，第二次不产生 LLM 抽取调用（有测试断言 `llm.calls`）。
3. `ontology_enabled=False` 时两个面板回退旧路径且功能正常（有测试）。
4. 攻略正文被多轮修改重写后，对象图自动重建（有测试）。
5. 记忆内容含 URL / 标签字面量 / 超长 / 非法 key 一律被拒且不影响同批其余动作（有测试）。
