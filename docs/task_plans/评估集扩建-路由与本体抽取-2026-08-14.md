# 评估集扩建：路由分类 + 本体抽取 + 过程验证换证据源

> 2026-08-14　Phase 93

## 背景

`backend/evals/` 立于 2026-08-04，测的是**攻略正文的输出质量**：11 条 query、
11 个规则检查、三层验证（结果/过程/质量），端到端跑真实流水线，一轮约 1 小时。

这之后加进来的东西落在它的射程外：

| 新增 | 现状 |
| --- | --- |
| 本体层（Phase 86） | `tests/test_ontology.py` 41 条**全 mock LLM**，真实抽取准确率零度量 |
| 路由三分类（Phase 22/23） | 零覆盖 |
| 轨迹接口（Phase 90） | 已有，但评估的过程层没用上 |

而 61 篇踩坑记录里大部分是基础设施（`create_all` 不加列、`cp -r` 嵌套目录、
snap chromium 多实例），归单测和部署脚本管——**不进输出质量闸门**，
沿用 `checks.py` 开头那条门槛：「新增检查项必须是线上真实翻过车的形态」。

## 目标

补三件事，都**不动**原有那个重家伙（`queries.yaml` 一轮 1 小时，不扩条数）：

| | 内容 | 成本 |
| --- | --- | --- |
| A | 本体抽取评估集 | 输入固定在磁盘，只调抽取那一步 |
| B | 路由分类评估集 | 单次 v4-flash，35 条约 1 分钟 |
| C | 过程验证改用轨迹 span 当主证据源 | 无 LLM 消耗 |

## A. 本体抽取评估集

**为什么最优先**：`app/ontology/extract.py` 是全系统唯一一处从攻略抽结构，
海报 / 预算 / 行程导入三个消费端全挂在它下面——抽歪一次，三处一起歪。

### 样本

5 篇真实线上攻略，天数跨度 3/3/5/7/10，其中 7 天和 10 天**超过
`ontology_single_call_max_days`(6)，走分块路径**。

样本**不进 git**：真实用户会话的产物，已核对不含手机号/证件号/邮箱，
但没必要把用户内容放进代码仓库。`extract.yaml` 登记 `message_id` + `sha256`，
`python -m evals.fetch_samples` 拉取并**校验哈希**——输入漂了而期望没改，
是最难查的一种评估失真。

### 检查项

每一项都对着下游一个具体的坏结果：

| code | 下游后果 |
| --- | --- |
| `ext_missing_days` / `ext_failed_days` | 海报少一张图、导入的行程少一天 |
| `ext_empty_day` | 海报那天是张白图 |
| `ext_missing_landmark` | 正文加粗写着的主地标没进路线 |
| `ext_total_as_item` | **预算总额翻倍**（合计行进了逐项，服务端再求和） |
| `ext_headcount` | 「两人合计」认成 1 人 → 人均金额整体翻倍 |
| `ext_no_expenses` / `ext_zero_amounts` | cost 路整条静默失败 |
| `ext_markdown_residue` | `**黄鹤楼**` 原样显示在海报里 |
| `ext_empty_lane_registered` | **空结果被缓存固化，永不重试** |

最后一条值得单说：`build_trip_object` 里某一路失败时**不登记进 `lanes`**，
下次调用才会重试它。反过来——空结果却登记了——会让缓存把「什么都没有」
当成功结果焊死，而且是**静默且长期**的。

## B. 路由分类评估集

**为什么值得单独立集**：分错的代价直接落在用户身上——

- guide 判成 direct → 该联网查的没查，用户拿到一段凭参数知识编的回答
- direct 判成 guide → 问「武汉交通如何」要等两分钟看一段常识

35 条，覆盖 direct 14 / guide 15 / research 6。判错分两级：

- **硬错**：落在 `tolerate` 之外，用户直接感知
- **软错**：设计允许的保守降级（ROUTE_SYSTEM 自己写着「拿不准时一律选 guide」，
  且 research 在服务器未启用时本来就退化成 guide）

闸门只看硬错——把软错也当失败，会逼着我们去「优化」一个本来就正确的降级。

`--repeat N` 跑多次看**摇摆**：摇摆比稳定判错更危险，稳定错能一次修掉，
摇摆的会随机复发，所以报表把它单列，不混进准确率。

数据集自身也有护栏（`tests/test_evals_routes.py`）：id 不重、expect 合法、
每条都写了「守什么边界」、**没有一条的 tolerate 覆盖全部通道**——那样的用例恒真，
留在集里只会稀释信号（立集时 `周末想出去玩有什么推荐` 就是这样一条，已删）。

### 首轮基线（线上，2026-08-14）

```
严格准确率 91.4%（32/35）　硬错 0　软错 3

| 期望＼实际 | direct | guide | research |
| direct     |   12   |   1   |    1     |
| guide      |    0   |  15   |    0     |
| research   |    1   |   0   |    5     |
```

guide 一行满分（15/15）——最贵的那类错（该查没查）一次都没发生。

三条软错都是边界上的合理分歧，其中 `b_long_but_direct` 值得留意：
「我下个月要带父母去旅游…这种情况下安排行程一般要注意些什么」耗时 **0.0s**，
说明它是被 `is_explicit_itinerary_request` 的**确定性关键词短路**判成 guide 的，
根本没到模型。这是一条真实的边界瑕疵（长的**建议类**提问被关键词误判成规划），
但代价只是慢，不是错，暂不改规则——先记在这里。

### 首轮基线（线上，2026-08-14）

| 样本 | 结论 | 耗时 | 天 | 停留点 | 开销 | 人数 |
| --- | --- | --- | --- | --- | --- | --- |
| tiantangzhai_3d_short | ❌ | 140.4s | 3 | 11 | 14 | 2 |
| wuhan_3d | ✅ | 125.5s | 3 | 15 | 13 | 2 |
| chongqing_5d_drive | ✅ | 93.9s | 5 | 20 | 13 | 3 |
| malaysia_7d_overseas | ❌ | 266.6s | 7 | 37 | **0** | 2 |
| yushu_10d_long | ✅ | 243.0s | 10 | 40 | 32 | 2 |

两条不通过，**性质完全不同**：

**① `malaysia_7d_overseas` —— 一个真实的线上缺陷，评估集第一轮就抓到了**

```
ontology cost failed: 结构化输出达到 8000 tokens 上限，已在 JSON 中途截断
```

itinerary 路天数多会**分块**（`ontology_single_call_max_days`），
但 **cost 路从来不分块**——整篇 12k 字喂进去，要求一次输出全部逐项开销。
7 天跨 3 地的攻略逐项几十条，在 8000 处截断 → 整条 cost 路失败 →
**线上这类行程点「💰 预算明细」是空的**。

根因是一次局部调优的适用范围没写清楚：`ontology_cost_max_tokens=8000` 那组
「实测最快」是在 3-5 天短攻略上量的。修法是按天数分档（与
`ontology_single_call_max_days` 同口径），短行程维持 8000 不拖慢：

```python
long_trip = len(sections) > settings.ontology_cost_long_days   # 6
max_tokens = 16000 if long_trip else 8000
```

回归测试 `tests/test_ontology.py::test_cost_lane_gets_a_bigger_output_budget_on_long_trips`
两个方向都钉住——长行程要更大预算，**短行程必须维持 8000**。

修复后复跑（`extract-fix`）：

```
tiantangzhai_3d_short  ✓ 91.7s   3天  8点 11项
malaysia_7d_overseas   ✓ 154.0s  7天 38点 34项   （原：266.6s / 0 项）
```

开销从 0 条变 34 条，而且**更快了**——原来的 266s 里有一大半花在
「截断 → 重试 → 又截断」的循环上。

**② `tiantangzhai_3d_short` —— 是我的期望值错了，不是模型错**

我按表头「预算估算表（人均）」把 `expect_headcount` 填成 1，模型给 2。
核对正文：表身写着「按200元/间/晚，**两人分摊**」——`headcount` 是**同行人数**，
不是金额口径，模型是对的。已改期望值。

> 新评估集的第一轮，找到的多半是评估自己的错。这条留在 yaml 注释里，
> 提醒后来者别反过来去「修」模型。

## C. 过程验证换证据源

原来的 `tool_sequence()` 靠正则匹配**进度气泡文案**还原工具序列。
文案是 UI 层的字符串，改一句就可能让整层静默失效（`verify_process` 的规则⑥
就是为此加的补丁）。

改成以 **Langfuse 轨迹的 span 名**为主证据源，进度文案降为回退。
span 名是代码里的常量，改它必然是有意的。

配套补了缺失的 span——这些工具**此前在轨迹面板里也是隐形的**，
guide 轮点开轨迹几乎看不到工具：

| span | 位置 |
| --- | --- |
| `xhs_search` / `xhs_detail` | `app/tools/xhs_mcp.py` |
| `amap_city_brief` | `app/agent/orchestrator.py: _collect_amap` |
| `site_ctrip` / `site_xhs` | `app/agent/site_router.py: collect_via_site` |

`collect_via_site` 因此拆成「外壳（挂 span）+ `_collect_via_site`（实现）」。
span **含登录等待在内**——那段等待本来就该在轨迹里看得见，它常常是整轮最慢的一段。

规则⑥的判据同步改成「**两个证据源都空**才算失效」；另加规则⑦：
主证据源在用轨迹时，如果进度文案模式已经全部打空，**警告但不判失败**——
Langfuse 一旦停用这层会毫无征兆地退化，得有人看见。

## 跑评估的两条环境约束

1. **本机连不上 `api.deepseek.com`**（服务器可以）→ 评估要在服务器上跑：
   `ssh ubuntu@… 'cd /home/ubuntu/travel-agent/backend && .venv/bin/python -m evals.…'`
2. **`deploy.sh` 的 `rsync -az --delete` 会清掉服务器上的 `evals/runs/`**，
   用本地那份覆盖。所以「在服务器跑完 → 再部署一次 → 回头取快照」会取到被覆盖的旧文件。
   顺序必须是**先部署，再跑评估，跑完立刻取回快照**。（立集当天就这么丢过一次基线。）

## 一个当天踩的坑

第一次跑路由评估报出「准确率 42.9%，模型严重偏向 guide」，是**假的**——
跑评估的机器连不上 `api.deepseek.com`，而生产的 `decide_route` 把 API 异常
兜底成 `guide`，评估直接复用它，于是断网和「模型判成 guide」返回值完全一样。

详见 `docs/pitfalls/评估器把断网算成了模型判错.md`。一般化的教训：

> **凡是生产代码有「失败时静默降级」的地方，评估都不能直接复用那条路径。**

## 刻意不做

- **不把 61 篇踩坑逐条变成检查项**：大半是基础设施问题，塞进输出质量闸门只会稀释信号
- **不扩 `queries.yaml`**：已经 1 小时/轮，每加一条多约 5 分钟真实消耗，问题不在条数少
- **不做 LLM 打分**：沿用 `checks.py` 的原判断——分数波动分不清是模型抖动还是真退化
- **不把评估接进 CI**：要真实 LLM 调用和线上环境，定位是「大改动前后手动对照」
