# Task Plan · 多城目的地消费点全量修复（2026-08-01）

## 背景

`Preference.destination` 在多城行程里是**顿号连接的整串**（「吉隆坡、仙本那、亚庇」）。
凡是把它当**单个城市名**用的地方都会错。一天之内已经因此连修三处（跨会话历史检索的
标题匹配、行程坐标定位、携程相关性校验），说明该做全量扫描而不是被报一次修一处。

## 扫描结果（`grep -rn "pref\.destination" app/` 全部 18 处）

| 消费点 | 判定 |
| --- | --- |
| `_xhs_query_plan` | ✅ 已用 `split_cities` 逐城 |
| `reuse_recent_xhs_sources` / `recall_past_chats` / `recent_plan_hint` | ✅ 今日已修 |
| hotel 分支 `split_cities` + `_collect_with(dest=…)` / `_dest_in_page` | ✅ 今日已修 |
| `_geocode_stops_by_city` / `_trip_city_for_day` | ✅ 今日已修 |
| `_index_conversation` | ✅ 存整串、读时 split，设计如此 |
| `_waypoint_directive` | ✅ 仅作展示文案 |
| **`_collect_amap` → `build_amap_source`** | ❌ **P0**：整串去 geocode 必失败 → 天气+景点坐标**整条丢失**且静默 |
| **`route_for_intent`** | ❌ `_norm_city(整串)` 查不到 → route 意图直接不路由 |
| **`_build_queries`** | ❌ 整串塞进必应查询词 |
| **`decide_revision`** | ❌ 字符串相等比较，多城顺序一变就判「换了目的地」→ 无谓重搜 |
| **`_is_relevant`** | ❌ 多城不命中（退化到旅行关键词，影响小但应一致） |

P0 实测（服务器）：

```
'吉隆坡、仙本那、亚庇' -> None（整条高德数据丢失）
'武汉、开封、洛阳'     -> None（整条高德数据丢失）
'武汉'                 -> 有来源
```

## 方案

1. **`_collect_amap` 逐城**：按 `split_cities` 取前 `amap_max_cities`(3) 城各建一条来源，
   任一城成功即有数据；全失败才返回空。
2. **`route_for_intent`**：内部对多城取首城（hotel 分支已有 `split_cities` 逐城逻辑，
   这里是给 route 意图兜底）。
3. **`_build_queries`**：多城时逐城生成查询（受必应限流约束，取前 2 城），
   不再把整串当关键词。
4. **`decide_revision`**：目的地比较改成**城市集合相等**，与顺序无关。
5. **`_is_relevant`**：与 `_dest_in_page` 一致，任一城命中即算相关。
6. **携程选城排序**（用户本轮另一个诉求）：不再按目的地串的字面顺序取前 N，
   改为**住宿意图优先**——用户原话/特殊要求里紧邻「住/酒店/度假村/民宿/晚」等词的
   城市排前面。纯字符串判断，无额外 LLM 调用、零延迟。
