| # | 场景 | 预期 |

## C. 登录 handoff（自动化 ✅）

| # | 场景 | 预期 |
| --- | --- | --- |
| C1 | 打开站点直接可读 | 正常抓取，返回带 site 标记的来源，无 handoff 卡片 |
| C2 | 登录墙 → 用户完成登录 | 写入 meta.handoff 的 progress 消息（卡片）；轮询用 check_page（不导航、不打断用户输入）；检测到可访问后重开目标页继续抓取 |
| C3 | 登录墙 → 用户始终未登录 | 等待 handoff_wait_s 超时 → 返回空 → progress 提示回退公开搜索 |
| C4 | 服务器 headless 模式（chrome_executable 非空） | 不发卡片、不轮询，直接回退搜索 |
| C5 | blocked 页面（如 payment） | 返回空，回退搜索 |
| C6 | 页面内容 <200 字（反爬空壳） | 不作为有效来源 |
| C7 | 摘要 LLM 失败 | 摘要退化为原文截断，来源仍有效 |

## D. 端到端手工验收

前置：`db_tunnel.sh`、`start_chrome.sh`、后端 :8000、前端 :5173。

| # | 步骤 | 预期 |
| --- | --- | --- |
| D1 | 输入「帮我查一下成都市中心的酒店，预算500左右一晚」 | progress 出现「检测到酒店需求，正在打开携程…」；调试 Chrome 导航到携程；若命中登录墙，对话流出现蓝色「携程」登录卡片 + 等待动画；登录后自动继续；超时则回退必应；最终输出酒店推荐（HOTEL_SYSTEM 格式） |
| D2 | 输入「帮我规划成都3天的路线，节奏轻松」 | 同上，站点为小红书（红色卡片），最终输出攻略 |
| D3 | 先生成攻略，再追问「帮我查下那边的酒店」 | 不复用旧来源直接生成，而是走携程路由补充酒店来源 |
| D4 | 界面（GPT 风格） | 侧边栏会话列表可切换/新对话；空态居中标题+胶囊输入+建议 chips；用户右侧灰气泡、助手全宽正文；「已深度思考」可折叠；底部胶囊 composer + 免责提示；导出长图可用 |
