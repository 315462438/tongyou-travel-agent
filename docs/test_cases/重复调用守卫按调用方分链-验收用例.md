# 重复调用守卫按调用方分链 — 验收用例

对应计划：`docs/task_plans/重复调用守卫按调用方分链-2026-08-18.md`（Phase 95）

自动化落点：`backend/tests/test_dsh_ports.py`（与 Phase 89 原有的 repeat guard 测试同文件）

```bash
cd backend && .venv/bin/python -m pytest tests/test_dsh_ports.py -q
```

全部离线，无 LLM、无网络、无数据库。

## 一、分链正确性（改动的目的）

| # | 用例 | 断言 | 测试 |
| --- | --- | --- | --- |
| 1 | 三个并发子代理各用**相同参数**调同一工具一次 | 一次都不该提醒；各自再调到第 3 次才各自提醒 | `test_concurrent_owners_do_not_accumulate_into_one_chain` |
| 2 | 主 agent（owner 空串）与子代理交替调同参 | 子代理首次不提醒；主 agent 第二次才提醒 | `test_main_agent_and_subagent_are_separate_chains` |
| 3 | 同一子代理跨 3 个 superstep（ns 尾段每步变、前缀不变） | owner 三次相同，链不断，第 3 次提醒 | `test_same_owner_chain_survives_across_supersteps` |
| 4 | 顶层图（主 agent）的 ns 只有一段 | owner 为空串 | `test_owner_of_top_level_graph_is_empty_string` |

用例 1 是整个改动存在的理由：共享单链时第三次调用会收到一句**事实错误**的系统提示
（「你已经连续 3 次调用 X」，而它其实是第一次调）。

用例 3 钉住的是「为什么不能用 `parent_run_id`」——它每个 superstep 都变。

## 二、健壮性（失败只许退化，不许打断）

| # | 用例 | 断言 | 测试 |

| 6 | 完全不传 config 直接调用包装后的工具 | 退化成共享单链，正常计数不报错 | `test_guard_tool_still_works_without_any_config` |
| 7 | `reset()` 后 | 所有 owner 的链都清零 | `test_reset_clears_every_owner` |
| 8 | 灌 50 个不同 owner、上限设 4 | `_chains` 不超过 4 | `test_owner_table_does_not_grow_without_bound` |

## 三、三个「静默失效点」（漏了不报错，功能直接死）

这三条对应计划里点名的三个坑。它们的共同特征是**出问题时没有任何异常**，
只是守卫悄悄退回老行为或彻底不触发，所以必须由测试钉住。

| # | 用例 | 断言 | 测试 |
| --- | --- | --- | --- |
| 9 | 同一 owner、同参数，但两次的 config **内容不同**（ns 尾段变了） | 仍判为同一条链 → 第二次提醒（证明 config 没进链键） | `test_config_is_not_part_of_the_chain_key` |
| 10 | 包装后的函数交给 `StructuredTool.from_function` | 模型可见参数只有 `keyword`/`city`，**没有 config** | `test_config_is_hidden_from_the_model_visible_schema` |
| 11 | 包装一个工具后检查原函数 | 原函数 `__annotations__` 未被塞进 `config` | `test_wrapping_does_not_pollute_original_annotations` |
| 12 | 包装后的签名 | `["city", "kw", "config"]`——原参数顺序不变，config 追加在后 | `test_guard_tool_preserves_signature_for_schema_inference`（Phase 89 原测试，本次更新） |

## 四、透传与端到端

| # | 用例 | 断言 | 测试 |
| --- | --- | --- | --- |
| 13 | 原函数**自己声明**了 `config` | 透传给原函数（`is` 同一对象），且仍不进链键 | `test_tool_declaring_config_itself_gets_it_passed_through` |
| 14 | 包装后的工具靠注入的 config 分链（不直接调 `check`） | 两个 owner 各自独立，a 的第二次才提醒 | `test_wrapped_tool_routes_by_injected_config` |
| 15 | **集成**：真实 `langgraph.prebuilt.ToolNode` 路径，并发两个子图各调一次同参工具 | config 确实被注入（owner 非空）且两个 owner **不相同** | `test_toolnode_really_injects_distinct_owners_for_concurrent_subagents` |

用例 15 是整个方案的地基。deepagents 的子代理内部就是走 ToolNode 执行工具的；
若哪天 LangGraph 不再注入 config，守卫会**静默**退回共享单链（不报错、只是变回老行为），
没有这条测试就永远发现不了。该测试不调任何 LLM——直接喂一条带 `tool_calls` 的
`AIMessage` 给 ToolNode。

| # | 用例 | 断言 | 测试 |
| --- | --- | --- | --- |
| 16 | 对**真实** `build_tools` 产物（9 个工具）逐个校验 | 每个都能被 `to_tool` 转换、签名含 config、schema 不含 config、原参数顺序不变 | `test_every_real_research_tool_survives_wrapping` |

用例 16 是给**将来**用的：新增研究工具时如果签名或包装出问题，这里会直接红。
实测覆盖 `web_search` / `open_page` / `read_source`×2 / `amap_city_brief` / `amap_poi` /
`fetch_url` / `xhs_search` / `xhs_detail`。
