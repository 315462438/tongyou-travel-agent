# 评估集扩建 · 验收用例

> 2026-08-14　Phase 93　对应 `docs/task_plans/评估集扩建-路由与本体抽取-2026-08-14.md`

评估器本身也会写错，而**一个永远返回「通过」的检查器比没有检查器更糟**——
它让人以为守住了。所以这批用例的写法统一是：构造一个**故意坏掉的输入**，
断言对应检查项确实报警。

自动化：`tests/test_evals_extract.py`、`tests/test_evals_routes.py`、
`tests/test_evals_verify.py`（新增「证据源升级」一组）、`tests/test_evals_checks.py`（原有）。

```bash
cd backend && .venv/bin/python -m pytest tests/test_evals_*.py -q
```

## 二、路由分类评分（`tests/test_evals_routes.py`）

| # | 用例 | 断言 |
| --- | --- | --- |
| 2.1 | 判对 | `hit` |
| 2.2 | research → guide，且在 `tolerate` 里 | `soft`（不是 hard） |
| 2.3 | guide → direct，不在 `tolerate` 里 | `hard` |
| 2.4 | 一 hit 一 soft | 严格准确率 **0.5**——软错不算答对 |
| 2.5 | **跑挂（`run_error`）** | 独立 `error` 档；分母只算跑成的；不进混淆矩阵 |
| 2.6 | 多次跑结果不一致 | 进 `unstable` 单列 |
| 2.7 | 混淆矩阵 | 按期望类归行 |
| 2.8 | `routes.yaml` 自洽 | ≥30 条、id 不重、expect 合法、expect 不在 tolerate 里、每条有 note |
| 2.9 | 三个通道各 ≥5 条 | 否则混淆矩阵有空行 |
| 2.10 | **没有一条 tolerate 覆盖全部通道** | 那样的用例恒真，是送分题 |

> 2.5 是当天真踩的坑固化下来的：生产 `decide_route` 把 API 异常兜底成 `guide`，
> 评估若直接调它，断网会长得和「模型判成 guide」一模一样。
> 见 `docs/pitfalls/评估器把断网算成了模型判错.md`。

## 三、过程验证换证据源（`tests/test_evals_verify.py` 新增组）

| # | 用例 | 断言 |
| --- | --- | --- |
| 3.1 | 轨迹含 `amap_city_brief`/`xhs_search`/`xhs_detail`×2/`site_ctrip` | 还原成 4 步，连续重复合并，`site_ctrip`→`ctrip_hotels` |
| 3.2 | 轨迹只有 `OpenAI-generation` 与 `conversation_turn` | 空序列（模型调用和轮外壳都不是工具） |
| 3.3 | **进度文案全改 + 轨迹有 span** | 用轨迹、判通过、不报 `proc_unrecognized_trail` |
| 3.4 | 同 3.3 | 但仍 warn「回退路径失效」 |
| 3.5 | 轨迹为空（Langfuse 未启用/落库延迟） | 回退进度文案，`sequence_source == "progress"` |
| 3.6 | **两个证据源都空** | 仍判失败 + `proc_unrecognized_trail` |

3.3 是这次改造的核心：改造前文案一改整层就失效（靠规则⑥兜住报红），
改造后 span 名是代码常量，改它必然是有意的。
3.6 保证元规则没被削弱——不能因为多了一个证据源就放行。
