# 验收用例 · 区域型提问给候选（2026-08-05，改造 ②）

## 背景

08-04 真实数据：8 个提问的新用户里 **3 个首问是区域型表达**——「合肥周边」「皖南」
「合肥周边溯溪」。这是「我想出去玩但不知道去哪」，恰恰是产品最该发挥价值的场景，
原来却一律被反问、要求用户先自己选个城市。

**产品决策：只列候选、等用户选**，不直接按最推荐的那个出完整攻略。
候选 ~14 秒返回，完整攻略要 140-898 秒；方向没确认前先跑几分钟，猜错纯浪费，
猜对也显得自作主张。

## 自动化

```bash
cd backend && .venv/bin/python -m pytest tests/test_destination_candidates.py -q   # 9 条
cd frontend && npm test
```

| 用例 | 断言 |
| --- | --- |
| A1 给出候选 | 区域型提问返回 name/reason/tag 三元组 |
| A2 走快模型 | 必须用 `model_classifier`——慢了这个方案就没意义 |
| A3 占位词拦截 | 「热门目的地」「周边」被丢弃（候选会被原样当成下轮目的地送进搜索，踩过坑） |
| A4 去重 | 同名候选只留一个 |
| A5 上限 3 个 | 不刷屏 |
| A6 失败回落 | LLM 抛错返回空 → 调用方回落原文字反问，不打挂整轮 |
| A7 空结果 | 模型返回空列表时同样回落 |
| A8 熔断计数 | **候选卡计入追问轮数**，否则连续给候选=换皮的无限追问 |
| A9 正常攻略中断计数 | 攻略消息会终止连续计数 |
| B1 前端渲染 | `meta.candidates` 渲染成可点卡片 |
| B2 点击即发 | 点候选直接以「去{地名}」发出，用户不用打字 |
| B3 留出路 | 有「都不合适？直接说个地名，或者让我来定」，不做成只能三选一 |

## 人工走查

| 用例 | 步骤 | 期望 |
| --- | --- | --- |
| M1 区域型 | 问「皖南的2日游，风景好」 | ~15 秒内出 3 张候选卡，彼此有区分度 |
| M2 点击 | 点其中一张 | 自动发出「去XX」并开始排行程 |
| M3 出路 | 不点卡片，直接打「宣城」 | 正常继续 |
| M4 熔断 | 连续两轮都不给具体地名 | 第三轮强制代选，不再给候选 |
| M5 明确目的地 | 问「我想去黄山玩3天」 | **不出候选**，直接排行程 |

线上实测（08-05）：「皖南的2日游，风景好」→ 14 秒 →
黄山风景区[登山云海] / 宏村[古村慢逛] / 牯牛降[山林野趣]。
